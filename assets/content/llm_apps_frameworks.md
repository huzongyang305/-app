## 核心概念定义

| 术语 | 操作性定义 | 常见边界与风险 |
| --- | --- | --- |
| Runnable | 统一实现调用、批处理、流式三种接口的组件协议。 | 易错：只有链才是 Runnable，模型与解析器同样是。 |
| 组合表达式 | 用竖线把多个组件按数据流方向串联的写法。 | 易错：把它读成并发或降级，实际是严格的顺序传值。 |
| Chain | 一段可复用的处理流程，输入输出形状明确。 | 易错：链越串越长，中间态不可见时难排查。 |
| Agent Executor | 由框架驱动的工具循环运行器。 | 易错：把它当黑盒，缺自定义终止与回调。 |
| Index | 文档经切块与嵌入后形成的可查询结构。 | 易错：索引一次建好不再管，增量与删除会失真。 |
| Retriever | 只负责「给问题返回若干相关片段」的组件。 | 易错：以为它会组织答案，它不生成文本。 |
| QueryEngine | 从提问到回答的完整链路封装。 | 易错：直接用它就无法在检索与生成之间插入自定义步骤。 |
| 输出解析器 | 把自由文本转成结构化对象的组件。 | 易错：不配校验，解析成功不代表字段合法。 |
| 持久化存储 | 把向量、文档与图结构落盘的适配层。 | 易错：本地内存库当生产用，重启即丢。 |

## 原理与运行机制

### 机制总览：两个框架的重心差异

一个偏「把调用组合起来」，抽象单位是可串联的组件；另一个偏「把数据组织起来」，抽象单位是索引与查询引擎。多数团队最终会同时用两者：用前者编排流程，用后者管理检索。

**教材衔接：组合表达式的传值语义**

竖线只是把左边的输出当作右边的输入。理解一条链的正确方式是逐步问「这一步吃什么、吐什么」。

```python
from langchain_core.runnables import RunnableLambda
upper = RunnableLambda(lambda s: s.upper())
exclaim = RunnableLambda(lambda s: s + '!')
chain = upper | exclaim
print(chain.invoke('rag'))
```

**教材衔接：最小 RAG 链的骨架**

```python
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser

prompt = ChatPromptTemplate.from_messages([
    ('system', '只依据资料回答，资料不足时回答未知。'),
    ('user', '资料：{context}\n问题：{question}'),
])

def pack(v):
    return {'question': v, 'context': '\n'.join(d.page_content for d in retrieve(v))}

chain = {'question': RunnableLambda(pack)} | prompt | model | StrOutputParser()
```

**教材衔接：Retriever 与 QueryEngine 的分工**

| 维度 | 检索器 | 查询引擎 |
| --- | --- | --- |
| 输入 | 一段查询文本 | 一个用户问题 |
| 输出 | 若干文档片段 | 一条完整回答 |
| 是否调用生成模型 | 否 | 是 |
| 适合定制的点 | 召回策略、过滤条件、重排 | 提示词、引用格式、多步查询 |
| 典型误用 | 拿它直接回答用户 | 在它的提示词里硬塞检索逻辑 |

需要「先检索、再判断是否够用、不够就改写问题重查」时，应当把检索器拿出来自己编排；只需要「提问得到带引用的答案」时，查询引擎更省事。

**教材衔接：可插拔的正确姿势**

组件之间只通过协议相接，实例由外部注入。业务代码里出现具体模型类名或具体向量库类名，通常就意味着替换成本已经产生。

```python
def build_chain(model, retriever, parser, prompt):
    def load(q):
        return {'question': q, 'context': render(retriever.invoke(q))}
    return {'question': RunnableLambda(load)} | prompt | model | parser
```

**教材衔接：版本迁移的三级排查顺序**

| 级别 | 现象 | 定位方式 | 常见修法 |
| --- | --- | --- | --- |
| 消息角色 | 系统提示不生效 | 打印请求体角色序列 | 改用统一的角色元组写法 |
| 序列化模板 | 变量没被替换 | 单步跑提示词模板 | 从字符串模板换成消息模板 |
| 导入路径 | 启动即报错 | 按报错栈逐级上溯 | 迁到新的包名与入口 |

## 典型应用场景

| 场景 | 推荐组合 | 说明 |
| --- | --- | --- |
| 文档问答最小可用版 | 索引加查询引擎 | 快速验证语料质量 |
| 需要引用与合规话术 | 自建链加检索器 | 在提示词层精确控制 |
| 多步任务与工具调度 | 链与执行器混用 | 结构化步骤用链，开放步骤用执行器 |
| 复杂文档结构解析 | 专门的加载器加分层索引 | 表格与代码块单独成块 |
| 换模型做成本对比 | 注入式构造 | 同一条链换模型实例即可 |

- 典型现象：本地跑通、上线后回答变短。正确做法：检查默认最大输出长度与提示词模板是否随版本变更。
- 典型现象：换供应商后工具调用全部失效。正确做法：把工具声明与强制策略从框架默认值改为显式传入。
- 典型现象：检索召回正常但答案忽略资料。正确做法：把资料块放在问题之前，并在系统提示中重申约束。

### 最小验证场景

- 准备：二十段固定语料，其中只有一段能回答问题，构造一个必须引用它的问题。
- 观察：检索器返回的第一条是否为目标段落，链是否把它写进了提示词，回答是否给出来源标识。
- 判定：回答内容仅来自目标段落；若出现语料外事实，说明约束提示未生效或被截断。

### 项目专属规格

- 语料规格：仅收录 Markdown 与纯文本，单文件不超过 200KB；表格转成逐行文本再切块。
- 分块规格：目标 700 字符、重叠 120 字符，段落边界优先；标题作为元数据随块携带。
- 检索规格：向量召回 `top_k=6`，重排后取 `top_n=3`，相似度阈值 0.32 以下直接丢弃。
- 生成规格：温度固定 0.2，最大输出 800 Token，系统提示必须包含「资料不足回答未知」。
- 时延与成本规格：单次问答 P95 不超过 4 秒，输入 Token 中位数不超过 2200。
- 兼容规格：模型与向量库均通过构造注入，替换任一实现时业务代码改动不超过一个文件。

## 时间/空间复杂度或性能分析

| 指标 | 随什么增长 | 典型区间 | 优化手段 |
| --- | --- | --- | --- |
| 建索引耗时 | 文档数与嵌入调用次数 | 线性偏网络受限 | 批量嵌入加并发 |
| 单次检索耗时 | 向量规模与索引类型 | 毫秒到数十毫秒 | 用近似索引并调候选参数 |
| 端到端时延 | 链上步骤数乘模型时延 | 模型占绝对主导 | 减少不必要步骤 |
| 上下文占用 | 召回片段数乘块长 | 与回答质量互相拉扯 | 重排后再截断 |
| 内存 | 载入的文档与向量副本 | 与语料体积同阶 | 落盘索引加流式读取 |

链的长度影响可维护性多于影响性能：真正拖慢系统的是模型调用次数。判断步骤该不该独立成链节点，标准是它的输出是否被复用或需要单独评测；仅仅「逻辑上更清晰」而多付一次模型往返，通常不划算。

检索质量的瓶颈在重排而非召回数量。把 `top_k` 从 4 提到 16 往往只让上下文更拥挤，而加一层重排能明显改善命中率。工程顺序建议是：先调分块，再看是否命中，最后才动模型与提示词。

框架带来的额外开销主要是序列化与对象包装，通常在毫秒级，相对模型调用可忽略。但批处理时的并发默认值可能非常保守，导致明明可以并行的检索被串行化，这类性能损失最容易被误判为模型变慢。

## 常见误区与易错点

- **把组合表达式读成并发或降级。** 它是严格的顺序传值，前一步输出即后一步输入。
- **在查询引擎里硬塞自定义检索逻辑。** 需要中间控制时应当改用检索器自编排。
- **认为只有链才是可组合组件。** 模型、解析器、检索器同样实现统一协议。
- **把提示词写死在业务函数里。** 换模型或改话术时要满仓库搜索。
- **用内存向量库上生产。** 进程重启索引即丢，必须换成可持久化后端。
- **升级只看导入报错。** 消息角色与模板序列化方式的变更不报错，只会静默降质。
- **一味加大召回数量。** 上下文拥挤会稀释关键段落，答案质量反而下降。
- **不校验解析器输出。** 解析成功只说明形状对，字段合法性仍需断言。
- **一个巨型链包揽全部逻辑。** 中间态不可见，出问题时无法定位环节。
- **忽略默认参数变更。** 最大输出长度与温度常随版本调整，需在配置中显式固定。
- **把执行器当黑盒。** 不加回调与终止条件时，工具循环同样会失控。

## 自测题与参考答案

**教材衔接：题号 1** — LCEL 表达式用竖线把两个链写在一起，它的实际语义是？

**参考答案**：前一个链的输出作为后一个的输入。

本题正确项是「前一个链的输出作为后一个的输入」。竖线把两个 Runnable 组成有向管道，前一步的返回值按输入模式传给后一步，同时继承流式和批量接口，是组合而非并发。并发取早属于 racing 语义，写日志与管道无关，失败降级需要显式的兜底包装，把组合子当成容错原语是迁移中最常见的误解。

**教材衔接：题号 2** — LlamaIndex 里 QueryEngine 与 Retriever 的分工是？

**参考答案**：前者组织提问到回答的完整链路。

本题正确项是「前者组织提问到回答的完整链路」。QueryEngine 把检索、重排、合成回复和响应模式串成一个可调用对象，是对外入口；Retriever 只完成从索引取节点这一步，可被嵌进引擎也能单独复用。分块与嵌入属于摄取阶段组件，和这两个抽象不在同一层。

**教材衔接：题号 3** — 升级框架大版本后提示词模板莫名失效，最该先排查的是？

**参考答案**：消息角色与序列化模板方式的变更。

本题正确项是「消息角色与序列化模板方式的变更」。版本升级常改动 System 与工具消息的拼接格式、角色顺序和特殊标记，模板内容没变但落到模型眼中的结构已经不同，因此失效集中在模板层。机房地址影响连通性，索引算法影响召回性能，前端组件只影响展示，都不会让提示词语义消失。

**教材衔接：题号 4** — 想让 RAG 组件可插拔，最符合框架设计意图的写法是？

**参考答案**：把检索器与模型作为参数注入链。

本题正确项是「把检索器与模型作为参数注入链」。框架的 Runnable 抽象要求组件只依赖传入的接口，检索器、语言模型和序列化器都可替换，测试时注入假对象即可断言中间输出。硬编码和复制粘贴把依赖焊死在实现里，全局缓存会让并发请求互相污染，三者都使升级和灰度实验变得不可能。

**教材衔接：题号 5** — 下面这条用竖线串起来的链，invoke 打印的结果是？
from langchain_core.runnables import RunnableLambda
upper = RunnableLambda(lambda s: s.upper())
exclaim = RunnableLambda(lambda s: s + '!')
chain = upper | exclaim
print(chain.invoke('rag'))

**参考答案**：字符串 RAG 加感叹号。

本题正确项是「字符串 RAG 加感叹号」。管道按左到右执行，先由第一个 RunnableLambda 把 rag 转成大写，再把结果交给第二个函数追加感叹号，最终得到大写加感叹号。忘了先转大写会得到小写形式，以为追加发生在转换之前会漏掉感叹号，而 Runnable 原生支持竖线组合，不会因串联报错。

## 考点精讲

**教材衔接：高频考点**

1. 组合表达式的顺序传值语义，以及每一步的输入输出形状。
2. 检索器与查询引擎的职责边界，什么场景必须自己编排。
3. 大版本升级后静默降质的三级排查顺序。
4. 可插拔的实现方式：组件作为参数注入而非内部构造。

**教材衔接：命题规律**

- 常给一条两到三步的小链问输出，考察是否真的按顺序传值。
- 抽象辨析题偏爱把「只返回片段」与「返回完整回答」混为同一能力。
- 迁移类题目以「提示词莫名失效」为现象，正确项指向协议或模板层面。

答：把检索器与模型作为参数注入链。

问：下面这条用竖线串起来的链，invoke 打印的结果是？
from langchain_core.runnables import RunnableLambda
upper = RunnableLambda(lambda s: s.upper())
exclaim = RunnableLambda(lambda s: s + '!')
chain = upper | exclaim
print(chain.invoke('rag'))
答：字符串 RAG 加感叹号。
