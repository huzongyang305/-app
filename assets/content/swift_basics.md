### 声明就决定了可变性

`let nickname = "ada"` 之后不能再写 `nickname = "bob"`，这不是约定而是编译期强制。选 let 还是 var 的判断依据只有一条：这个绑定在后面会不会被换成另一个值。集合类型容易让人误会——`var list = [1,2]` 和 `let list = [1,2]` 都能 `append`，因为 let 约束的是「绑定」，不是「内容」。想连内容一起锁住，靠的是把属性设计成不可变、或提供只读访问接口，而不是在 let 上做文章。

### 可选值的四条安全出路

`String?` 不是一个「可能为空的字符串」，它是另一种类型：要么装着 String，要么是 nil。编译器不允许你直接把 `String?` 当 `String` 用，必须先把这层剥掉，本课示例里的 `nickname?.uppercased() ?? "none"` 就同时用了两条路：

1. **可选链 `?.`**：左边是 nil 时整段表达式短路，结果仍是 nil，不会崩。
2. **空合运算符 `??`**：左边为 nil 时取右边默认值，于是 `print` 拿到的保证是 `String`。
3. **if let 绑定**：`if let name = nickname { 这里 name 是 String }`，分支外又回到可选世界，作用域清楚。
4. **guard let 提前退出**：适合「没有它就别往下走」的场景，解包结果在整个函数剩余部分可用。

而 `nickname!` 是把上面四条全跳过，直接向运行时赌一把：赌输了就是 `Fatal error: unexpectedly found nil while unwrapping an Optional value`，线上表现为闪退且日志里只剩一行。`String!`（隐式解包）只在「确定会在赋值之后才被使用」的极少数场景（例如接口连接前的 IBOutlet）勉强合理，从网络或文件解码出来的数据一个都不该用。

### 值类型与引用类型的分界

`struct` 是值类型：赋值、传参、从数组里取出，得到的都是一份独立副本，改动不会回声到原处。`class` 是引用类型：变量存的是同一个实例的引用，一边改另一边就能看到。判断该用哪个的标准不是「性能」，而是身份——需要「这两个东西是同一个对象」这种语义（共享状态、有生命周期、要比较指针身份）才用 class，其余优先 struct 加协议组合。

Array、Dictionary 的写法同样是值语义，但底层做了写时复制（Copy-on-Write）：赋值时只增加引用计数，真正要修改时才把缓冲区复制一份。所以「传一个数组会不会拷贝十万个元素」的答案取决于有没有人写它，而 `isKnownUniquelyReferenced` 之类的优化在跨线程共享同一份可变数据时并不会救你——那时缺的是同步，不是复制。

### 错误是值，不是异常栈

Swift 的 `throws` 把失败当成类型系统的一部分：函数签名里写了 `throws`，调用方就必须显式处理，编译器不给过。配合 `enum ... : Error` 定义具体错误种类，`do-catch` 里按类型分支处理，`try?` 降级成可选值（丢掉原因），`try!` 断言不会失败（失败即崩溃），后两者是逃生口而非常路。

这里最容易混的是「用 nil 表示失败」：`func find(id: Int) -> User?` 无法区分「这个 id 不存在」和「数据库查询炸了」，界面只能显示空白。正确的拆法是返回值只表达数据存在与否，环境层面的失败用 `throws` 抛出，两者不要共用一条通道。金额、库存这类要累加的量另有一条规则：用 `Decimal` 或以最小单位计的 `Int`，别用 `Double`，因为 0.1 在二进制浮点里根本无法精确表示，误差会随加法累积。

### 三个会反复遇到的写法

**表单提交前的必填校验**：十几个字段都是可选值时，逐个 `if let` 会把逻辑裹成洋葱。Swift 的写法是一串 `guard let`：任何一项取不到就 `return`，函数体后半段从头到尾都在非可选的命名值上操作，读起来是「先排除，再干活」。

**解码远端 JSON**：`JSONDecoder().decode(User.self, from: data)` 是 `throws` 调用，字段缺失、类型不符、数据为空都会走抛错路径。把模型属性写成可选值能让解码宽松一些，但代价是所有下游都要处理 nil；更常见的取舍是模型保持非可选、错误在 `catch` 里按种类翻译成用户能看懂的提示，而不是用 `try?` 换回一个 nil 然后什么都不做。

**列表里的一行更新**：`struct Row` 放进数组后，改动某一行的下标访问会触发写时复制；把 `Row` 换成 `class` 看似省了复制，实则让「同一行数据被两处同时改」成为可能。要共享就明确共享边界（谁拥有、谁只读），不要为了省一次复制换掉语义。

### 第二步：把可选值变成必走的关口

上面的示例只有一层可选，实际项目里通常是一个「有就对，没有就走人」的判断。`guard let` 的写法让函数后半段只看到非可选值：

```swift
func greeting(_ raw: String?) -> String {
    guard let name = raw, !name.isEmpty else { return "访客" }
    return "你好，" + name.uppercased()
}

print(greeting("ada"))   // 你好，ADA
print(greeting(nil))     // 访客
print(greeting(""))      // 访客
```

三行调用正好覆盖三条路径：有值、压根没有值、有值但内容为空。把这三条跑齐，比写一句「看起来能编译」更有说服力。

### 完整示例：值语义与 throws 同时登场

金额一律用最小单位「分」记录，失败用 `throws` 上报，`struct` 保证每次传递都是独立副本。

```swift
enum CartError: Error {
    case invalidArgument
    case exceedsLimit(Int)
}

struct Cart {                              // 值类型：复制出去就是独立的一份
    private(set) var cents: Int = 0

    mutating func add(unitCents: Int, quantity: Int) throws {
        guard unitCents > 0, quantity > 0 else { throw CartError.invalidArgument }
        let added = unitCents * quantity
        guard cents + added <= 100_000 else { throw CartError.exceedsLimit(100_000) }
        cents += added                     // mutating：只有值类型才需要标这一步
    }
}

var cart = Cart()
let snapshot = cart                        // 此刻复制，之后互不影响
do {
    try cart.add(unitCents: 2000, quantity: 3)
    print("合计 \(cart.cents) 分，快照 \(snapshot.cents) 分")
    try cart.add(unitCents: 0, quantity: 1)
} catch CartError.invalidArgument {
    print("价格或数量非法")
} catch CartError.exceedsLimit(let limit) {
    print("超出上限 \(limit)")
} catch {
    print("未预期错误 \(error)")
}
```

```text
合计 6000 分，快照 0 分
价格或数量非法
```

注意 `snapshot` 一直是 0：如果 `Cart` 是 `class`，这里打印的就会是 6000，两处引用同一个对象。这个差别是值类型与引用类型最直观的分工，也是「修改后的行为与预期不符」这条易错点的常见来源。

### 练习

给 `add` 补一条边界数据 `unitCents: 1, quantity: 100_000`，先猜它命中哪个 catch 分支再运行验证。然后把 `guard` 换成 `if` 并删掉提前退出，看编译器在哪一行拒绝你——这条报错正是 Swift 用类型系统逼你处理失败的方式。

### 三项容易被忽略的开销

**引用计数的增减**：class 实例每多一处持有，就多一次 retain/release。把频繁创建的小对象从 class 换成 struct，省掉的不只是堆分配，还有这两次跨模块调用；反过来，把本该共享身份的对象写成 struct，会让「改了但别处没生效」变成要靠调试才能发现的问题。

**写时复制的那一次真复制**：`let copy = bigArray` 几乎免费，但 `copy[0] = 1` 会立刻触发整块缓冲区复制。在循环里反复「取出来改一下再放回去」，最坏情况会退化成每次 O(n)，表现为算法复杂度没变而耗时线性上涨。

**协议与泛型的派发方式**：通过具体类型直接调用可以内联；通过 `any P` 这样的存在类型调用要查方法表；跨模块的协议扩展默认实现还可能拿不到特化版本。这属于「同一份逻辑换个写法差几倍」的开销，要靠 Instruments 或至少靠前后两版的计时对比来确认，不能凭直觉。

### 编译期与运行期的责任划分

可选类型、`throws` 声明、值语义这些约束都在编译期生效，代价接近零；运行期真正要花钱的是解包后的分支预测、大 struct 的按位复制、以及抛错时的返回值传递。所以「为了性能把 String? 改成 String!」不但省不了多少，还把一次编译期检查换成了一次线上崩溃风险——这类交换在这门语言里基本永远是亏的。

### 现场 1：强制解包可选值

## 与其他知识点的关系

**教材衔接：复习与迁移**

**和 Java 的对照**：Java 用 `Optional<User>` 包装类型来表达「可能没有」，取值时要 `.orElse()` 或 `.ifPresent()`；Swift 把可选性写进类型本身（`User?`），语法层面就禁止你把可选值当非可选值直接用。两者目标一致——把空指针错误从运行期挪到编译期——但 Swift 的约束更早也更硬，代价是到处都要显式解包。

**和 Kotlin 的对照**：Kotlin 的可空类型 `String?`、`?.`、`?:`、`!!` 与 Swift 的可选链、空合运算符、强制解包几乎一一同对应，唯一差别是 Kotlin 的可空性是平台类型可以「逃逸」的，从 Java 接口拿到的值可能带着不确定的可空标记；Swift 没有这个洞。

**和后续 iOS 课程的关系**：`throws` 与可选值是接口设计语言， UIKit 或 SwiftUI 章节里那些「可选的 delegate」「会抛错的 URLSession 调用」都靠本课这两样东西来读；ARC 与循环引用则在讲到 class 与闭包捕获时展开，本课只需要先建立「值类型没有引用计数共享」这个前提。
