## 核心概念定义

| 术语 | 操作性定义 | 常见边界与风险 |
| --- | --- | --- |
| 仓库 | 由 .git 目录保存全部提交历史的项目目录。 | 易错：以为改动落在项目目录里就算存好了；只有提交进 .git 的历史能回退，像游戏存档没存过的那一格被覆盖就找不回来。 |
| 提交（commit） | 一次带说明的历史快照，记录作者、时间与改动内容。 | 提交对象存的是父提交与整棵目录树，一次混入格式化、重构和功能变更，回滚时就会带走不相关内容。 |
| 暂存区 | 用 git add 把改动放进暂存区，再一次性提交，便于挑选改动。 | 易错：不看 `git diff --staged` 就把工作区改动一把提交；工作区、暂存区与 HEAD 三处可以不一致，得小步暂存、按单一目的提交。 |
| 分支 | 指向某次提交的可移动指针，用来隔离并行开发。 | 易错：多件事混在一起，无法回退；正确做法是用分支隔离改动，提交粒度保持小。 |
| 远程仓库 | 托管在服务器上的副本，push 上传、pull 拉取并合并。 | 远程不会自动同步，fetch 只下载对象与引用、push 才上传本地提交；已推送又被他人使用的提交别随意 rebase。 |

## 原理与运行机制

### 机制总览

**教材衔接：一句话入门**

完成初始化、提交、分支和远程同步。

**教材衔接：Git 的三个区域与一次提交**

Git 的核心模型是三个区域：工作区保存你正在编辑的文件，暂存区保存下一次提交的快照，本地仓库保存已经提交的历史。`git add` 把工作区变化放入暂存区，`git commit` 把暂存区内容写成一个新的提交对象。提交对象包含作者、时间、提交说明、父提交以及一棵完整的目录树，因此历史不是“文件差异的列表”，而是一串可以追溯和回放的状态快照。

`HEAD` 通常指向当前分支的最新提交，分支本质上只是一个可移动的提交指针。工作区、暂存区和 HEAD 三者不一致时，`git status` 会告诉你每个文件处于什么状态。修改文件后先看差异，再决定暂存哪些改动；`git diff` 看工作区与暂存区，`git diff --staged` 看暂存区与 HEAD。养成“小步暂存、单一目的提交”的习惯，比事后写一篇很长的提交说明更能保证历史清晰。

提交说明应说明“为什么做这个改动”，而不是重复文件名。一个好的提交可以独立回滚，也能让 reviewer 快速判断影响范围。如果一次提交同时包含格式化、重构和功能变更，回滚时就会被迫带走不相关的内容，这是最常见的历史污染。

**教材衔接：分支、合并与远程同步**

分支让你在不影响主线的情况下开发。创建分支只是新建一个指针，成本很低；真正需要处理的是合并时的差异。`merge` 会保留两条分支的历史并生成合并提交，`rebase` 则把你的提交重新放到目标分支之后，历史更线性但会改写提交 ID。已经推送并被他人使用的提交不要随意 rebase，否则会给协作者制造冲突。

远程仓库不是自动同步的。`fetch` 只把远程对象和引用下载到本地，`pull` 通常等于 fetch 后再 merge 或 rebase，`push` 才把本地提交上传。遇到冲突时，Git 会标记冲突文件，需要手动选择保留哪些内容，再 `git add` 并继续操作。冲突不是错误，而是两个分支对同一区域做了不同修改，解决时要同时理解两边的意图。

撤销操作要先判断影响范围：`git restore` 恢复工作区文件，`git revert` 创建一个反向提交，适合已经共享的历史；`git reset` 移动分支指针，可能改变暂存区或工作区，因此要格外谨慎。验证 Git 操作是否成功，不要只看命令退出码，还要用 `git status`、`git log --oneline --graph` 和差异命令确认最终状态。

### 三个区域之间怎么流动

想象你在写毕业论文：工作区是桌上摊开的草稿，暂存区是挑出来准备装订的那一叠，仓库区是交给档案室的存档。命令只负责在三层之间搬动改动：

```text
工作区   你正在编辑的 README.md
   |  git add README.md          挑进下一次要提交的篮子
   v
暂存区   下一次提交的快照
   |  git commit -m "docs: 添加说明"  盖章存档，HEAD 前移一格
   v
仓库区   只读的历史，git log 列出来的就是它
```

commit 像游戏存档：存过的那一格随时能回去，没存档的改动被覆盖就找不回来。分支用的是同一张图：`git switch -c note` 只是新挂一根指针，`git merge note` 把 `main` 挪到包含 note 改动的那一格，旧存档一行也没被改写。

### 选择与边界

- 使用 `仓库` 时，由 .git 目录保存全部提交历史的项目目录；隔离级别与并发事务会影响可见性，换级别或换存储引擎后要重新验证。
- 使用 `提交（commit）` 时，一次带说明的历史快照，记录作者、时间与改动内容。
- 使用 `暂存区` 时，用 git add 把改动放进暂存区，再一次性提交，便于挑选改动；隔离级别与并发事务会影响可见性，换级别或换存储引擎后要重新验证。
- 使用 `分支` 时，指向某次提交的可移动指针，用来隔离并行开发；易错：多件事混在一起，无法回退；正确做法是用分支隔离改动，提交粒度保持小。
- 使用 `远程仓库` 时，托管在服务器上的副本，push 上传、pull 拉取并合并。

git add note.md                      # 5 搬进暂存区，状态变成 A  note.md

### 考点 7：`仓库`

- **要点**：由 .git 目录保存全部提交历史的项目目录。
- **仓库 的边界**：隔离级别与并发事务会影响可见性，换级别或换存储引擎后要重新验证。

### 考点 8：`提交（commit）`

- **要点**：一次带说明的历史快照，记录作者、时间与改动内容。

### 考点 9：`暂存区`

- **要点**：用 git add 把改动放进暂存区，再一次性提交，便于挑选改动。
- **暂存区 的边界**：隔离级别与并发事务会影响可见性，换级别或换存储引擎后要重新验证。

### 考点 10：`分支`

- **要点**：指向某次提交的可移动指针，用来隔离并行开发。
- **分支 的边界**：易错：多件事混在一起，无法回退；正确做法是用分支隔离改动，提交粒度保持小。

### 考点 11：`远程仓库`

- **要点**：托管在服务器上的副本，push 上传、pull 拉取并合并。

### 考点 12：排错——直接在主干上改

- **现象**：多件事混在一起，无法回退。
- **处理**：用分支隔离改动，提交粒度保持小。

### 考点 13：排错——提交信息写得太笼统

- **现象**：历史无法回溯问题来源。
- **处理**：写清改动目的与影响范围。

### 考点 14：综合辨析——`仓库` 与 `远程仓库`

- **辨析点**：`仓库` 的定义是 由 .git 目录保存全部提交历史的项目目录；`远程仓库` 的定义是 托管在服务器上的副本，push 上传、pull 拉取并合并。
- **答题要求**：面对 `Git 入门` 的题目，先判断描述的是 `仓库` 还是 `远程仓库`，再归到对应定义，最后写出一个会让该定义失效的边界输入。

### 考点 15：排错评分点

- **现象分**：能写出 多件事混在一起，无法回退，而不是只写“程序有错”。
- **证据分**：保留触发 直接在主干上改 的输入、版本和错误原文。
- **修复分**：按 用分支隔离改动，提交粒度保持小 只改一处，并同时回归正常路径与边界路径。
