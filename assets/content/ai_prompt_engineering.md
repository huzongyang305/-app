### 从概念到验证的学习链条

1. `提示词`：先掌握 交给模型的指令、上下文和示例组合，用来约束任务目标与输出格式，再用它解释 `few-shot` 为什么会出现。

3. `思维链`：先掌握 开始前先复习：提示词、few-shot、思维链，再用它解释 `结构化输出` 为什么会出现。

## 原理与运行机制

### 机制总览

**教材衔接：常用技巧**

| 技巧 | 说明 |
| --- | --- |
| 少样本（Few-shot） | 给 1~3 个输入输出示例，让格式与风格稳定 |
| 思维链（CoT） | 要求「先分析再结论」，提升推理类任务准确率 |
| 角色设定 | 「你是……」，影响用词与专业深度 |
| 结构化输出 | 指定 JSON / Markdown 模板，便于程序解析 |
| 分步执行 | 复杂任务拆成多个提示，逐步收敛 |
| 反问澄清 | 信息不足时让模型先提问，避免瞎猜 |

**教材衔接：少样本与结构化输出**

```python
prompt = f"""把用户评论分类为 positive / negative / neutral。
示例：
评论：物流很快，包装完好 -> {{"label": "positive"}}
评论：三天没发货 -> {{"label": "negative"}}
评论：快递一般 -> {{"label": "neutral"}}
现在分类：
评论：{user_comment}
只输出 JSON，不要解释。"""
```

**教材衔接：提示词版本管理**

| 做法 | 说明 |
| --- | --- |
| 提示词入库 | 与代码同仓库、同评审，变更可追溯 |
| 变量化 | 把动态部分抽为 `{question}`、`{context}`，避免拼接混乱 |
| 回归用例 | 每个提示词配 10~30 条固定输入与期望，改动后重跑 |
| 版本对比 | 新旧提示在同一批用例上对比胜率，而非凭感觉 |

**教材衔接：结构化输出与工具调用的选择**

| 需求 | 推荐方式 | 理由 |
| --- | --- | --- |
| 让模型返回固定字段的 JSON | 结构化输出（JSON Schema / json_object） | 模型只需生成数据，无需执行动作 |
| 让模型查询实时数据或触发操作 | 工具调用（Function Calling） | 由你的代码执行并回传结果，安全可控 |
| 既取数据又要结构化结果 | 两者组合：工具取数 → 模型按 schema 输出 | 职责分离，便于校验与重试 |

工具定义的三要素：**清晰的 name**（动词+名词）、**description 写清何时用与不用的边界**、**parameters 给出类型/必填/枚举**。描述写得含糊，模型就会选错工具或编造参数。

组合流程的标准骨架：模型请求调用工具 → 代码校验参数并按白名单执行 → 把结果作为消息回传 → 模型基于真实数据按 schema 生成最终 JSON → 代码校验字段与取值 → 失败则带错误信息重试一次（不要无限重试）。

常见坑：把工具描述写成实现细节（模型看不懂用途）；参数没有枚举约束导致传入非法值；把大段工具原始返回塞回上下文（应裁剪只留必要字段）；未做超时与失败兜底。

**教材衔接：提示词结构速查**

| 组成部分 | 作用 | 示例 |
| --- | --- | --- |
| 角色 | 限定专业视角 | 「你是一名资深后端工程师」 |
| 任务 | 明确要做什么 | 「审查下面的 SQL 并指出性能问题」 |
| 上下文 | 提供必要背景 | 表结构、数据量、数据库版本 |
| 约束 | 边界与禁止项 | 「不要编造字段名；不确定就说不确定」 |
| 输出格式 | 便于程序解析 | 「输出 JSON，字段为 risk/level/fix」 |
| 示例 | 对齐风格（Few-shot） | 给出 1~3 个输入输出样例 |
| 自检 | 提升可靠性 | 「回答前先核对是否满足全部约束」 |

**教材衔接：输出与解析速查**

| 需求 | 推荐做法 |
| --- | --- |
| 稳定 JSON | 明确字段与类型、提供示例、开启结构化输出（如 JSON Schema 模式） |
| 字段缺失兜底 | 解析失败时重试一次并把错误信息回传给模型 |
| 长度控制 | 明确「不超过 200 字」，并在解析端截断 |
| 引用来源 | 要求给出原文片段与文档编号，便于人工核对 |
| 多语言 | 明确目标语言与术语表，避免混用 |

### 五、AI 工程补充

在提示工程里，模型输出只是系统的一部分：输入要先经过权限与数据质量检查，检索或工具调用要有超时和降级，输出要经过引用核验或规则校验，最后记录 token、延迟、失败类型和人工反馈。评测时至少准备固定题、边界题和对抗题，并把 提示词 与 few-shot 的指标分开记录；否则一次提示词改动看似提升体验，实际可能只是评测样本泄漏或随机波动。

### 机制拆解：每一步的输入、动作与输出

#### 1. `提示词`
- 输入：`提示词`；本步把 交给模型的指令、上下文和示例组合，用来约束任务目标与输出格式 当作判断规则。
- 动作：围绕 `提示词` 保留中间状态，并记录它与 `few-shot` 的对应关系。
- 输出：`few-shot`，它可以被下一段代码、测试或记录继续使用。
- `提示词` 的失败条件：结果依赖数据分布、模型版本与算力预算，换数据集或换硬件都要重新评估。

#### 2. `few-shot`
- 输入：`提示词`；本步把 在提示词中给出少量输入输出示例，让模型模仿任务格式和判断标准 当作判断规则。
- 动作：围绕 `few-shot` 保留中间状态，并记录它与 `思维链` 的对应关系。
- 输出：`思维链`，它可以被下一段代码、测试或记录继续使用。
- `few-shot` 的失败条件：结果依赖数据分布、模型版本与算力预算，换数据集或换硬件都要重新评估。

#### 3. `思维链`
- 输入：`few-shot`；本步把 开始前先复习：提示词、few-shot、思维链 当作判断规则。
- 动作：围绕 `思维链` 保留中间状态，并记录它与 `结构化输出` 的对应关系。
- 输出：`结构化输出`，它可以被下一段代码、测试或记录继续使用。
- `思维链` 的失败条件：只在「开始前先复习：提示词、few-shot、思维链」这一前提下成立，换输入或换环境要重新验证。

#### 4. `结构化输出`
- 输入：`思维链`；本步把 约束模型按 JSON、枚举或模式返回可直接解析的数据 当作判断规则。
- 动作：围绕 `结构化输出` 保留中间状态，并记录它与 `工具调用` 的对应关系。
- 输出：`工具调用`，它可以被下一段代码、测试或记录继续使用。
- `结构化输出` 的失败条件：结果依赖数据分布、模型版本与算力预算，换数据集或换硬件都要重新评估。

#### 5. `工具调用`
- 输入：`结构化输出`；本步把 模型按结构化参数请求外部函数或服务，并把结果带回后续推理 当作判断规则。
- 动作：围绕 `工具调用` 保留中间状态，并记录它与 `label` 的对应关系。
- 输出：`label`，它可以被下一段代码、测试或记录继续使用。
- `工具调用` 的失败条件：网络延迟、超时与版本协商会改变行为，只在真实链路或多版本客户端上验证才算数。

## 典型应用场景

- **一次塞进多个互不相关的任务**：典型现象是输出混乱、遗漏；正确做法是拆成多次调用或明确分步。
- **只写「写得详细一点」**：典型现象是结果随机、不可复现；正确做法是给出具体长度、结构与验收标准。
- **让模型输出 JSON 但不校验**：典型现象是线上解析失败；正确做法是用 Schema 校验，失败时重试或降级。

### 最小验证场景

- 准备：保留 `python` 示例的原始输入，先记录 `提示工程` 的基线输出和完整运行命令。
- 观察：先核对 出现字面量 `label`，再改变一个与 `提示词` 相关的条件。
- 判定：新结果与 `提示工程` 的基线不同不等于错误；只有当差异破坏了 `提示词` 的定义或错误表中的约束，才判定为失败。

### 选择与边界

- 使用 `提示词` 时，先满足它的定义：交给模型的指令、上下文和示例组合，用来约束任务目标与输出格式；结果依赖数据分布、模型版本与算力预算，换数据集或换硬件都要重新评估。
- 使用 `few-shot` 时，先满足它的定义：在提示词中给出少量输入输出示例，让模型模仿任务格式和判断标准；结果依赖数据分布、模型版本与算力预算，换数据集或换硬件都要重新评估。
- 使用 `思维链` 时，先满足它的定义：开始前先复习：提示词、few-shot、思维链；只在「开始前先复习：提示词、few-shot、思维链」这一前提下成立，换输入或换环境要重新验证。
- 使用 `结构化输出` 时，先满足它的定义：约束模型按 JSON、枚举或模式返回可直接解析的数据；结果依赖数据分布、模型版本与算力预算，换数据集或换硬件都要重新评估。

## 代码/协议/SQL 示例

**教材衔接：核心原则**

好提示 = **清晰的任务 + 必要的上下文 + 明确的输出格式 + 约束条件**。

```text
角色：你是一名资深代码评审员
任务：审查下面的 Python 函数，找出 bug 与性能问题
输入：<代码>
约束：只指出确定存在的问题，不要臆测；每条给出修改建议
输出格式：JSON 数组，字段为 line / issue / suggestion / severity
```

**教材衔接：思维链的正确用法**

对推理、计算、多步判断类任务，要求模型显式写出中间步骤通常更准：

```text
请先逐步分析（步骤用 1. 2. 3. 编号），最后用一行「结论：」给出答案。
```

注意：面向用户的最终回复不必展示全部推理过程，可以只保留结论与关键依据。

**教材衔接：迭代与评测**

```text
写提示 -> 用一批真实样例测试 -> 记录失败案例
      -> 定位是缺上下文、指令冲突还是格式不清 -> 修改 -> 回归测试
```

把提示当作代码管理：放进版本控制、写清变更原因、保留测试用例集。改动提示后必须跑一遍回归，否则很容易「修好一个、弄坏三个」。

**教材衔接：少样本与结构化输出的可运行示例**

```python
import json
from openai import OpenAI

client = OpenAI()

SYSTEM = "你是电商评论分类器。只输出 JSON，不要任何解释。"

EXAMPLES = [
    {"role": "user", "content": "物流很快，包装完好"},
    {"role": "assistant", "content": '{"label":"positive","confidence":0.95}'},
    {"role": "user", "content": "三天没发货"},
    {"role": "assistant", "content": '{"label":"negative","confidence":0.9}'},
]

def classify(comment: str) -> dict:
    response = client.chat.completions.create(
        model="gpt-4o-mini",
        temperature=0,                     # 分类任务要确定性
        response_format={"type": "json_object"},   # 强制 JSON 输出
        messages=[{"role": "system", "content": SYSTEM}, *EXAMPLES,
                  {"role": "user", "content": comment}],
    )
    data = json.loads(response.choices[0].message.content)
    # 校验：字段与取值必须符合约定，否则走兜底逻辑
    assert data["label"] in {"positive", "negative", "neutral"}
    assert 0 <= float(data["confidence"]) <= 1
    return data
```

三个关键点：**给 2~3 个示例稳定格式**、**temperature 设 0 保证确定性**、**拿到结果后仍要校验**（模型可能返回越界取值）。生产环境把校验失败记为指标并告警，而不是静默使用。

**教材衔接：常用技巧速查**

| 技巧 | 适用场景 | 注意点 |
| --- | --- | --- |
| 零样本 | 简单任务 | 直接描述需求即可 |
| 少样本（Few-shot） | 需要固定风格或格式 | 示例要覆盖边界情况 |
| 思维链（CoT） | 多步推理、计算 | 增加 Token 成本，敏感场景不要让模型暴露推理细节 |
| 分步执行 | 复杂任务 | 先规划再执行，便于人工检查中间结果 |
| 角色扮演 | 需要特定视角 | 角色不能替代事实依据 |
| 结构化输出 | 需要程序消费 | 指定 JSON Schema，并做运行时校验 |
| 自一致性 | 需要高准确率 | 多次采样取多数，成本成倍增加 |

- **思维链 的边界**：只在「开始前先复习：提示词、few-shot、思维链」这一前提下成立，换输入或换环境要重新验证。

### 考点 10：`结构化输出`

- **要点**：约束模型按 JSON、枚举或模式返回可直接解析的数据。
- **结构化输出 的边界**：结果依赖数据分布、模型版本与算力预算，换数据集或换硬件都要重新评估。

### 考点 11：`工具调用`

- **要点**：模型按结构化参数请求外部函数或服务，并把结果带回后续推理
- **工具调用 的边界**：网络延迟、超时与版本协商会改变行为，只在真实链路或多版本客户端上验证才算数。

### 考点 12：排错——一次塞进多个互不相关的任务

- **现象**：输出混乱、遗漏。
- **处理**：拆成多次调用或明确分步。

### 考点 13：排错——只写「写得详细一点」

- **现象**：结果随机、不可复现。
- **处理**：给出具体长度、结构与验收标准。

### 考点 14：综合辨析——`提示词` 与 `工具调用`

- **辨析点**：`提示词` 的定义是 交给模型的指令、上下文和示例组合，用来约束任务目标与输出格式；`工具调用` 的定义是 模型按结构化参数请求外部函数或服务，并把结果带回后续推理。
- **答题要求**：面对 `提示工程` 的题目，先判断描述的是 `提示词` 还是 `工具调用`，再归到对应定义，最后写出一个会让该定义失效的边界输入。

### 考点 15：排错评分点

- **现象分**：能写出 输出混乱、遗漏，而不是只写“程序有错”。
- **证据分**：保留触发 一次塞进多个互不相关的任务 的输入、版本和错误原文。
- **修复分**：按 拆成多次调用或明确分步 只改一处，并同时回归正常路径与边界路径。
