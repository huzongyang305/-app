## 核心概念定义

| 术语 | 操作性定义 | 常见边界与风险 |
| --- | --- | --- |
| Kotlin | 运行于 JVM 等平台、强调空安全与简洁语法的现代编程语言。 | 权限与密钥策略变化会让结论失效，按最小权限并用真实凭据流程复验。 |
| 空安全 | 类型系统区分可空与非空值，并在编译期要求显式处理空值。 | 静态检查只在编译期成立，运行期输入仍需校验。 |
| val | Kotlin 中声明只读引用的关键字，引用一旦赋值不能再指向其他对象。 | 越界、悬垂引用与释放顺序会破坏结论，必须在边界输入下复验。 |
| 类型推断 | 编译器根据初始值推断变量类型（val x = 1 即 Int），显式标注只在需要澄清时使用。 | 静态检查只在编译期成立，运行期输入仍需校验。 |
| `var` | 允许再指向其他对象的可变引用，需要累积状态或就地推进时才用。 | 作用域过大的 `var` 让状态来源难以追踪，读写点一散就不好验证。 |
| 可空类型 | 类型后加 `?`（如 `String?`）表示允许 null；非空类型不接受 null，赋值与传参都在编译期判。 | 反射和部分泛型调用能绕过可空推断，边界处仍要自己判空。 |
| `!!` 非空断言 | 把可空类型强行当非空使用，遇到 null 立刻抛 `NullPointerException`。 | 编译器从此不再提醒，异常出现的位置还可能不是空值的来源。 |

### val 锁的是引用，不是内容

```kotlin
val items = mutableListOf("A")
items.add("B")              // 合法：改的是列表内容
// items = mutableListOf()  // 不合法：val 不能再指向别的对象
```

`val` 保证的是「这个名字不再换对象」，至于对象里面能不能改，取决于它的类型是 `List` 还是 `MutableList`。所以「默认用不可变声明」只解决第一层，真正防住意外修改要靠只读接口与不可变数据：对外发 `List`，内部才留 `MutableList`，或者交出一份 `toList()` 的副本。把 `val` 当成深度不可变，就是「对象被意外修改」这个坑的源头。

### 可空类型在编译期逼你处理的三条路径

`?.` 负责「有就往下走，没有就是 null」，`?:` 负责「null 时换个值」，`?.let { }` 负责「确认非空之后再执行一段代码」，块里的 `it` 是非空版本。三条拼起来就能一行处理缺失数据：`val city = user?.address?.city ?: "未知城市"`。关键不在语法糖，而在 `String?` 与 `String` 是两个不兼容的类型——想把可空值当非空用，编译器当场拒绝，处理方式只能显式写出来。

### 类型推断省的是样板，不是契约

`val year = 1815` 推成 `Int`，`val year = 1815L` 是 `Long`，`val list = listOf("a")` 是 `List<String>`，函数内部这些都不用写。但两处要显式：一是模块对外的函数返回值与类的公开属性，推断结果一旦随实现改动而变化，依赖方就跟着编译失败；二是可空性，`fun find(): User?` 与 `fun find(): User` 对调用方是两种承诺，靠推断出来的类型别人根本看不见。

### 平台类型与 `!!`：崩在运行期的那条缝

调 Java 库拿回的 `String` 既没标 `@Nullable` 也没标 `@NotNull` 时，Kotlin 当它是「平台类型」放行：你按非空用，编译器不拦；一旦那个方法真返回 null，异常出现在使用处而不是赋值处，中间可能已经穿过好几层。修法是在边界把可空性写死，例如 `fun load(name: String): User? = javaDao.find(name)`，或给 Java 侧补注解。`!!` 是同一类问题的另一种写法，它把「以后再说」变成「现在就炸」：断言抛出的异常只给你堆栈，而 `?: error("缺少 userId")` 会直接告诉你少了什么，所以断言只留给逻辑上确定非空、且能举出反例证明的位置。

### 场景：表单里的 null 与空白是两件事

字段可能没填（null），也可能填了一串空格，两者不是一回事：可空类型管「有没有」，`isBlank()` 管「有没有内容」。处理顺序是先判缺失再判空白——`val name = raw?.trim() ?: return "请先填写姓名"`，接着 `if (name.isEmpty()) return "姓名不能是空白"`。正常输入、空白输入、缺失输入三条路径都要各跑一次；只测「你好，Ada」那条，等于失败分支从没被说明过。

### 场景：把 Java 服务返回的资料拼成展示文案

`user?.address?.city ?: "未知城市"` 一次到位：链子上任何一环是 null，结果就落到默认值，不会出现「检查了 address 却忘了 user」这种遗漏。这就是把非空断言换成安全调用后的主要收益——链子变长也不必手写层层 if，而编译期仍然要求你对最终的可空结果做一次交代。

### 完整示例：val/var、类型推断与可空处理放在一起

```kotlin
fun parseAge(raw: String?): Int? {
    val trimmed = raw?.trim() ?: return null
    if (trimmed.isEmpty()) return null
    return trimmed.toIntOrNull()        // 转不了就是 null，而不是抛异常
}

fun main() {
    val inputs = listOf("1815", " 19 ", null, "", "abc")
    var ok = 0
    for (item in inputs) {
        val age: Int? = parseAge(item)
        println(age?.let { "年龄 $it" } ?: "无法解析：$item")
        if (age != null) ok++
    }
    println("成功 $ok / ${inputs.size}")
}
```

`val age: Int?` 显式写出可空类型，因为它的值要分岔进 `let` 与 `?:`；`toIntOrNull()` 是「失败不炸」的转换，比 `toInt()` 少一条异常路径；`ok` 用 `var` 是因为它确实要在循环里累加，其余全是 `val`。预期输出五行：前两行给出 1815 与 19，中间两行分别是「无法解析：null」和「无法解析：」，最后一行是「成功 2 / 5」。

### 练习：把安全调用换成断言再复现一次

把 `parseAge` 里的 `?: return null` 改成 `raw!!.trim()`，喂进那条 `null` 输入，记下异常出现的行号——它指向断言那一行，而不是数据真正缺失的地方。这个差别就是排错成本，也是错误表第一条「运行期空指针异常」的由来。
