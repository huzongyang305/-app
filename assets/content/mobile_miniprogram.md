## 核心概念定义

先快速认识几个关键术语，后面会反复提到它们：

| 术语 | 一句话说明 |
| --- | --- |
| 小程序 | 运行在微信等宿主 App 里的轻量应用，用 WXML + WXSS + JS/TS 编写，没有浏览器 DOM 环境 |
| setData | 小程序把数据从逻辑层同步到视图层的接口，应合并调用、只传变化字段，避免频繁跨层通信 |
| 分包 | 把非首屏页面拆到子包里按需下载，用来控制主包体积以通过平台限制 |
| 渲染层 | 小程序把视图渲染放在独立线程，逻辑层通过 setData 把数据同步过去 |
| 逻辑层 | 运行 JavaScript 的地方（iOS 上是 JSCore，Android 上是 V8），负责处理业务逻辑 |
| rpx | 小程序专用的响应式尺寸单位，会根据屏幕宽度自动适配，750rpx 永远等于屏幕宽度 |
| 主包 | app.json 的 pages 与启动即需要的代码资源所在包，体积直接决定首屏下载耗时 |
| 预加载 | preloadRule 配置的空闲时段提前下载分包，让用户跳转时子包已经在本地 |
| 数据路径 | setData 里用 "orders[1].title" 这类路径只更新一格，替代整块重传 |

## 原理与运行机制

### 双线程模型

小程序和网页最大的区别在于：小程序没有浏览器环境，它的渲染和逻辑分别跑在两个不同的线程里。

想象一下这样的场景：你开了一家餐厅，前台负责接待客人、展示菜单（渲染层），后厨负责做菜（逻辑层）。前台和后厨之间不能直接对话，必须通过对讲机传递信息——这个对讲机就是 setData。

具体来说：

1. 用户在页面上的操作（点击、滑动）会被渲染层捕获
2. 渲染层把事件发送给逻辑层
3. 逻辑层处理完业务逻辑后，调用 setData 把新数据发回渲染层
4. 渲染层收到数据后更新页面显示

这种设计的好处是：即使 JS 代码跑了一个很耗时的计算，页面也不会卡住，因为它们在不同的线程里。但代价是：每次 setData 都是一次跨线程通信，数据量太大或者调用太频繁，就会造成延迟和卡顿。

### setData 的工作原理

setData 做的事情看起来简单——把数据从逻辑层传到渲染层，但背后有几个关键点：

- 每次调用都会触发一次序列化（把 JS 对象变成可传输的格式）和反序列化
- 数据量越大，传输耗时越长
- 渲染层收到数据后会做 diff 对比，然后更新对应的视图节点

所以用好 setData 的核心原则就是：少传、合并传、只传变化的部分。

### 分包加载机制

微信对小程序的主包大小有限制（目前 2MB），如果所有页面都塞进主包，很快就会超限，而且用户打开小程序时要下载全部内容，首屏就会很慢。

分包的思路很直接：把首屏需要的页面放在主包，其他页面放到不同的子包里。用户打开小程序时只下载主包，访问分包页面时再按需下载对应的子包。

你还可以配置预加载规则：当用户进入某个页面时，在空闲网络下提前下载指定的分包，这样用户真正跳转时就不用等了。

预加载规则写在 app.json 的 `preloadRule` 里，键是「哪个页面触发预载」，值是「网络条件 + 要提前下载的分包名」。合理写法是把预载挂在用户大概率会停留的首页，而不是挂在马上就要跳走的过渡页，否则分包下载还没完成用户已经进页面，只能回退到实时下载。

### 一次点击要跨几次线程

小程序里「点一下按钮」的完整往返比网页长：

1. 渲染层捕获 `tap` 事件，把事件对象序列化后发给逻辑层
2. 逻辑层执行你在 `methods` 或 `Page` 里写的处理函数
3. 处理函数调用 setData，把新的数据再序列化发回渲染层
4. 渲染层做 diff，更新真正变化的那几个节点

这条链路里第 1、3 步各有一次跨线程通信，所以「点一下才更新一次」是免费的，而「手指滑动时每 16ms 调一次 setData」会把通信队列堵住，表现为列表掉帧。这也是页面初始 `data` 不宜放常量大对象的原因：初次渲染同样要走这条通道。

### 为什么没有 DOM，以及拿节点的正规姿势

逻辑层运行在 JSCore（iOS）或 V8（Android）里，那是纯 JS 引擎，没有浏览器提供的 document、window 和整个 DOM 树，写了 `document.getElementById` 就是引用了一个不存在的变量，运行阶段直接报错。要读取或操作节点，用官方的查询接口：在逻辑层通过 `this.createSelectorQuery()` 选择器查询节点的尺寸与位置，需要滚动到某个位置时用页面实例提供的滚动能力，而不是去改 scrollTop 属性。视图的变化一律由数据驱动，你改的是 data，渲染层自己决定改哪几个节点。

### 安全边界放在哪一层

小程序前端代码是可逆的（包体下载后就能被读），所以有三类东西不能出现在前端：签名密钥与 AppSecret、`session_key`、以及任何能直接决定金额或权限的判断逻辑。正规流程是：前端 `wx.login` 拿到临时 code，把 code 传给自家服务端，由服务端去换 openid 与 session_key，会话凭据由服务端签发并保存在服务端侧。加购、领券这类接口也必须在服务端重算价格与库存，前端的展示数字只是提示，不是依据。

## 典型应用场景

小程序适合哪些场景呢？下面列举几个最常见的：

**电商与点餐**：商品列表、购物车、下单支付。这类场景页面多、交互频繁，需要合理使用分包和 setData 优化。

**工具类应用**：扫码、查询、打卡。这类场景注重首屏速度，主包要尽量精简。

**内容展示**：文章列表、详情页、个人中心。长列表场景要注意用虚拟列表或分页加载，避免一次渲染上千条数据。

**企业内部工具**：审批、报表、巡检。这类场景经常需要调用 wx.request 与后端交互，要注意请求域名配置和登录态管理。

不管哪种场景，有几个通用原则要记住：

- 首屏相关的资源放主包，其余分包
- setData 只传必要字段，大列表用分页
- 敏感信息（密钥、session_key）只放服务端
- 图片等大资源放 CDN，不占包体积

### 长列表页的落地做法

订单列表、商品列表这类页面同时踩中「数据量大」和「更新频繁」两个点，做法可以固定成四条：

1. 一次只拉 20 条，触底后再拉下一页，`data` 里永远只留当前已加载的部分
2. 更新某一条时用路径写法 `this.setData({ "orders[3].status": "已发货" })`，别把整个数组重传一遍
3. 列表项状态靠 `wx:key` 绑定后端返回的稳定 id，用 index 当 key 在中间插入数据时会串位
4. 超过几百条就上虚拟列表或 recycle-view，只渲染屏幕内可见的节点

### 一次首屏提速的复盘

有个点餐小程序首屏要 4 秒多，排查顺序是这样走的：先看开发者工具 Audits 里的「包体积」和「首屏渲染」两段耗时，确认瓶颈在下载而不是渲染；再统计主包里有多少页面属于二级入口，把它们移到分包，主包从 1.8MB 降到 700KB；然后把首页一次性 setData 的 200 条推荐菜改成 20 条；最后给「购物车」分包加预加载规则，用户在首页停留时就把它拉下来。改完首屏降到 1.9 秒。这条链路里没有任何一处是「换语法」，全是砍数据量和挪包。

## 代码/协议/SQL 示例

下面是一个典型的小程序列表页，展示了分页加载、防抖触底和错误处理：

```javascript
// pages/list/list.js
Page({
  data: {
    items: [],
    page: 1,
    loading: false,
    hasMore: true
  },

  onLoad() {
    this.loadMore();
  },

  onReachBottom() {
    this.loadMore();
  },

  async loadMore() {
    if (this.data.loading || !this.data.hasMore) return;
    this.setData({ loading: true });
    try {
      const res = await wx.request({
        url: "https://api.example.com/items",
        data: { page: this.data.page, size: 20 }
      });
      const list = res.data.items || [];
      this.setData({
        items: this.data.items.concat(list),
        page: this.data.page + 1,
        hasMore: list.length === 20,
        loading: false
      });
    } catch (error) {
      this.setData({ loading: false });
      wx.showToast({ title: "加载失败", icon: "none" });
    }
  }
});
```

再来看一个页面的结构文件，小程序用 WXML 来描述页面内容（类似 HTML）：

```html
<!-- pages/orders/orders.wxml -->
<view class="page">
  <view wx:if="{{loading}}" class="tip">加载中...</view>
  <view wx:elif="{{error}}" class="tip error">{{error}}</view>
  <view wx:elif="{{orders.length === 0}}" class="tip">暂无订单</view>
  <view wx:else>
    <view
      wx:for="{{orders}}"
      wx:key="id"
      class="card"
      bindtap="onTapOrder"
      data-id="{{item.id}}"
    >
      <text class="title">{{item.title}}</text>
      <text class="amount">¥{{item.amount}}</text>
    </view>
  </view>
</view>
```

页面文件结构长这样：

```text
pages/orders/
  orders.wxml      结构（类似 HTML）
  orders.wxss      样式（类似 CSS）
  orders.js        逻辑（JavaScript）
  orders.json      页面配置
app.json           全局配置（页面注册、分包规则等）
app.js             应用生命周期
```

分包配置写在 app.json 里，大致结构如下：

```text
pages 数组放首屏页面路径
subPackages 数组放各分包的 root 和 pages
preloadRule 对象配置预加载规则，指定在哪个页面空闲时下载哪些分包
```

### 只传变化的字段

小程序支持用数据路径做局部更新，这是把 setData 从「重传整块」降成「传一格」的关键写法：

```javascript
// 列表第 2 项的标题变了：只传这一格，不要重传整个 orders
this.setData({ "orders[1].title": "新标题" });

// 循环里攒够改动再一次提交，避免每项都跨线程一次
const patch = {};
for (const item of changed) {
  patch[`orders[${item.index}].status`] = item.status;
}
this.setData(patch);

// 反例：把 500 条记录整体重传，序列化与 diff 的开销全在这一次
this.setData({ orders: allOrders });
```

setData 的值只能是可序列化的纯数据：函数、undefined、Date 实例传过去会丢失或变形，日期请先格式化成字符串，倒计时这类高频值放渲染层的组件内部处理。

### 分包与预加载的配置写法

```json
{
  "pages": ["pages/index/index", "pages/cart/cart"],
  "subPackages": [
    {
      "root": "packages/order",
      "pages": ["pages/list/list", "pages/detail/detail"]
    },
    {
      "root": "packages/coupon",
      "pages": ["pages/list/list"]
    }
  ],
  "preloadRule": {
    "pages/index/index": {
      "network": "wifi",
      "packages": ["packages/order"]
    }
  }
}
```

`pages` 里只留首屏真要用到的两个页面，其余挪进 `subPackages`；`preloadRule` 表示用户停在首页且连着 wifi 时，提前把订单分包拉下来，等他点进订单列表就不用再等下载。图片、字体这类大文件不进包，改走 CDN，包体积只留代码。

### 用 rpx 做机型适配

```css
/* 750rpx 恒等于屏幕宽度，所以 750rpx 就是通栏 */
.card {
  width: 690rpx;        /* 左右各留 30rpx 边距 */
  margin: 0 30rpx;
  padding: 24rpx;
  border-radius: 16rpx;
}

.card__title {
  font-size: 30rpx;     /* 字号也用 rpx，小屏上会整体缩小 */
}
```

在 375pt 宽的机型上 1rpx 约等于 0.5px，在更宽的机型上自动放大，所以同一份样式在不同机器上的比例关系不会变。需要「不随屏幕缩放」的场景才用 px，典型是 1px 细线边框；正文行高、间距这些走 rpx，两端对齐的布局用 flex 而不是硬算宽度。

## 时间/空间复杂度或性能分析

小程序的性能瓶颈主要集中在三个地方：

**setData 通信开销**：每次 setData 都要把数据从逻辑层序列化后传到渲染层。如果你一次传了一个包含几千条记录的数组，光是序列化就要花不少时间，渲染层收到后做 diff 和更新视图也需要时间。经验法则：单次 setData 的数据量控制在几十 KB 以内，列表超过 100 条就要考虑分页或虚拟列表。

**首屏加载耗时**：主包越大，下载和解压的时间越长。微信对主包大小有限制，即使没超限，主包里有太多非首屏资源也会拖慢启动速度。分包是解决这个问题最直接的手段。

**长列表渲染**：用 wx:for 直接渲染上千个节点会导致滚动卡顿。解决方案是使用 recycle-view 组件或者自己实现虚拟列表，只渲染屏幕可见区域内的元素。

测量性能时，可以用微信开发者工具里的 Audits 面板查看首屏耗时和帧率，也可以在代码里用 Date.now() 或 performance 做打点。关键是固定输入条件反复测量，而不是只看一次的结果。

### setData 的成本怎么估

一次 setData 的耗时大致等于「序列化数据 + 跨线程传输 + 渲染层 diff + 更新节点」四段之和。前三段和传出去的数据体积近似成正比，第四段和实际发生变化的节点数量成正比，所以「传 5KB 改 1 个节点」比「传 200KB 改 1 个节点」便宜得多，而 diff 的代价并不会因为你传了全量就省掉。经验做法是：单次 setData 的 payload 控制在几十 KB 内，同一个事件回调里合并成一次调用，高频更新（滚动、倒计时）交给渲染层的组件或用 animate 接口，别把它接到跨线程通道上。

### 首屏时间由哪几段组成

把「点开小程序到看见内容」拆开看：拉主包（受包体积与网络影响）→ 注入 JS 与初始化基础库 → 首次 setData 渲染 → 首屏数据接口返回。前两段只有分包能压下来，第三段靠精简初始 data，第四段靠接口聚合与缓存。测出来如果下载阶段占比最高，就说明该动包结构；如果数据返回最慢，动 setData 是没用的。这也是「验证 setData 时要固定版本并覆盖边界输入」的实际含义——同一份改动，在弱网、大列表和冷启动三种条件下结论可能完全不同。

## 常见误区与易错点

初学者在小程序开发中最容易犯这些错误：

| 错误 | 现象 | 修法 |
| --- | --- | --- |
| 频繁调用 setData | 界面明显卡顿，滚动掉帧 | 合并多次 setData 为一次，只传变化的字段 |
| 用 document 或 window 操作 DOM | 运行直接报错 | 小程序没有浏览器 DOM 环境，改用官方 API |
| wx:for 忘记写 wx:key | 列表项状态错乱，输入框内容串位 | 给 wx:for 加上稳定唯一的 wx:key 字段 |
| 把密钥写在前端代码里 | 密钥泄露，被恶意调用 | 敏感操作全部放服务端，前端只做展示 |
| 主包塞了太多页面和资源 | 首屏加载慢，甚至超限无法上传 | 用分包拆分，图片等大资源放 CDN |
| 忽略 rpx 和 px 的区别 | 不同机型上界面尺寸错乱 | 布局尺寸统一用 rpx 做自适应 |
| 不处理请求失败的情况 | 网络异常时页面白屏 | 请求加上 catch，页面要有加载、空态、错误、正常四种状态 |
| 用 data-* 传复杂对象 | 序列化后数据丢失或变形 | 只传 id，需要详情时根据 id 去查数据 |
| 在 onPageScroll 里每帧 setData | 通信排队，滚动明显掉帧 | 节流后再更新，或把动画交给渲染层组件自己处理 |
| wx:key 写成 index | 列表中间插入或删除后，输入框内容和勾选状态串到别的行 | 用后端返回的稳定 id 作为 key |
| 初始 data 里放常量大数据 | 首次渲染就背上全量传输，白屏时间变长 | 常量放模块顶层变量，需要时再按需 setData 进视图 |
| 在 setData 里传函数或 Date 对象 | 字段被静默丢弃，页面上对应位置空白 | 只传可序列化的纯数据，日期先格式化成字符串 |
| 把 session_key 或签名密钥写进前端 | 包体被解出后密钥外泄，接口被伪造调用 | 密钥只在服务端持有，前端只拿临时凭据 |

### 出错时的定位顺序

页面表现不对，先按这条顺序缩小范围，而不是直接改代码：

1. 逻辑层有没有拿到数据：把响应打在控制台，确认字段名与类型
2. 数据有没有同步过去：在 setData 回调里读 `this.data`，能读到新值说明跨线程这段没问题
3. 渲染层有没有更新：检查 WXML 里的绑定路径拼写，`{{orders[0].title}}` 少一层就整块不显示
4. 是不是节点复用问题：换一个唯一 id 当 wx:key，看状态错乱是否消失

## 与其他知识点的关系

小程序开发涉及的知识并不是孤立的，它和你已经学过或即将学到的内容都有联系：

**与前端基础的关系**：WXML 类似 HTML，WXSS 类似 CSS，JS 逻辑和前端 JavaScript 基本一致。如果你之前学过 HTML/CSS/JS，上手会很快。但要注意小程序没有 DOM，不能直接操作页面元素。

**与移动端性能优化的关系**：setData 的优化本质上就是跨线程通信的性能优化，分包加载本质上就是按需加载的思想在小程序里的具体应用。这些概念在后续的《移动端性能优化实战》里还会深入展开。

**与网络请求的关系**：小程序的网络请求（wx.request）只能发 HTTPS 请求，而且域名要在小程序后台提前配置白名单。登录流程（wx.login 换 code，服务端换 openid）也比普通网页更复杂，需要前后端配合。

**术语衔接提醒**：本课定义的 `小程序`、`setData`、`分包` 在后续课程中会继续出现。如果后续课程改写了某个术语的含义，记得以当时的定义为准。

**和相邻概念的分工**：
- 与 H5 页面相比，小程序多了「包体积」和「跨线程通信」这两项约束，同一个列表页的优化手段并不通用：H5 里靠虚拟滚动就能解决的事，在小程序里还得再叠一层 setData 数据量控制。
- 与原生 App 相比，小程序的逻辑跑在 JS 引擎里，没有直接操作视图节点的能力，凡是要改界面的地方都必须绕回数据驱动这条路。
- 与服务端课程的关系落在安全边界那一节：`wx.login` 换 code、服务端换 openid 这条链路，是前端与后端两门课共同负责的接缝，任何一边单独改都可能让登录态失效。

## 自测题与参考答案

先自己试着回答，再看参考答案。答案都能在上面正文里找到。

**自测 1**：不看正文，用自己的话说出小程序是什么，它和网页有什么区别？

参考答案：小程序是运行在微信等宿主 App 里的轻量应用，用 WXML + WXSS + JS 编写。和网页最大的区别是小程序没有浏览器 DOM 环境，渲染和逻辑跑在两个不同的线程里，数据通过 setData 单向传递。

**自测 2**：setData 为什么不能频繁调用？应该怎么优化？

参考答案：因为每次 setData 都是一次跨线程通信，需要序列化和传输数据。频繁调用会导致界面卡顿。优化方式是合并多次调用为一次，只传变化的字段，不要传整个大数组。

**自测 3**：什么是分包？为什么要用分包？

参考答案：分包是把非首屏页面拆到子包里按需下载。因为微信对主包大小有限制，而且主包越大首屏加载越慢。分包后用户打开小程序时只下载主包，访问分包页面时再按需加载。

**自测 4**：为什么在小程序里写 document.getElementById 会报错？

参考答案：因为小程序没有浏览器 DOM 环境。小程序的渲染层和逻辑层是分开的两个线程，逻辑层里运行的 JS 无法直接访问 DOM。要操作页面要用小程序提供的 API，比如 setData 更新数据来驱动视图变化。

**自测 5**：rpx 和 px 有什么区别？什么时候该用 rpx？

参考答案：px 是固定像素单位，不同屏幕上实际大小不同。rpx 是小程序的响应式单位，750rpx 永远等于屏幕宽度，会根据屏幕大小自动缩放。做布局时应该用 rpx 来适配不同机型。

### 考点 1

题目：围绕“小程序开发要点”中的 小程序、setData、分包，下列哪两项是本课强调的实践判断？

A. 验证 setData 时要固定版本并覆盖边界输入，结论才可复现
B. 把 setData 的单次运行结果当成所有版本和规模都成立
C. 学习 小程序 时要同时说明输入、输出和失败路径，不能只看正常流程
D. 只要 小程序 的常规示例通过，就可以跳过边界与异常路径

正确答案：AC

这道题考的是学习方法论。验证任何结论都要固定条件、覆盖边界，不能只看正常情况就下结论。A 和 C 都强调了这一点，B 和 D 则犯了以偏概全的错误。

### 考点 2

题目：首屏加载过慢，最先考虑的手段是？

A. 把所有资源放进主包
B. 主包瘦身并使用分包与预加载
C. 增加页面数量
D. 关闭缓存

正确答案：B

首屏慢的根本原因是主包太大，要下载的内容太多。解决办法就是把非首屏资源拆出去（分包），同时配置预加载规则让用户在空闲时提前下载。A 会让问题更严重，C 和 D 跟首屏速度没有直接关系。

### 考点 3

题目：`小程序开发要点` 的示例代码用于验证 `小程序`，其背景是双线程模型、setData 优化、分包加载与安全边界。代码的真实内容是下面哪一项？

A. 调用了 `setData()`
B. 调用了 `increase2()`
C. 调用了 `print()`
D. 调用了 `Counter()`

正确答案：A

本课的示例代码是一个分页加载的列表页，核心操作就是调用 setData 把新数据同步到视图层。increase2、print、Counter 都不是小程序的 API。

### 考点 4

题目：为什么小程序里不能使用 document 与 window？

A. 因为性能太差
B. 因为需要付费开通
C. 因为没有浏览器 DOM 环境
D. 因为语法不支持

正确答案：C

小程序的逻辑层跑在 JSCore 或 V8 引擎里，不是浏览器环境，自然没有 document 和 window 这些浏览器对象。这是小程序架构设计决定的，不是性能问题也不是语法限制。

### 考点 5

题目：适配不同机型屏幕尺寸，推荐使用哪个单位？

A. pt
B. em 固定值
C. px
D. rpx

正确答案：D

rpx 是小程序专门为屏幕适配设计的单位，750rpx 始终等于屏幕宽度。px 是固定像素，在不同屏幕上大小不一样。pt 主要用于 iOS 原生开发，em 是 CSS 里的相对单位但不适合做小程序的主要布局单位。

### 考点 6

题目：填空：补齐下面这段术语说明中的空缺。课程 `双线程模型、setData 优化、分包加载与安全边界。`，这段说明是：`____`：小程序把数据从逻辑层同步到视图层的接口；应合并调用、只传变化字段，避免频繁跨层通信。空缺处应填哪个术语？

正确答案：setData

这道题考的就是 setData 的定义。记住关键词：数据同步、逻辑层到视图层、合并调用、只传变化字段。

## 术语速查

| 术语 | 一句话说明 |
| --- | --- |
| 小程序 | 运行在宿主 App 里的轻量应用，用 WXML + WXSS + JS/TS 编写，没有浏览器 DOM |
| setData | 把数据从逻辑层同步到视图层的接口，要合并调用、只传变化字段 |
| 分包 | 把非首屏页面拆到子包按需下载，控制主包体积通过平台限制 |
| 渲染层 | 独立线程，负责视图渲染，通过 setData 接收逻辑层的数据 |
| 逻辑层 | 运行 JS 的线程，处理业务逻辑，通过 setData 与渲染层通信 |
| rpx | 响应式尺寸单位，750rpx 等于屏幕宽度，用于适配不同机型 |
| 主包 | 启动就要用到的代码与页面所在包，体积直接决定首屏下载耗时 |
| 预加载 | 用户停在指定页面时提前下载分包，跳转时子包已在本地 |
| 数据路径 | setData 中形如 orders[1].title 的写法，只更新变化的那一格 |
| wx:key | 给 wx:for 列表项绑的稳定唯一标识，缺了会导致节点复用错位 |
| createSelectorQuery | 逻辑层查询节点尺寸与位置的官方接口，替代 DOM 查询 |
| 虚拟列表 | 只渲染屏幕可见区域节点的长列表方案，配合分页把节点数压到几十 |
