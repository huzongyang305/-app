## 核心概念定义

| 术语 | 操作性定义 | 常见边界与风险 |
| --- | --- | --- |
| SSD | 用闪存保存数据、没有机械寻道、随机访问快的存储设备。 | 没有机械寻道不等于什么负载都快：只测顺序读写会低估随机访问，盘接近填满时长尾延迟还会陡增。 |
| 写放大 | 一次逻辑写入最终引起多倍物理写入，常见于日志与 SSD。 | 易错：固态盘寿命与性能同时下降；正确做法是对齐写入、减少小随机写，并启用回收指令。 |
| ftl | 闪存转换层：把闪存先擦后写、按块擦除的特性抽象成块设备，并负责磨损均衡与垃圾回收。 | 它替你挡掉按块擦除的怪癖，代价是映射表一改、回收一动，一次逻辑写就变成好几页物理写。 |
| 页缓存 | 内核把最近读写的文件页留在内存里的缓存，写入先进缓存，fsync 才保证落盘。 | 易错：把 `write` 返回 0 当成数据已在盘上；脏页还在内存排队，掉电就丢，反过来过量 fsync 又抬高写放大。 |

## 原理与运行机制

### 机制总览

**教材衔接：核心知识**

### 1. SSD 以页读写、以块擦除，FTL 负责地址映射、磨损均衡和垃圾回收。

- 关键做法：基线只保留 写放大 必需的部分，其余条件一次加一个。
- 验证标准：SSD 的结果可复现、错误可解释、失败能恢复。

一次 `write()` 在这条栈里往下走多远，就是"数据到底在哪一层"的答案：

```text
你的程序  write(fd, buf)
   ↓  libc 只是陷入内核，字节还全在内存里
内核页缓存（脏页在这里排队）
   ↓  write 返回 0 只说明"内核收到了"，不说明"盘上有了"
文件系统（ext4 / APFS / NTFS）：把字节切成块，记元数据
   ↓  fsync、O_SYNC 或写回线程把脏页压下去，顺带发 TRIM
块层与驱动：按逻辑块号下发请求
   ↓
FTL：逻辑块号 → 物理页的映射表，外加磨损均衡与垃圾回收
   ↓  闪存只能按页写、按块擦
NAND 颗粒
```

看图能记住三件事：一是 `write` 与"落盘"之间隔着好几层；二是"先擦后写"这个硬件怪癖被 FTL 用一层地址翻译挡掉了，所以你才敢当块设备用；三是你以为一次写入只动一页，映射表一改、垃圾回收一动，实际物理写入常常不止一页——写放大就是从这张图里长出来的。

### 2. 随机写、未对齐写和过量 fsync 会放大写放大并降低寿命。

### 边界条件与常见反例

「SSD、存储栈与持久化」的边界不只包括最大最小值，还要覆盖空、重复和失败：

- 空：写 0 字节的记录仍然占一个页；日志文件刚创建就 fsync，需要落的是目录项，光 fsync 文件本身不够。
- 差一：写入大小取"页大小减 1"（4095 字节）照样吃掉一整页，剩下的 1 字节谁都塞不进来。
- 重复：同一逻辑块连写三次，FTL 只是把映射表换到三个新物理页，旧页变成垃圾等回收——测出来的写放大里含这一份。
- 错位：起始偏移没对齐时，一次 4096 字节的写会跨到两个对齐块，多出来的那一半要走读-改-写。
- 满盘：可用空间压到 90% 以上后，空闲块不足，垃圾回收开始搬家式写入，延迟长尾陡增；空盘测出来的数字不能当容量规划依据。
- 失败：中途拔电或内核崩溃时，已经返回成功的 `write` 可能整批丢失；只有做完 fsync 并检查返回值的那一笔，才有资格写进"已提交"列表。

**教材衔接：最小可运行示例**

```python
block = 4096

```

```text

```

### 对齐示例：同样写 4096 字节，代价差一倍

把偏移量也算进去，就能看见"未对齐"三个字到底多贵：

```python
PAGE = 4096  # 闪存页大小，也是对齐单位


def touched_blocks(size: int, offset: int) -> int:
    """这次写入横跨多少个对齐块：跨块的那一半要走读-改-写。"""
    first = offset // PAGE
    last = (offset + size - 1) // PAGE
    return last - first + 1


for size, offset in ((100, 0), (100, 4000), (4096, 0), (4096, 512), (8192, 0)):
    print(f"写 {size} 字节，偏移 {offset} -> 落到 {touched_blocks(size, offset)} 个对齐块")
```

```text
写 100 字节，偏移 0 -> 落到 1 个对齐块
写 100 字节，偏移 4000 -> 落到 2 个对齐块
写 4096 字节，偏移 0 -> 落到 1 个对齐块
写 4096 字节，偏移 512 -> 落到 2 个对齐块
写 8192 字节，偏移 0 -> 落到 2 个对齐块
```

第三行和第四行是同一笔 4096 字节的写，只是起点差了 512 字节，代价就从 1 块变成 2 块。日志、数据库页缓存这类模块喜欢"接着上次的位置往后写"，偏移量很容易不是 4 的倍数，这就是排查写放大时要先看对齐的原因。

### 落盘示例：write 之后还要不要 fsync

```python
import os

fd = os.open("wal.log", os.O_WRONLY | os.O_CREAT | os.O_TRUNC)
os.write(fd, b"commit\n")   # 到这一步只保证进了内核页缓存
os.fsync(fd)                 # 等脏页真正压到设备再返回

dir_fd = os.open(".", os.O_RDONLY)   # 新建的文件还要保证目录项落盘
os.fsync(dir_fd)
os.close(dir_fd)
os.close(fd)

print("已落盘")
```

```text
已落盘
```

跑两遍你会看到完全一样的输出——正常路径本来就该一样。差别只有拔掉电源才暴露：去掉 `os.fsync(fd)` 那行，`wal.log` 里的这笔记录可能整条不存在。动手验证的方式是写完立刻 `strace -e fsync python 你的脚本`（Linux）或用系统调用监控工具，看有没有真的发出 fsync，而不是靠肉眼读代码。

## 常见误区与易错点

| 容易写错的做法 | 实际现象 | 原因与正确做法 |
| --- | --- | --- |
| 把写入当成立即可靠 | 缓存未落盘，掉电就丢数据。 | 关键路径显式落盘，或按业务设定持久化级别。 |
| 忽略写放大与磨损 | 固态盘寿命与性能同时下降。 | 对齐写入、减少小随机写，并启用回收指令。 |
| 只测顺序读写 | 真实负载是随机访问，结论不成立。 | 用贴近业务的随机读写与队列深度测试。 |
| 拿空盘跑分做容量规划 | 占用爬到九成后延迟长尾突然炸开。 | 在 80%、90%、95% 三档占用下分别复测随机读写。 |
| 只对新文件的内容做 fsync | 掉电后目录里根本查不到这个文件。 | 新建或改名后，再对父目录的句柄 fsync 一次。 |

## 术语速查

| 术语 | 一句话说明 |
| --- | --- |
| `SSD` | 用闪存保存数据、没有机械寻道、随机访问快的存储设备。 |
| `写放大` | 一次逻辑写入最终引起多倍物理写入，常见于日志与 SSD。 |
| `ftl` | 闪存转换层：把闪存先擦后写、按块擦除的特性抽象成块设备，并负责磨损均衡与垃圾回收。 |
| `页缓存` | 内核把最近读写的文件页留在内存里的缓存，写入先进缓存，fsync 才保证落盘。 |
| `fsync` | 让内核等到这笔写入真正落到设备再返回的系统调用。 |
| `对齐写` | 起始偏移和长度都踩在页或扇区边界上，避免半块写入触发读-改-写。 |
| `TRIM` | 告诉固态盘哪些逻辑块已经没用了，让它提前把这些块擦掉、留出空闲池。 |
| `写屏障` | 强制"数据块先落、元数据后落"的顺序，防止掉电后日志比数据还新。 |

**术语关系**：`SSD`（用闪存保存数据、没有机械寻道、随机访问快的存储设备） → `写放大`（一次逻辑写入最终引起多倍物理写入） → `ftl`（闪存转换层：把闪存先擦后写、按块擦除的特性抽象成块设备） → `页缓存`（内核把最近读写的文件页留在内存里的缓存）。
