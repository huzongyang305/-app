## 核心概念定义

| 术语 | 操作性定义 | 常见边界与风险 |
| --- | --- | --- |
| 多路复用 | 一条连接上并发交错传输多个请求，省掉重复建连与连接排队。 | 只在请求真正并发时才有收益：单请求或串行压测看不出区别，大文件下载场景协议版本影响也有限。 |
| 队头阻塞 | 前面的响应或丢包卡住后续数据；HTTP/2 在 TCP 层仍有这个问题，HTTP/3 用 QUIC 消除。 | 易错：丢包时全部流受影响；正确做法是TCP 层队头阻塞仍存在，需 HTTP/3。 |
| QUIC | 基于 UDP 的传输协议，把加密、流控与多路复用做进协议本身，支持独立流与快速建连。 | 依赖 UDP：企业网络封 UDP 或七层网关不支持时一直走不了，局域网几乎不丢包也测不出它的优势。 |
| 0-RTT | 复用会话票据让首个请求随握手一起发出，代价是存在被重放的风险。 | 易错：非幂等请求也随票据提前发出，会话票据被重放时同一操作会执行两次；只对幂等请求启用。 |
| 流（Stream） | 逻辑上的独立请求响应通道 | 流是连接内部的逻辑通道，粒度小到可以单独取消，也容易被漏看；排查时要记录流取消与重传率，只看整条连接成功会掩盖问题。 |
| 帧（Frame） | HTTP/2 的最小传输单位 | 请求与响应被拆成多个帧交错发送，单个帧不完整就无从解读，也没有按帧重传这回事，补包仍由底层 TCP 负责。 |
| 多路复用 | 多个流在同一连接上交错传输 | 它解决的是应用层排队，底层一个 TCP 丢包仍会让同连接上所有流一起等重传；再搞域名分片会把收益抵消掉。 |
| HPACK / QPACK | 头部压缩算法，QPACK 解决 QUIC 乱序问题 | 靠静态表与动态表消掉重复头部，但 Cookie 与冗余头不精简，压完体积照样大；HTTP/2 与 HTTP/3 各自用不同算法。 |
| 服务器推送 | HTTP/2 特性，实践中收益有限，已逐步弃用 | 推的资源若客户端已缓存或最终没用上，就是纯浪费带宽；与其依赖推送，不如改用 `preload` 与 103 Early Hints。 |
| 优先级 | HTTP/2 的优先级树；HTTP/3 用紧急度 + 增量 | 优先级树实现复杂，标了也未必换来预期的发送顺序；HTTP/3 已把它简化成紧急度加增量，且不能靠它代替资源瘦身。 |
| ALPN | TLS 握手时协商应用协议（h2、h3） | 协商不上时会静默退回旧协议且无人知，要用示例里的 `grep -E` 核对 ALPN 结果并监控协商版本分布。 |
| 0-RTT | 会话复用下提前发送数据，需防重放 | 只有握过手、拿到会话票据的重连才能省掉这一往返，首次访问仍是 1-RTT；按 0 往返估算提速会高估收益。 |

## 原理与运行机制

### 机制总览

**教材衔接：HTTP/1.1 的瓶颈**

1. **队头阻塞**：同一连接上请求必须按序返回，前面慢会拖住后面。
2. **连接数限制**：浏览器对同域名并发连接有限制，只能靠多开连接绕过。
3. **头部重复**：每次请求都重复发送大量头部（Cookie、User-Agent）。

**教材衔接：HTTP/2 的改进**

| 特性 | 作用 |
| --- | --- |
| 二进制分帧 | 把请求与响应拆成帧，替代文本协议 |
| 多路复用 | 一条连接上并行多个流，解决应用层队头阻塞 |
| 头部压缩 HPACK | 用静态表与动态表压缩重复头部 |
| 服务器推送 | 主动推送资源（实践中效果有限，已逐步弃用） |
| 流优先级 | 标记资源优先级（实现复杂，HTTP/3 已简化） |

注意：HTTP/2 仍建立在 TCP 之上，**TCP 层的队头阻塞依然存在**——丢一个包会阻塞整条连接的所有流。

**教材衔接：HTTP/3 与 QUIC**

HTTP/3 改用基于 UDP 的 QUIC 协议：

1. **彻底解决队头阻塞**：各流独立重传，互不影响。
2. **0-RTT / 1-RTT 建连**：把 TLS 1.3 握手与传输握手合并，恢复连接几乎零延迟。
3. **连接迁移**：用连接 ID 而不是 IP+端口标识连接，切换 Wi-Fi/蜂窝网络不掉线。
4. **强制加密**：QUIC 默认加密，包括大部分传输元数据。

代价：UDP 在部分企业网络被限制，服务端实现与运维复杂度更高。

**教材衔接：实践建议**

| 场景 | 建议 |
| --- | --- |
| 普通网站 | 开启 HTTP/2，配合 TLS 与 Brotli 压缩 |
| 移动端 / 弱网 | 优先启用 HTTP/3（CDN 一般可一键开启） |
| 大量小请求 | 多路复用收益明显，减少域名分片 |
| 大文件下载 | 关注带宽与断点续传，协议版本影响较小 |

优化顺序建议：先做缓存与压缩、减少请求数与体积，再考虑协议升级；协议只是放大器，不能弥补糟糕的资源策略。

**教材衔接：队头阻塞对比演示**

假设一条连接上同时请求 A、B、C 三个资源，且传输中丢失了一个数据包：

| 版本 | 表现 |
| --- | --- |
| HTTP/1.1 | 请求串行，A 未返回前 B、C 排队等待（应用层队头阻塞） |
| HTTP/2 | 三条流并行发送，但共用一条 TCP 连接——丢包导致**所有流**一起等待重传（TCP 层队头阻塞） |
| HTTP/3 | 每条流独立重传，只有受影响的那条流等待，其余照常到达 |

这就是为什么弱网（丢包率高）环境下 HTTP/3 的收益最明显，而局域网（几乎不丢包）下三者差异不大。

**教材衔接：版本迁移与兼容实践**

1. 服务端同时支持 h2 与 h3（h3 通过 Alt-Svc 头通告），客户端自动择优。
2. 保留 HTTP/1.1 作为兜底，部分企业网络会封 UDP。
3. HTTP/2 下不要再做域名分片（会削弱多路复用收益），可去掉雪碧图与内联小图。
4. 观察指标：协议版本分布、握手耗时、首字节时间、重传率，用真实数据判断收益。

**教材衔接：深入补充：HTTP/2 与 HTTP/3 的取舍与边界**

### 一、把概念放回真实约束

学习HTTP/2 与 HTTP/3时，最容易只记住结论而忽略前提。先写出三个约束：数据规模、时间预算、可接受的失败方式；再判断 HTTP/2 与 HTTP/3 在这些约束下是否仍然成立。只要约束改变，原来的最优解就可能变成错误解。

## 典型应用场景

- **认为 HTTP/2 没有队头阻塞**：典型现象是丢包时全部流受影响；正确做法是TCP 层队头阻塞仍存在，需 HTTP/3。
- **继续做域名分片**：典型现象是连接数增加、收益为负；正确做法是HTTP/2 下收敛域名。
- **无脑使用 0-RTT**：典型现象是重放攻击风险；正确做法是只对幂等请求启用。
- **防火墙未放行 UDP**：典型现象是HTTP/3 一直不可用；正确做法是放行 UDP 并验证 Alt-Svc。

### 最小验证场景

- 准备：保留 `bash` 示例的原始输入，先记录 `HTTP/2 与 HTTP/3` 的基线输出和完整运行命令。
- 观察：先核对 出现字面量 `ALPN|HTTP/`，再改变一个与 `多路复用` 相关的条件。
- 判定：新结果与 `HTTP/2 与 HTTP/3` 的基线不同不等于错误；只有当差异破坏了 `多路复用` 的定义或错误表中的约束，才判定为失败。

### 选择与边界

- 使用 `多路复用` 时，一条连接上并发交错传输多个请求，省掉重复建连与连接排队；共享状态与调度顺序会改变结论，单线程或串行测试通过不等于并发下成立。
- 使用 `队头阻塞` 时，前面的响应或丢包卡住后续数据；HTTP/2 在 TCP 层仍有这个问题，HTTP/3 用 QUIC 消除；易错：丢包时全部流受影响；正确做法是TCP 层队头阻塞仍存在，需 HTTP/3。
- 使用 `QUIC` 时，基于 UDP 的传输协议，把加密、流控与多路复用做进协议本身，支持独立流与快速建连；网络延迟、超时与版本协商会改变行为，只在真实链路或多版本客户端上验证才算数。
- 使用 `0-RTT` 时，复用会话票据让首个请求随握手一起发出，代价是存在被重放的风险；易错：重放攻击风险；正确做法是只对幂等请求启用。

### 最小可验证示例

```bash
# 检查服务端支持的协议版本
curl -I --http2 https://example.com
curl -I --http3 https://example.com          # 需要 curl 支持 HTTP/3

# 查看协商结果与连接复用情况
curl -v -o /dev/null -s https://example.com 2>&1 | grep -E 'ALPN|HTTP/'
```

## 时间/空间复杂度或性能分析

| 要点 | 说明 |
| --- | --- |
| 域名收敛 | HTTP/2 下单连接多路复用，域名分片反而有害 |
| 资源合并 | 不再为减少请求数而过度合并，避免缓存粒度变粗 |
| 服务端推送替代方案 | 用 `preload` / `103 Early Hints` |
| 头部体积 | 压缩后仍需精简 Cookie 与自定义头 |
| 拥塞控制 | QUIC 可插拔，常见 CUBIC 与 BBR |
| 中间设备 | HTTP/3 依赖 UDP，需确认防火墙与负载均衡支持 |
| 降级策略 | 客户端先用 HTTP/2，Alt-Svc 探测成功后再走 h3 |
| 观测 | 记录协商版本、握手耗时、流取消与重传率 |

**测量方法**：以 `HTTP/2 与 HTTP/3` 的 `HTTP/2` 场景为对象，固定输入跑一遍记录基线，再把规模或并发度提高一个数量级复测；两次结果的差值与波动范围才是结论依据。

## 与其他知识点的关系

**教材衔接：版本对照速查**

| 维度 | HTTP/1.1 | HTTP/2 | HTTP/3 |
| --- | --- | --- | --- |
| 传输层 | TCP | TCP | QUIC（基于 UDP） |
| 并发方式 | 多连接或流水线 | 单连接多路复用 | 单连接多路复用（独立流） |
| 队头阻塞 | 有（连接级） | TCP 层仍有 | 基本消除（流级独立） |
| 头部压缩 | 无 | HPACK | QPACK |
| 建连 | TCP + TLS | TCP + TLS（ALPN 协商） | TLS 集成在 QUIC 内 |
| 握手往返 | 3 次以上 | 2 到 3 次 | 1 次（会话复用可 0 次） |
| 连接迁移 | 不支持 | 不支持 | 支持（连接 ID） |
