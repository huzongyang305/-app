## 项目背景

一个批量任务在单机运行正常，上并发后偶发超时、CPU 利用率不高但吞吐上不去。需要区分线程池排队、锁竞争、伪共享、上下文切换、内存可见性与 GC 暂停，并用可控实验验证。

## 故障现场

### 现场 1：并发度越高反而越慢

**症状**：并发度越高反而越慢。

**定位**：锁竞争或线程切换成本超过了并行收益。

**修复**：缩小临界区、分批聚合或改用无锁结构与 channel，再重新测并发拐点。

### 现场 2：结果偶发不一致

**症状**：结果偶发不一致。

**定位**：共享状态缺少同步，或内存可见性没有保证。

**修复**：用原子操作、锁或 channel 明确所有权，并用 race detector 或压力测试复现。

## 常见错误与排查

> 复核：已人工核对并重写（2026-10-06），每行对应本课的一个真实易错点。

| 易错点 | 容易踩的做法 | 正确结论 |
| --- | --- | --- |
| 线程池不设上限与拒绝策略 | 任务堆积导致内存膨胀，最终雪崩 | 设置队列上限与拒绝策略，并监控排队时间 |
| 用锁保护过大的范围 | 锁竞争让并行退化成串行 | 缩小临界区，必要时拆锁或改用无锁结构 |
| 靠功能测试验证数据竞争 | 竞争有随机性，跑一次通过不代表没问题 | 使用 race detector 或 ThreadSanitizer 并配合压力测试 |
| 忽略上下文切换成本 | 线程过多时切换开销吃掉并行收益 | 按 CPU 与 IO 特性调整线程数，用剖析数据决定 |
