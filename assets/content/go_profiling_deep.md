### 从概念到验证的学习链条

1. `pprof`：先掌握 Go 自带的性能剖析工具，可采集 CPU、内存与阻塞 profile，再用它解释 `trace` 为什么会出现。
2. `trace`：先掌握 记录运行时事件的追踪工具，用来观察调度与 GC 时间线，再用它解释 `基准测试` 为什么会出现。
3. `基准测试`：先掌握 以 Benchmark 开头的测试函数，重复执行并报告每次耗时与内存分配，再用它解释 `逃逸分析` 为什么会出现。
4. `逃逸分析`：先掌握 编译器判断变量能否分配在栈上，用 -gcflags=-m 查看结果，再用它解释 `内存分配剖析` 为什么会出现。
5. `内存分配剖析`：先掌握 用 -benchmem 与 memprofile 找出分配热点，减少不必要的堆分配，再用它解释 本课示例的观察结果 为什么会出现。

- **优化后不做回归对比**：典型现象是无法证明改进有效；正确做法是保留基准与剖析快照做前后对比。

### 考点 7：`pprof`

- **要点**：Go 自带的性能剖析工具，可采集 CPU、内存与阻塞 profile。
- **pprof 的边界**：结论随输入规模变化，小规模成立不代表大规模成立，需要重新测量。

### 考点 8：`trace`

- **要点**：记录运行时事件的追踪工具，用来观察调度与 GC 时间线。
- **trace 的边界**：只在「记录运行时事件的追踪工具，用来观察调度与 GC 时间线」这一前提下成立，换输入或换环境要重新验证。

### 考点 9：`基准测试`

- **要点**：以 Benchmark 开头的测试函数，重复执行并报告每次耗时与内存分配。
- **基准测试 的边界**：越界、悬垂引用与释放顺序会破坏结论，必须在边界输入下复验。

### 考点 10：`逃逸分析`

- **要点**：编译器判断变量能否分配在栈上，用 -gcflags=-m 查看结果。
- **逃逸分析 的边界**：静态检查只在编译期成立，运行期输入仍需校验。

### 考点 11：`内存分配剖析`

- **要点**：用 -benchmem 与 memprofile 找出分配热点，减少不必要的堆分配。
- **内存分配剖析 的边界**：越界、悬垂引用与释放顺序会破坏结论，必须在边界输入下复验。

### 考点 12：排错——只做 CPU 剖析

- **现象**：阻塞与内存问题看不到。
- **处理**：结合阻塞、互斥与堆剖析一起看。

### 考点 13：排错——采样时间过短

- **现象**：数据波动大，结论不可靠。
- **处理**：延长采集时间并重复验证。

### 考点 14：综合辨析——`pprof` 与 `内存分配剖析`

- **辨析点**：`pprof` 的定义是 Go 自带的性能剖析工具，可采集 CPU、内存与阻塞 profile；`内存分配剖析` 的定义是 用 -benchmem 与 memprofile 找出分配热点，减少不必要的堆分配。
- **答题要求**：面对 `Go 性能剖析与调优（进阶）` 的题目，先判断描述的是 `pprof` 还是 `内存分配剖析`，再归到对应定义，最后写出一个会让该定义失效的边界输入。

### 考点 15：排错评分点

- **现象分**：能写出 阻塞与内存问题看不到，而不是只写“程序有错”。
- **证据分**：保留触发 只做 CPU 剖析 的输入、版本和错误原文。
