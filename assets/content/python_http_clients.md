## 核心概念定义

想象你在学开车——先认识仪表盘上的各种指示灯，再上路才不会慌。下面这些术语就是你写 HTTP 客户端时的"仪表盘"。

| 术语 | 通俗类比 | 操作性定义 | 常见边界与风险 |
| --- | --- | --- | --- |
| 连接超时 | 就像打电话等对方接听的秒数——你不能永远等下去 | 客户端等待与目标建立连接的最长时间。 | 易错：以为设了它就能管住整个请求；连接建好之后的等待归读取超时，写入和池等待还要各自设预算。 |
| 读取超时 | 接通电话后，等对方说话的最长时间——沉默太久就挂断 | 连接建立后等待响应数据的单次最长时间。 | 它只管单次等待响应数据的时间；正文要求超时预算从用户请求总时长反推，另设一个总超时兜住整次请求。 |
| 幂等性 | 就像按电梯按钮——按一次和按十次，电梯只来一趟 | 同一请求执行多次产生与执行一次相同结果的语义。 | 语义上幂等不等于服务端真能去重：下单超时后重复提交会扣款两次，写操作必须由服务端提供幂等键保证。 |
| 连接池 | 像共享单车站点——车骑完放回站点，下个人直接骑走，不用每次造新车 | 复用已建立连接并限制并发数量的资源池。 | 易错：在《Python HTTP 客户端工程：超时、重试与认证》里采用「调用外部接口不传 timeout，连接或读取一直等待，线程和连接池被占满」时，请求不设置超时会表现为错误结果、异常中断或状态不一致；正确做法是为连接、读取、写入和池等待设置明确预算，并设置总超时。 |
| 指数退避 | 像给忙碌的朋友打电话——第一次等 1 分钟再打，第二次等 2 分钟，第三次等 4 分钟……别一直狂轰滥炸 | 每次重试按指数增长等待时间，并常加入随机抖动避免同时重试。 | 示例用 `min` 把增长封顶在 5.0 秒；不设次数与上限、又对非幂等请求退避重试，只会放大故障。 |
| 限流 | 像餐厅门口叫号——一小时只放 60 桌进去，超了就得排队等 | 服务端按时间窗口限制请求速率或并发量，客户端需要识别并配合等待。 | 429 通常带 Retry-After，客户端要按它等待而不是立刻重发；把限流状态接进监控，才能看出配额有没有被反复撞满。 |

## 原理与运行机制

### 机制总览

**教材衔接：核心知识**

### 1. 请求组成与状态码分类

一次 HTTP 请求就像寄一封快递信——你需要写收件地址（URL）、选寄送方式（方法）、在信封上贴标签（请求头）、塞进信件内容（正文）。对方收到后回你一个编号（状态码），告诉你结果如何。

2xx 表示成功（快递已签收），3xx 表示重定向（地址改了，帮你转寄），4xx 通常是客户端错误（地址写错了），5xx 表示服务端错误（快递站着火了）；429 表示被限流（快递站今天收件满了，明天再来），具体语义还要结合响应体和接口文档。

在Python HTTP 客户端工程：超时、重试与认证里可以这样验证：用 MockTransport 返回 503 和 200，打印每次请求的状态码与响应体，观察分支逻辑。

边界：不能只看状态码判断业务结果，很多接口在 200 中返回错误码；也不能把 404 当成可重试错误无限请求。

工程视角：状态码分类集中在客户端层，业务层只处理解析后的结果或领域异常；每个错误附带请求编号和时间戳。

### 2. 超时与重试策略

超时就像给每次外卖订单设定"最长等待时间"——超过 30 分钟没到就取消；重试就是取消后重新下一单。两者共同决定故障时你浪费多少时间。

连接超时针对建立连接（打电话等接通），读取超时针对等待响应数据（等对方说话），写入超时针对发送正文（你说话的时间），池超时针对等待空闲连接（等电话线路空出来）；指数退避让等待时间逐次增长，抖动避免大量客户端同时重试。

在Python HTTP 客户端工程：超时、重试与认证里可以这样验证：对返回 503 的模拟接口只在 429 与 5xx 时重试，最多三次，并打印每次退避时间。

边界：只应重试幂等或带幂等键的操作；重试次数过多会放大故障，银行扣款、下单等操作必须有服务端幂等保证。

工程视角：超时预算从用户请求总时长反推，重试次数与退避上限写进配置，记录每次尝试和最终结果。

### 3. 会话、连接池与并发

客户端对象就像一个专属快递员——他认识所有常去地址的路，效率越来越高。如果每次寄信都换一个全新快递员，他就永远记不住路。复用连接可以显著降低延迟。

连接池按主机复用 TCP 连接，池大小限制并发请求；会话还能统一管理请求头、认证、Cookie 和重定向策略。

在Python HTTP 客户端工程：超时、重试与认证里可以这样验证：在 with 语句中创建一个客户端并连续发送多次请求，确认退出时连接被关闭。

边界：同一个客户端可以被多个线程共享，但配置不可在请求期间随意修改；异步客户端要放在异步上下文中使用。

工程视角：应用生命周期内复用一个客户端，按依赖注入传入业务服务；关闭钩子负责释放连接池。

### 4. 认证、TLS 与秘密管理

认证就像进大楼刷门禁卡——你要证明"我是谁"。把凭据放在请求头里（像把门禁卡挂在脖子上），而不是放在 URL 里（像把密码写在明信片上）。TLS 校验就像检查门禁系统有没有被改装过。

Bearer 令牌放入 Authorization 头，Basic 认证把用户名密码编码后放入头部；OAuth2 需要获取、刷新和过期处理，TLS 证书验证防止中间人攻击。

在Python HTTP 客户端工程：超时、重试与认证里可以这样验证：创建带默认 Authorization 头的客户端，并让日志只记录令牌前缀和哈希，不输出完整值。

边界：关闭证书校验会让 HTTPS 失去防篡改能力；把令牌放在查询参数会进入代理和访问日志。

工程视角：凭据轮换有明确流程，测试使用假令牌，生产日志脱敏；重定向到其他域时避免自动携带敏感头部。

### 5. 分页、限流与流式响应

分页就像翻字典——一次看一页，翻到看完为止。限流就像餐厅叫号——别催太急。流式响应就像水管放水——不要等整个游泳池灌满再开始喝，边灌边喝。

游标分页使用下一页标记，页码分页依赖页大小和总数；429 响应通常带 Retry-After，客户端应尊重等待时间；流式响应按块读取，避免把大文件全部放进内存。

在Python HTTP 客户端工程：超时、重试与认证里可以这样验证：读取分页响应直到下一页为空，并在收到 429 时根据 Retry-After 暂停。

边界：分页期间数据可能变化，结果不一定是一致快照；无限循环的分页接口要有最大页数和总大小保护。

工程视角：分页器封装成生成器，下载设置大小上限和校验和，限流状态纳入监控。

### 渐进式示例 1：指数退避计算

先来一个简单的——计算第 5 次重试时应该等多久：

```python
def delay(attempt):
    return min(0.2 * (2 ** attempt), 5.0)
print(delay(5))
```

运行结果：`5.0`。为什么？0.2 × 2⁵ = 6.4，但上限是 5.0，所以取 5.0。就像你等朋友回电话，最多等 5 秒就不等了。

### 渐进式示例 2：带重试的 HTTP 请求

下面用 httpx 的 MockTransport 模拟一个"前两次失败、第三次成功"的服务：

```python
import httpx

calls = {"count": 0}

def handler(request: httpx.Request) -> httpx.Response:
    calls["count"] += 1
    if calls["count"] < 3:
        return httpx.Response(503, text="busy", request=request)
    return httpx.Response(200, json={"ok": True}, request=request)

transport = httpx.MockTransport(handler)
with httpx.Client(transport=transport, base_url="https://api.test") as client:
    for attempt in range(3):
        response = client.get("/health", timeout=2.0)
        print("尝试", attempt + 1, "状态", response.status_code)
        if response.status_code == 200:
            print("结果:", response.json())
            break
    else:
        print("三次后仍失败")

print("请求次数:", calls["count"])
```

输出：
```text
尝试 1 状态 503
尝试 2 状态 503
尝试 3 状态 200
结果: {'ok': True}
请求次数: 3
```

### 渐进式示例 3：安全的分页循环

```python
import httpx

def fetch_all_pages(client, max_pages=100):
    cursor = None
    all_items = []
    for _ in range(max_pages):
        params = {"cursor": cursor} if cursor else {}
        resp = client.get("/items", params=params, timeout=5.0)
        data = resp.json()
        all_items.extend(data.get("items", []))
        cursor = data.get("next")
        if not cursor:
            break
    return all_items
```

这段代码设置了 `max_pages` 保护，即使服务端游标异常也不会无限请求。

## 常见误区与易错点

| 容易写错的做法 | 实际现象 | 原因与正确做法 |
| --- | --- | --- |
| 请求不设置超时 | 在《Python HTTP 客户端工程：超时、重试与认证》里采用「调用外部接口不传 timeout，连接或读取一直等待，线程和连接池被占满」时，请求不设置超时会表现为错误结果、异常中断或状态不一致。 | 为连接、读取、写入和池等待设置明确预算，并设置总超时 |

| 每次请求新建客户端 | 在《Python HTTP 客户端工程：超时、重试与认证》里采用「在循环里创建新 Client 或 Session，连接无法复用且资源反复建立」时，每次请求新建客户端会表现为错误结果、异常中断或状态不一致。 | 应用级复用一个客户端，通过依赖注入传入业务层，退出时关闭 |
| 把令牌放在 URL 中 | 在《Python HTTP 客户端工程：超时、重试与认证》里采用「用查询参数传递访问令牌，令牌进入代理、浏览器历史和访问日志」时，把令牌放在 URL 中会表现为错误结果、异常中断或状态不一致。 | 使用 Authorization 请求头，日志只保留脱敏后的凭据标识 |

### 现场 1：请求不设置超时

**症状**：在《Python HTTP 客户端工程：超时、重试与认证》里采用「调用外部接口不传 timeout，连接或读取一直等待，线程和连接池被占满」时，请求不设置超时会表现为错误结果、异常中断或状态不一致。

**根因与修复**：为连接、读取、写入和池等待设置明确预算，并设置总超时。

**自检**：在本课示例里复现「请求不设置超时」，改成为连接、读取、写入和池等待设置明确预算，并设置总超时后重跑；如果症状消失且失败路径按预期变化，说明定位正确。

### 现场 2：对非幂等操作盲目重试

**症状**：在《Python HTTP 客户端工程：超时、重试与认证》里采用「下单请求超时后自动重复提交，用户被扣款两次」时，对非幂等操作盲目重试会表现为错误结果、异常中断或状态不一致。
