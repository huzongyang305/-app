## 核心概念定义

| 术语 | 操作性定义 | 常见边界与风险 |
| --- | --- | --- |
| 工具声明 | 交给模型的可调用能力描述，含名称、说明、输入 Schema 与是否必须调用。 | 易错：声明写得越详细越准，冗长描述会稀释关键约束。 |
| 输入 Schema | 用 JSON Schema 描述参数的类型、必填项、枚举与嵌套结构。 | 易错：必填性写在属性里，实际由 required 列表决定。 |
| 强制策略 | 控制模型能否直接回答的自由度：自动、禁止、必须、指定某个。 | 易错：设为必须就能保证业务安全，仍需服务端二次判权。 |
| 并行调用 | 模型在一次响应里给出多个相互独立的调用意图。 | 易错：并行调用可以只回填第一个，其余编号缺失会打断推理。 |
| 调用编号 | 每次调用的唯一标识，结果消息必须原样带回。 | 易错：编号可随意编造，它必须与模型给出的完全一致。 |
| tool_use 块 | Anthropic 协议里把文本与工具调用作为并列内容块返回的形态。 | 易错：把它当成消息字段处理，解析路径不同会漏读。 |
| 错误恢复 | 工具失败后把结构化错误作为结果回传，让模型改参或换工具。 | 易错：失败就返回空串，模型会误认为执行成功。 |
| MCP | 用统一协议把工具、资源与提示模板暴露给模型的开放标准。 | 易错：MCP 只是远程函数调用，它带能力发现与上下文协议语义。 |

## 原理与运行机制

### 机制总览：一次工具调用的四个必经状态

模型侧的调用意图、客户端侧的执行、结果回填、模型再推理，构成一个不可缺环的四状态机。工程上几乎所有「工具不稳定」的现象，都能定位到某个状态没有正确闭合。

**教材衔接：一份可上线的工具声明**

```json
{
  "name": "query_order",
  "description": "按订单号查询物流状态与预计送达日期。仅用于已下单订单，不用于退款申请。",
  "input_schema": {
    "type": "object",
    "properties": {
      "order_id": {"type": "string", "pattern": "^\\d{8}$", "description": "八位数字订单号"},
      "region": {"type": "string", "enum": ["cn", "sea", "eu"], "default": "cn"},
      "with_detail": {"type": "boolean", "default": false}
    },
    "required": ["order_id"],
    "additionalProperties": false
  }
}
```

**教材衔接：四要素各自防什么错**

| 要素 | 作用 | 缺失后果 | 写法要点 |
| --- | --- | --- | --- |
| 名称 | 供模型选择 | 名称含糊导致选错工具 | 动词加对象，避免缩写 |
| 描述 | 界定适用与不适用 | 模型把退款请求也拿来自查 | 明确写出「不用于什么」 |
| 参数 Schema | 约束形状 | 参数类型漂移，校验失败 | 必填放 required，取值放枚举 |
| 强制策略 | 控制自由度 | 该查的没查，靠记忆作答 | 关键动作设必须或指定 |

**教材衔接：并行调用的正确闭合**

模型给出三个调用时，客户端要并发执行并逐条回填。并发只改变执行方式，不改变「每个编号一条结果」的协议要求。

```python
import concurrent.futures as cf

def run_tool_calls(tool_calls: list[dict], registry: dict) -> list[dict]:
    def one(call):
        fn = registry[call['name']]
        try:
            import json
            args = json.loads(call['arguments'])
            return {'tool_call_id': call['id'], 'content': json.dumps(fn(**args), ensure_ascii=False)}
        except Exception as exc:                     # 失败也要原样回传，让模型有机会改参
            return {'tool_call_id': call['id'], 'content': f'ERROR: {type(exc).__name__}: {exc}'}

    with cf.ThreadPoolExecutor(max_workers=4) as pool:
        return list(pool.map(one, tool_calls))
```

**教材衔接：两种协议形态的差异**

| 维度 | tools 加 tool_calls | tool_use 内容块 |
| --- | --- | --- |
| 调用意图位置 | 挂在 assistant 消息的数组字段上 | 与文本并列的独立内容块 |
| 结果回填 | tool 角色消息加调用编号 | 在 user 消息里放 tool_result 块并带编号 |
| 并行表达 | 数组里多个条目 | 同一次响应多个块 |
| 停止原因 | 结束原因为工具调用 | 停止原因为工具使用 |

**教材衔接：MCP 的分层与工具生态**

MCP 把「能力发现」「调用」「上下文与资源」三类交互标准化：客户端先列举服务端暴露的工具，再按 Schema 调用，同时还能读取资源与提示模板。相比每家各写一个适配函数，它的价值在于工具可跨应用复用、权限在会话层声明、调用可审计。

```python
TOOLS = [
    {'name': 'query_order', 'desc': '查询订单状态', 'risk': 'read'},
    {'name': 'create_refund', 'desc': '发起退款', 'risk': 'write'},
]

def expose(only_read: bool = True) -> list[str]:
    return [t['name'] for t in TOOLS if not only_read or t['risk'] == 'read']

print(expose(True), len(TOOLS))
```

## 典型应用场景

| 场景 | 典型输入或前提 | 期望产物 |
| --- | --- | --- |
| 订单状态查询 | 用户提供八位订单号 | 一次读取调用加口语化转述 |
| 多店铺库存核对 | 一次需比较三个仓库 | 并行三个调用后汇总比较结论 |
| 退款审批 | 写操作且涉及金额 | 必须经人工确认再执行写入 |
| 跨系统工单流转 | 工具分布在不同团队 | 用 MCP 服务端统一暴露与鉴权 |

- 典型现象：模型反复调用同一个查询却从不收尾。正确做法：检查是否每个调用编号都回填了结果，未闭合会让模型停在等待状态。
- 典型现象：工具偶尔返回半结构化文本导致解析崩溃。正确做法：工具出口统一成 JSON 字符串，失败时返回结构化错误而不是抛异常。
- 典型现象：把删除类接口直接暴露给模型。正确做法：写操作设为需确认，或从可调用集合里移除，只允许生成待执行草案。

### 最小验证场景

- 准备：注册两个只读工具与一个写工具，固定一段必须触发两次调用的问题。
- 观察：模型是否一次给出两个调用、客户端是否并发执行、两条结果是否各自带正确编号回填。
- 判定：最终回答引用了两次调用的返回值且没有再补发调用；若出现第三次重复调用，说明某条结果未闭合。

## 代码/协议/SQL 示例

**教材衔接：调用前的本地校验**

模型给出的参数要先在客户端校验，再交给业务函数。把校验失败信息写成结构化错误回传，是提升一次成功率最便宜的手段。

```python
import json, re

def validate(call: dict) -> tuple[bool, str]:
    try:
        args = json.loads(call['arguments'])
    except json.JSONDecodeError:
        return False, 'ERROR: arguments 不是合法 JSON，请重新输出'
    if not re.fullmatch(r'\d{8}', str(args.get('order_id', ''))):
        return False, 'ERROR: order_id 必须是 8 位数字字符串'
    return True, ''

print(validate({'arguments': '{"order_id": "8023"}'})[0])
```

**教材衔接：统计工具调用质量的表结构**

工具调用是否稳定，只能靠落库统计。按工具名聚合成功率与平均轮次，能直接暴露最不可靠的那个工具。

```sql
SELECT tool_name,
       COUNT(*)                                    AS calls,
       ROUND(100.0 * SUM(ok::int) / COUNT(*), 1)   AS success_rate,
       ROUND(AVG(round_index), 2)                  AS avg_round
FROM tool_call_log
WHERE ts >= now() - INTERVAL '7 day'
GROUP BY tool_name
ORDER BY success_rate ASC;
```

错误表现：用正则从自由文本里抠参数，模型稍改措辞就失效。

```python
order_id = re.search(r'订单号(.+)', reply).group(1)   # 依赖模型的表述习惯
```

正确写法：让模型走结构化调用通道，参数从 Schema 字段读取，不解析自然语言。

```python
args = json.loads(response.choices[0].message.tool_calls[0].arguments)
order_id = args['order_id']
```

## 时间/空间复杂度或性能分析

| 指标 | 随什么增长 | 典型区间 | 优化手段 |
| --- | --- | --- | --- |
| 声明占用 Token | 工具数量与描述长度 | 每工具数十至上百 Token | 只暴露当前意图相关的子集 |
| 单轮时延 | 一次模型往返加工具执行 | 工具快、模型慢 | 并行执行多个调用 |
| 会话总轮次 | 依赖链深度与失败重试 | 一到六轮常见 | 提高一次成功率、合并调用 |
| 尾延迟 | 最慢的那个工具 | 取决于外部系统 | 超时上限加降级返回 |
| 空间 | 历史调用与结果累积 | 每轮都进上下文 | 结果摘要、丢弃已完成中间态 |

工具数量与提示成本是线性关系，但选错率的上升是非线性的：当功能相近的工具同时存在时，模型区分它们的负担明显加大。可行做法是先做意图分类，再按类别只挂载相关的三到五个工具。

并行调用改善的是墙钟时间而不是 Token。三个调用并发执行可以把总等待压到最慢一个的量级，但三条调用与三条结果都会进入上下文，输入成本随调用数上升。要控制成本就要收紧结果体积，例如只回必要字段而不是整个对象。

错误恢复的成本结构值得单独设计。一次校验失败后重试，通常只增加一小段轮次；但如果把异常直接抛给前端，用户会看到完全失败的会话，等于前面所有 Token 全部浪费。因此「把错误原样回传给模型」在期望成本上几乎总是更划算。

## 常见误区与易错点

- **必填性写在属性描述里。** 是否必填由 required 列表决定，描述文字不承担约束。
- **描述只写「能做什么」。** 不写「不用于什么」，模型会把它用在边界外的请求上。
- **并行调用只回填第一个。** 未闭合的编号会让模型停在等待，表现为重复调用或不回答。
- **把参数当字典直接用。** 参数多为 JSON 字符串，必须先解析再校验。
- **工具失败返回空串。** 空结果被理解为「查到了但没内容」，比明确报错更危险。
- **让模型直接执行写操作。** 金额、删除、外发类动作必须有确认或人在环节点。
- **一次挂载全部工具。** 声明本身占 Token，且相近工具会互相干扰选择。
- **把 MCP 当纯远程调用。** 它同时规定能力发现、资源与上下文的表达方式。
- **强制策略当成安全机制。** 它只约束模型是否必须调用，权限判定必须在服务端。
- **不记录调用审计。** 出问题时无法回答「是谁让模型调了这个接口」，合规风险很高。

## 自测题与参考答案

**教材衔接：题号 1** — 在 tools 参数里描述一个函数时，最容易被模型用错的字段是？

**参考答案**：parameters 里的类型与必填约束。

本题正确项是「parameters 里的类型与必填约束」。名字和描述帮模型选对工具，而真正把参数填错的多半是类型与必填项没写清，例如把数字写成字符串、可选项被当必填漏传，导致校验直接失败。示例代码有助理解却不参与结构约束，光靠描述很难表达嵌套对象和枚举取值，Schema 才是执行前的合同。

**教材衔接：题号 2** — 模型一次返回三个 tool_calls，正确的处理方式是？

**参考答案**：逐个执行并各回一条结果消息。

本题正确项是「逐个执行并各回一条结果消息」。协议规定每个 tool_call 都有独立 id，客户端要为每个 id 回一条对应结果，模型才能把返回值与调用配对，缺失或错配会打断后续推理。只执行第一个会让另外两个查询永远没有结果，合并成一条丢掉 id 对应关系，拒答则浪费了一次已经成功的规划。

**教材衔接：题号 3** — Anthropic 的 tool_use 块与 OpenAI 的 tool_calls 字段相比，显著差异是？

**参考答案**：后者挂在 assistant 消息而非内容块。

本题正确项是「后者挂在 assistant 消息而非内容块」。OpenAI 把调用意图挂在 assistant 消息的 tool_calls 数组上，Anthropic 则在 content 块序列里插入 tool_use 块，文本与工具调用是同一次响应中的并列内容块，解析路径因此不同。两边都要用 Schema 声明输入参数，也都支持一轮多个调用。

**教材衔接：题号 4** — 工具执行抛异常时，最有利于模型自我纠正的做法是？

**参考答案**：回传结构化的错误原因和修正建议。

本题正确项是「回传结构化的错误原因和修正建议」。把失败信息作为工具结果原路返回，模型能据此改参数或换工具，形成有依据的重试闭环，同时保留调用链与 id 的对应关系。空字符串让模型误判成功，直接中断流程会让用户看不到任何解释，重发原始提问则丢掉了这次调用的上下文。

**教材衔接：题号 5** — 下面这份工具声明里，模型必须提供的参数有几个？
import json
spec = {'name': 'query_order', 'parameters': {'type': 'object', 'properties': {'order_id': {'type': 'string'}, 'lang': {'type': 'string'}}, 'required': ['order_id']}}
print(len(spec['parameters']['required']))

**参考答案**：1 个，即 order_id。

本题正确项是「1 个，即 order_id」。required 列表只登记了 order_id，properties 只声明字段的存在与类型，是否必填完全由 required 决定，因此模型可以省略 lang 但必须给出订单号。enum 只约束取值范围而不是必填性，把 properties 的数量当成必填数会误判为 2，认为必填可空则与 Schema 语义相反。

spec = {'name': 'query_order', 'parameters': {'type': 'object', 'properties': {'order_id': {'type': 'string'}, 'lang': {'type': 'string'}}, 'required': ['order_id']}}
print(len(spec['parameters']['required']))
答：1 个，即 order_id。
