## 核心概念定义

| 术语 | 操作性定义 | 常见边界与风险 |
| --- | --- | --- |
| 带宽时延积 | 链路带宽与往返时延的乘积，表示网络中在途数据量。 | 乘积随路径与负载变化；只在空闲网络测一次就当窗口依据不可信，要固定路径、时间窗与数据量，在接近真实负载下复测。 |
| 拥塞控制 | TCP 根据网络反馈调整发送速率，避免丢包和排队崩溃。 | 换成 CUBIC 或 BBR 对丢包的反应就不同；小缓冲降延迟但伤吞吐，大缓冲提吞吐却造成缓冲膨胀，必须按场景选。 |
| TCP | 面向连接的可靠传输协议：握手建连、序号与重传保序，滑动窗口与拥塞控制决定吞吐。 | 易错：局域小链路里窗口够用就照搬参数；长肥管道上窗口小于带宽时延积时吞吐上不去，要在该规模重新评估。 |
| 调优 | 结合带宽时延积、拥塞控制、TCP、调优，写出一个真实项目中的使用场景。 | 易错：只改内核参数不做分层测量；先定位慢在 DNS、连接、传输还是应用处理，再动 RTT、重传、丢包与窗口的参数。 |
| 带宽 | 带宽决定单位时间能传多少数据，延迟决定第一个字节多久到达 | 易错：高带宽但交互卡顿的问题被漏掉；正确做法是同时记录带宽、往返时延、抖动与丢包。 |
| 窗口 | TCP 允许发送方在途的数据量上限，取接收窗口与拥塞窗口的较小值。 | 易错：只调大内核缓冲却忽略窗口缩放协商；跨洲链路上窗口小于带宽时延积，吞吐会被锁死。 |
| 缓冲膨胀 | 队列过长导致排队延迟显著上升的现象。 | 易错：把带宽跑满当成健康；交互流量对排队延迟敏感，要结合 AQM 与队列长度治理。 |

## 原理与运行机制

### 先分层：一次请求慢在哪里

打开网页或调用 API，总耗时可以拆成几段：

| 阶段 | 典型耗时 | 主要影响因素 | 观察手段 |
| --- | --- | --- | --- |
| DNS 解析 | 0~100 ms | 缓存命中、递归服务器距离 | `dig`、`%{time_namelookup}` |
| TCP 握手 | 1 个 RTT | 物理距离、丢包重传 | `%{time_connect}` |
| TLS 握手 | 1~2 个 RTT | 协议版本、证书链、会话复用 | `%{time_appconnect}` |
| 首字节 TTFB | 取决于服务端 | 排队、数据库、下游调用 | `%{time_starttransfer}` |
| 内容传输 | 大小 ÷ 有效吞吐 | 带宽、窗口、丢包 | `%{time_total}` |

只有把总耗时拆开，才能判断该优化 DNS、连接、服务端还是传输。把"接口慢"直接归因于带宽，是网络排障最常见的起点错误。

### 带宽、延迟与带宽时延积

带宽是单位时间能发送的比特数，延迟是数据走完路径需要的时间。二者衡量不同维度：一条 1 Gbps 的卫星链路带宽很高，但 RTT 可能有 600 ms，交互依然迟钝。

带宽时延积（Bandwidth-Delay Product，BDP）把两者乘起来：

BDP（字节）= 带宽（bit/s）× RTT（s）÷ 8

它表示"链路中最多能同时在途多少数据"，也就是管道本身能装下的水量。1 Gbps × 100 ms 的链路 BDP 是 12.5 MB。如果发送窗口只有 64 KB，发送方每 100 ms 只能发出一窗口，吞吐上限约为 64 KB ÷ 0.1 s ≈ 5.2 Mbps，带宽的绝大部分都闲着。

### 三个窗口：rwnd、cwnd 与实际可发数据

TCP 的发送量受两个窗口约束：

- **接收窗口 rwnd**：接收方通过 ACK 通告"我还能收多少"，受接收缓冲区大小限制。
- **拥塞窗口 cwnd**：发送方根据拥塞控制算法维护的估计值，网络拥塞时缩小。
- **实际可发送 = min(rwnd, cwnd)**，再减去已发送但未确认的数据。

窗口缩放（window scaling）选项让 rwnd 可以超过 64 KB；如果协商失败，长肥管道会被 64 KB 上限卡死。`ss -ti` 能看到 `cwnd`、`rwnd`、`rtt`、`retrans` 等字段，是排查单连接吞吐的第一手数据。

### 丢包、队列与缓冲膨胀

路由器接口的队列满时会丢包。传统尾部丢弃（tail drop）会让多条流同时减窗，吞吐呈锯齿状。队列排得越长，端到端延迟越高，这就是**缓冲膨胀**（bufferbloat）：带宽没跑满，但每个包都要在队列里等几百毫秒。

- 队列太小：突发流量直接丢包，链路利用率下降。
- 队列太大：延迟被排队拉长，实时音视频、游戏和交互请求先受害。
- **AQM**（如 CoDel、FQ-CoDel）按"包在队列里待了多久"决定丢弃或标记，把排队延迟压在几十毫秒内。

所以"加带宽"不一定能解决卡顿：如果瓶颈是队列延迟，更大的缓冲区反而让情况更糟。

### 拥塞控制：loss-based 与 model-based

拥塞控制决定发送方如何探测可用带宽：

- **Reno/CUBIC**（Linux 默认 CUBIC）：把丢包当作拥塞信号，丢包就减小 cwnd。在随机丢包的无线链路上容易误判，吞吐上不去。
- **BBR**：测量瓶颈带宽和最小 RTT，按模型维持发送速率，不把丢包直接当拥塞。在高丢包长距离链路上通常表现更好，但会与 loss-based 流争抢带宽。

换算法不是"越快越好"：BBR 可能让同链路上的 CUBIC 流饿死，必须在自己的业务路径上压测，并观察重传率与延迟分布。

### 重传、RTO 与虚假重传

- 超时重传（RTO）在迟迟收不到 ACK 时触发，并带指数退避，最坏情况下一次丢包会让连接停顿数百毫秒到数秒。
- 快速重传靠 3 个重复 ACK 提前发现丢包，不必等 RTO。
- **虚假重传**（spurious retransmission）是包其实到了、只是 ACK 慢，重传纯属浪费。抓包看到重传率高但应用正常，要区分真丢包与乱序、延迟造成的假象。

### 读数：工具与指标

| 工具 | 看什么 | 典型用法 |
| --- | --- | --- |
| `curl -w` | DNS、连接、TLS、TTFB、总耗时 | `curl -w '%{time_namelookup} %{time_connect} %{time_starttransfer} %{time_total}\n' -o /dev/null -s URL` |
| `mtr` | 逐跳延迟与丢包 | `mtr -rwc 100 host` |
| `ss -ti` | cwnd、rtt、重传、发送队列 | `ss -tin state established` |
| `iperf3` | 纯吞吐基线 | `iperf3 -c host -t 30 -P 4` |
| `tcpdump` | 重传、乱序、窗口 | `tcpdump -i eth0 -w cap.pcap 'tcp port 443'` |

测量必须固定路径、时间窗与数据量；一次测速只能说明那个瞬间。

## 典型应用场景

### 五种常见现场

| 现场 | 典型现象 | 先查指标 | 处理方向 |
| --- | --- | --- | --- |
| 跨国 API 下载慢 | 首字节正常，传输阶段慢 | BDP、rwnd、cwnd | 扩大接收缓冲、确认窗口缩放、就近接入 |
| 视频会议卡顿 | 带宽充足但延迟忽高忽低 | 排队延迟、抖动 | 缩短队列或启用 AQM |
| 移动网络上传慢 | 丢包 1%~3% 时吞吐骤降 | 重传率、cwnd 变化 | 评估 BBR，别把丢包全当归因 |
| 容器内吞吐上不去 | 多连接总和远低于网卡能力 | 软中断、CPU limit | 多队列/RSS、调整 CPU 配额 |
| 首屏加载慢 | DNS 与 TLS 占比高 | 分阶段计时 | 预连接、会话复用、CDN |

### 排障顺序

1. **量化现象**：记录 URL、客户端位置、时间窗与成功率，先确认是普遍慢还是个别用户慢。
2. **分阶段计时**：用 `curl -w` 或浏览器瀑布图拆出 DNS、连接、TLS、TTFB、传输。
3. **只改一层**：慢在传输就先看 `ss -ti` 的 rwnd、cwnd、retrans；慢在 TTFB 就转去查服务端。
4. **对照实验**：换网络、换客户端版本重复测量，排除本机与缓存因素。
5. **回归**：在同一时间窗、同一路径复测，记录 P50/P95 与重传率，而不是只看峰值带宽。

### 最小验证场景

- 准备：选一个目标 URL，记录 `curl -w` 的五个时间字段与所在网络。
- 观察：把 `--http1.1` 换成 `--http2`，或打开、关闭连接复用，比较连接与 TLS 耗时。
- 判定：某一段耗时占比超过 30% 时优先优化那一段；只改一处后复测，差异要能重复出现。
- 失败信号：总耗时变化但分段没变，说明瓶颈可能在客户端或测量方式本身。

### 选择与边界

- `带宽时延积` 只在路径稳定时有意义：跨运营商、跨洲路径的 RTT 会波动，要按时间窗取分位数。
- `拥塞控制` 的收益依赖对端与中间设备：BBR 对丢包不敏感，但可能与 CUBIC 流不公平竞争。
- `TCP` 调优参数在三处生效：容器、宿主机、客户端，实际吞吐取最小限制，只改一端可能完全无效。
- 用无线、VPN、代理测量时，链路本身会引入额外延迟与丢包，结论不能直接外推到生产路径。

## 代码/协议/SQL 示例

### 用 Python 算一遍 BDP 与窗口上限

示例先用 `gethostbyname` 验证本机解析，再用同一组链路参数计算 BDP 与窗口受限吞吐：

```python
import socket

ip = socket.gethostbyname("localhost")
print("resolved:", ip)

bandwidth_mbps = 1000
rtt_ms = 100
window_kb = 64

bdp_bytes = bandwidth_mbps * 1_000_000 / 8 * (rtt_ms / 1000)
window_limited_mbps = window_kb * 1024 * 8 / (rtt_ms / 1000) / 1_000_000

print(f"BDP: {bdp_bytes / 1024 / 1024:.1f} MB")
print(f"window-limited: {window_limited_mbps:.1f} Mbps")
print(f"bdp_covers_window={window_kb * 1024 <= bdp_bytes}")
```

```text
resolved: 127.0.0.1
BDP: 11.9 MB
window-limited: 5.2 Mbps
bdp_covers_window=False
```

把 `window_kb` 改成 8192（8 MB）再运行，窗口受限吞吐约 655.4 Mbps，仍达不到 1 Gbps，因为 8 MB 还是小于 11.9 MB 的 BDP。只有窗口不小于 BDP，单连接才可能跑满带宽。

### 用 curl 做分阶段计时

`curl -w` 可以直接给出各阶段耗时，适合在真实请求上验证上面的分层：

```bash
curl -s -o /dev/null -w \
  'dns=%{time_namelookup}s connect=%{time_connect}s tls=%{time_appconnect}s ttfb=%{time_starttransfer}s total=%{time_total}s\n' \
  https://example.com/
```

```text
dns=0.004s connect=0.021s tls=0.067s ttfb=0.089s total=0.112s
```

读法：`connect - dns` 是 TCP 握手耗时，`tls - connect` 是 TLS 握手耗时，`ttfb - tls` 是服务端处理与首包时间，`total - ttfb` 是内容传输时间。四项相加接近总耗时，哪一项异常就把排查方向定到那一层。

## 时间/空间复杂度或性能分析

### 三个可以直接算的公式

1. **吞吐上限** ≈ min(rwnd, cwnd) ÷ RTT。窗口 64 KB、RTT 100 ms → 5.2 Mbps；窗口 1 MB、RTT 100 ms → 83.9 Mbps；窗口 12 MB、RTT 100 ms → 约 1006 Mbps，才够 1 Gbps。
2. **BDP** = 带宽 × RTT ÷ 8。1 Gbps × 100 ms → 12.5 MB；10 Gbps × 20 ms → 25 MB。窗口至少要达到 BDP，否则带宽跑不满。
3. **排队延迟** ≈ 队列字节数 ÷ 出口速率。10 Mbps 链路上积压 1 MB，排队约 0.8 秒；同样 1 MB 在 1 Gbps 链路上只排约 8 ms。

### 缓冲膨胀与重传的代价

- **缓冲膨胀**：一条 10 Mbps 家庭链路，路由器队列 2 MB，满载时每个包多等约 1.6 秒，视频会议会先崩。把队列压到 50 ms × 10 Mbps ≈ 62.5 KB，并启用 AQM，延迟会明显下降。
- **重传**：1% 丢包配合 RTO 300 ms，若每丢一个包都触发一次 RTO，1 万个包中约 100 次停顿，累计等待可能超过 30 秒。快速重传能减少一部分，但窗口太小时重复 ACK 不足，仍会退化为 RTO。
- **TLS 握手**：TLS 1.3 把完整握手压到 1 RTT，TLS 1.2 通常要 2 RTT；跨洲 RTT 200 ms 时，一次冷连接就差出 200 ms。
- **DNS**：缓存未命中时一次解析可能 20~100 ms，移动网络下更久；首屏优化里预解析和连接复用往往比换带宽更划算。

### 测量方法

1. 固定路径、时间窗和目标 URL，记录基线：吞吐、RTT 分位数、重传率、TTFB。
2. 只改一个变量（窗口、拥塞算法、队列长度或 CDN），复测同一组指标。
3. 同时记录 P50 与 P95：平均值会掩盖尾部延迟，而用户感知的是尾延迟。
4. 把客户端与服务端指标对齐到同一时间轴，避免把服务端排队误判成网络丢包。

## 常见误区与易错点

| 容易写错的做法 | 实际现象 | 原因与正确做法 |
| --- | --- | --- |
| 只测带宽不看延迟与抖动 | 高带宽但交互卡顿的问题被漏掉。 | 同时记录带宽、往返时延、抖动与丢包。 |
| 只在空闲网络测试 | 拥塞场景下的表现没有验证。 | 在接近真实负载的条件下测量。 |
| 把重传当成唯一指标 | 忽略应用层排队与处理耗时。 | 结合抓包与应用侧指标一起定位。 |
| 把窗口调得远超 BDP | 丢包时大量重传，延迟上升。 | 窗口略大于 BDP 即可，其余交给拥塞控制调节。 |
| 用 ping 代表应用延迟 | 忽略了 TLS 握手与服务端排队。 | 用 `curl -w` 分阶段计时或接入 APM。 |
| 只在 loopback 上压测 | 真实链路的重传与排队没被覆盖。 | 在代表性路径和丢包率下复测。 |
| 只看平均延迟不看分位数 | 尾延迟问题被平均值掩盖。 | 记录 P95/P99 与抖动，和业务 SLA 对齐。 |

### 现场 1：只测带宽不看延迟与抖动

**症状**：高带宽但交互卡顿的问题被漏掉。

**根因与修复**：同时记录带宽、往返时延、抖动与丢包。

**自检**：在本课示例里复现「只测带宽不看延迟与抖动」，改成同时记录带宽、往返时延、抖动与丢包后重跑；如果症状消失且失败路径按预期变化，说明定位正确。

### 现场 2：只在空闲网络测试

**症状**：拥塞场景下的表现没有验证。

**根因与修复**：在接近真实负载的条件下测量。

**自检**：在本课示例里复现「只在空闲网络测试」，改成在接近真实负载的条件下测量后重跑；如果症状消失且失败路径按预期变化，说明定位正确。

### 现场 3：把重传当成唯一指标

**症状**：忽略应用层排队与处理耗时。

**根因与修复**：结合抓包与应用侧指标一起定位。

**自检**：在本课示例里复现「把重传当成唯一指标」，改成结合抓包与应用侧指标一起定位后重跑；如果症状消失且失败路径按预期变化，说明定位正确。

### 自测 1（概念复述）

## 术语速查

| 术语 | 一句话说明 |
| --- | --- |
| `带宽时延积` | 链路带宽与往返时延的乘积，表示网络中在途数据量。 |
| `拥塞控制` | TCP 根据网络反馈调整发送速率，避免丢包和排队崩溃。 |
| `TCP` | 面向连接的可靠传输协议：握手建连、序号与重传保序，滑动窗口与拥塞控制决定吞吐。 |
| `调优` | 结合带宽时延积、拥塞控制、TCP、调优，写出一个真实项目中的使用场景。 |
| `带宽` | 带宽决定单位时间能传多少数据，延迟决定第一个字节多久到达。 |
| `RTT` | 一个数据包往返一次所需的时间，是窗口与超时计算的基准。 |
| `接收窗口` | 接收方通告的可用缓冲空间，限制发送方在途数据量。 |
| `拥塞窗口` | 发送方按拥塞控制算法维护的发送上限，遇到拥塞时收缩。 |
| `缓冲膨胀` | 队列过长导致排队延迟显著上升的现象。 |
| `AQM` | 主动队列管理，按排队时延提前丢弃或标记，控制缓冲膨胀。 |
| `TTFB` | 从发出请求到收到第一个响应字节的时间，包含服务端处理。 |
| `重传` | 丢失或疑似丢失的报文再次发送，过多重传说明链路或窗口异常。 |
