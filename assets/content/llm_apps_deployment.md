## 核心概念定义

| 术语 | 操作性定义 | 常见边界与风险 |
| --- | --- | --- |
| 预填充 | 把整段提示并行算完并写入缓存的阶段。 | 易错：把它当解码计时，长提示的首字延迟会失控。 |
| 解码 | 逐个生成下一 Token 的自回归阶段。 | 易错：认为堆批能无限提升吞吐，显存先触顶。 |
| KV Cache | 缓存历史键值以避免重复计算的结构。 | 易错：忽略它随上下文与并发线性增长。 |
| PagedAttention | 把 KV Cache 分页管理以提升显存利用率。 | 易错：以为它加速了注意力计算，改善的是内存碎片。 |
| 连续批处理 | 请求完成即退出、新请求随时补入批次。 | 易错：与静态批处理混为一谈，后者要等同批最慢者。 |
| 张量并行 | 单层权重切到多卡同时算一层。 | 易错：跨机做张量并行，通信会吃掉收益。 |
| 流水线并行 | 按层切段，数据在多段上流水。 | 易错：批太小时段间空转，气泡严重。 |
| 量化 | 用更低比特表示权重或激活以省显存。 | 易错：只看困惑度不看业务任务，上线后能力塌陷。 |
| LoRA | 冻结基座、只训练低秩增量适配器。 | 易错：多个适配器长期叠加会互相干扰。 |

## 原理与运行机制

### 机制总览：一次请求的开销去哪了

解码阶段每生成一个 Token 都要读一遍全部权重，因此它是内存带宽受限而非算力受限。这解释了为什么单纯换更强算力卡未必提升逐 Token 速度，而量化把权重从 16 比特压到 4 比特往往立刻见效。

**教材衔接：显存构成估算**

```python
GB = 1024 ** 3

def vram_gb(params_b: int, bits: int, ctx: int, batch: int,
            layers: int = 64, hidden: int = 4096) -> tuple[float, float]:
    weight = params_b * bits / 8 / GB                    # 权重占用，与并发无关
    kv = layers * 2 * ctx * hidden * 2 / 8 * batch / GB  # 每层键与值各一份
    return round(weight, 1), round(kv, 1)

print(vram_gb(7, 4, 4096, 16))
```

权重项决定「装不装得下」，缓存项决定「能同时服务多少人」。长上下文场景下后者经常反超前者，这也是很多服务在提示变长后并发骤降的原因。

**教材衔接：四种框架的定位**

| 维度 | vLLM | TGI | Ollama | SGLang |
| --- | --- | --- | --- | --- |
| 主要定位 | 高并发生产服务 | 生产服务与生态兼容 | 本地与单机易用 | 复杂结构化程序化推理 |
| 显存调度 | 分页缓存 | 分页缓存 | 常规分配 | 分页加基数树复用 |
| 批量策略 | 连续批处理 | 连续批处理 | 简单并发 | 连续批处理 |
| 多卡并行 | 张量与流水线 | 张量为主 | 有限 | 张量为主 |
| 适合阶段 | 线上主链路 | 已有生态时 | 开发与小规模内网 | 前缀高度重复的负载 |

**教材衔接：静态批处理与连续批处理**

静态批处理把四条请求绑在一起，直到最长的那条结束才换下一批，短请求在原地空等。连续批处理让先完成的槽位立刻被新请求补上，吞吐提升主要来自减少空转而非算得更快。

```python
def makespan(lens, batch):
    total, i = 0, 0
    while i < len(lens):
        total += max(lens[i:i + batch])
        i += batch
    return total

print(makespan([2, 2, 2, 10], 4), sum([2, 2, 2, 10]))
```

**教材衔接：量化路线对比**

| 路线 | 位宽 | 训练需求 | 典型代价 | 适用判断 |
| --- | --- | --- | --- | --- |
| FP16 / BF16 | 16 | 无 | 显存最大 | 精度优先、显存充足 |
| FP8 | 8 | 需硬件支持 | 极小 | 新卡上的高吞吐 |
| AWQ | 4 | 校准集 | 小幅 | 通用部署首选之一 |
| GPTQ | 4 | 校准集 | 小幅偏任务相关 | 已有工具链时 |
| 稀疏与蒸馏 | 可变 | 需要再训练 | 结构性变化 | 长期固定任务 |

量化必须按业务任务验收，而不是只看困惑度。抽取类与代码类任务对 4 比特更敏感，闲聊与摘要通常容忍度较高。上线前应固定一批回归用例，比较量化前后逐题差异。

**教材衔接：LoRA 的两种服务形态**

训练完的适配器可以合并进基座权重后部署，得到单一模型但失去快速切换能力；也可以保留为独立小权重，由服务侧按请求热切换，省显存但需要框架支持多适配器。多个适配器长期叠加时，能力会向训练分布的并集漂移，表现为「哪个都不精」。

```python
adapters = ['sales', 'legal', 'code']
print(len(adapters), sum(len(a) for a in adapters) > 8)
```

## 典型应用场景

| 场景 | 推荐组合 | 理由 |
| --- | --- | --- |
| 公网高并发问答 | vLLM 加 AWQ 4 比特 | 吞吐与显存利用最优 |
| 内部长文档摘要 | 分页缓存加长上下文预算 | 缓存占比高，需限并发 |
| 单机开发调试 | Ollama | 拉起最快，接口兼容 |
| 多租户不同人设 | 基座加多适配器热切换 | 避免为每个租户存一份权重 |
| 严格低首字延迟 | 缩小提示加前缀复用 | 预填充是首字瓶颈 |

- 典型现象：吞吐随并发先升后降。正确做法：显存触顶后出现换入换出，应限制最大并发并压缩上下文上限。
- 典型现象：量化后函数调用格式频繁出错。正确做法：结构化输出走受限解码，并在评测集里加入格式断言。
- 典型现象：多卡比单卡还慢。正确做法：跨机张量并行的通信开销过大，改用流水线并行或按模型副本水平扩展。

### 最小验证场景

- 准备：固定一批十条请求，长度分布覆盖短与长，分别以并发 1、4、8 压测。
- 观察：首 Token 时延、逐 Token 时延、每秒输出 Token 总数与显存峰值四项。
- 判定：吞吐随并发上升且逐 Token 时延劣化在可接受范围内；若逐 Token 时延翻倍而吞吐未涨，说明已达带宽或显存上限。

```sql
SELECT model_name, quant, concurrency,
       ROUND(AVG(ttft_ms))                AS avg_ttft,
       ROUND(PERCENTILE_CONT(0.95)
         WITHIN GROUP (ORDER BY e2e_ms))  AS p95_e2e,
       ROUND(MAX(tokens_per_sec))         AS peak_tps
FROM bench_run
WHERE started_at >= now() - INTERVAL '3 day'
GROUP BY model_name, quant, concurrency
ORDER BY model_name, concurrency;
```

avg = sum(lat) / len(lat)          # 长尾被完全抹平
```

import statistics
p95 = statistics.quantiles(lat, n=20)[18]
```

## 时间/空间复杂度或性能分析

| 指标 | 随什么增长 | 典型区间 | 优化手段 |
| --- | --- | --- | --- |
| 首 Token 时延 | 提示长度，近线性 | 百毫秒到数秒 | 缩短提示、前缀缓存复用 |
| 逐 Token 时延 | 权重量级与带宽 | 相对稳定 | 量化、更大带宽卡 |
| 显存峰值 | 权重加缓存乘并发 | 与并发线性 | 分页缓存、限制上下文 |
| 吞吐 | 并发与批调度效率 | 存在拐点 | 连续批处理、调候选参数 |
| 冷启动 | 权重大小与磁盘带宽 | 秒到分钟 | 常驻副本、懒加载 |

分页缓存改善的是显存利用率而非计算量：把连续分配换成小页之后，原本被碎片浪费的部分被回收，同等显存能容纳的并发显著提升。收益大小与请求长度方差正相关，长短混合负载受益最大，等长负载受益有限。

量化对两项指标的作用不同。权重位宽下降直接减少每步需要读取的字节，因此逐 Token 时延通常同步改善；但解码计算量下降有限，长提示的预填充阶段若也做激活量化才有明显收益。4 比特与 16 比特的困惑度差异，在真实业务上的表现差异可能更大，务必用任务级评测确认。

批处理存在明确拐点。低于拐点时吞吐随并发近似线性上升；接近显存上限后开始出现缓存换入换出，此时逐 Token 时延急剧恶化而吞吐不再增长。压测的正确产出是拐点位置，而不是单个「最大吞吐」数字。

## 常见误区与易错点

- **把分页缓存当成算子加速。** 它解决显存碎片，注意力算子本身未变快。
- **认为量化只影响精度。** 位宽下降同时改变带宽需求与延迟。
- **跨机做张量并行。** 层内的 AllReduce 对互联带宽极其敏感。
- **只看吞吐不看尾延迟。** 平均值达标而 P95 超时的服务不可用。
- **用困惑度代替任务评测。** 结构化输出与代码任务可能先塌陷。
- **长上下文不单独设限。** 少数超长请求会挤占全部并发额度。
- **批大小一味调大。** 显存触顶后换入换出反而拖慢。
- **LoRA 适配器长期叠加不回归。** 能力互相干扰且难以归因。
- **合并适配器后不留回退。** 一旦漂移需要重训，基座权重应可重新拉起。
- **忽略冷启动与自动扩缩。** 分钟级加载让突发流量直接超时。
- **没有降级路径。** 自建服务抖动时应能切回托管端点而不是整体不可用。

## 自测题与参考答案

**教材衔接：题号 1** — PagedAttention 解决的核心问题是？

**参考答案**：KV Cache 显存碎片与浪费。

本题正确项是「KV Cache 显存碎片与浪费」。传统实现按最大长度连续预留缓存，短请求也占满整块显存，PagedAttention 把缓存切成页并用块表映射，按需分配，显著抬高同卡并发量。量化处理的才是权重精度，注意力算子优化属于内核层面，跨机带宽由张量并行和网络拓扑决定。

**教材衔接：题号 2** — 连续批处理与传统静态批处理的差别是？

**参考答案**：请求随到随插入正在解码的批次。

本题正确项是「请求随到随插入正在解码的批次」。连续批处理在解码步进的间隙替换已完成序列并补入新请求，卡上始终留满算力，尾延迟因此下降；静态批要等整批结束才能换人，短请求被长请求拖住。批大小仍可设动态上限，这种方式完全服务于在线服务，说成固定或离线专用与引入动机相反。

**教材衔接：题号 3** — 单张消费级显卡上要跑 70B 模型做内部工具，代价最低的起步方案是？

**参考答案**：选量化权重并用单卡推理。

本题正确项是「选量化权重并用单卡推理」。量化把权重降到四位左右，显存占用与半精度相比数量级下降，单张消费级卡即可加载，团队上手最快。张量并行需要多卡和高速互联，成本更高；LoRA 只减少训练时的可训练参数，不解决推理显存问题；把上下文压到一个 Token 会让模型失去可用性。

**教材衔接：题号 4** — LoRA 适配器合入基座模型后长期的主要风险是？

**参考答案**：多适配器叠加会互相干扰漂移。

本题正确项是「多适配器叠加会互相干扰漂移」。LoRA 在权重上增加低秩增量，多个适配器同时挂载时增量彼此叠加，容易让原本各自擅长的能力互相抵消或漂移，合入基座后也难以再单独回滚。推理速度只有极小额外开销，主流框架都支持加载适配器，显存不会因低秩结构成倍上涨。

**教材衔接：题号 5** — 下面脚本读取本地 Ollama 服务的标签接口，打印内容对应什么？
import httpx
r = httpx.get('http://127.0.0.1:11434/api/tags')
print(r.status_code, len(r.json().get('models', [])))

**参考答案**：200 与服务上的模型数。

本题正确项是「200 与服务上的模型数」。标签接口是本地 Ollama 的健康与清单端点，服务在跑时返回 200，models 数组给出已拉取或已导入的模型条目，正好对应打印的两个值。404 不是该路径的正常行为，连接被拒只在服务没启动时发生而不是必然结果，显存占用要查另一组接口。

2. 连续批处理的定义：请求随到随插入，完成即退出。
3. 单卡跑超大模型的最低代价路径是量化权重而非并行或微调。
4. 多适配器长期叠加导致能力互相干扰与漂移。

## 术语速查

| 术语 | 一句话说明 |
| --- | --- |
| 预填充 | 并行算完整个提示的阶段，决定首 Token 时延。 |
| 解码 | 逐个生成 Token 的阶段，受内存带宽主导。 |
| KV Cache | 缓存历史键值避免重算，随上下文与并发增长。 |
| PagedAttention | 以分页方式管理缓存，提高显存利用率。 |
| 连续批处理 | 请求随时补入批次，减少槽位空转。 |
| 张量并行 | 单层权重切多卡，适合机内高速互联。 |
| 流水线并行 | 按层切段流水执行，批小则气泡多。 |
| 量化 | 降低位宽以省显存与带宽，需任务级验收。 |
| LoRA | 冻结基座只训低秩增量，可合并或热切换。 |
