## 原理与运行机制

### 机制总览

**教材衔接：核心知识**

### 1. 完整异常处理结构 —— 像餐厅的"应急四步法"

想象你在餐厅遇到一位过敏的客人。你的处理流程是：

1. **try（尝试）**：先看看能不能正常上菜。
2. **except（捕获）**：如果客人过敏了，只处理"过敏"这种情况——别把"客人觉得菜太咸"也当过敏处理。
3. **else（无异常时）**：如果一切顺利，记录"本次服务正常完成"。
4. **finally（无论如何）**：最后一定要清理桌面，不管刚才发生了什么。

异常会沿着调用栈向上传播，就像问题从服务员传到经理、再传到老板。除非中途有人"接住"了它。你可以用裸 `raise` 把异常原样丢给上级，也可以用 `raise 新异常 from 原异常` 建立一个"因果链"——就像在事故报告里写"这次停电是因为昨天的雷击"。

**EAFP vs LBYL**：EAFP（先做了再说，出了问题再处理）像先做菜再调整口味；LBYL（先检查再做）像做菜前先把所有食材检查一遍。Python 社区更偏爱 EAFP。

在 Python 异常、日志与文件 I/O 进阶里可以这样验证：读取配置时把文件不存在与 JSON 格式错误分别转换为领域异常，再用 from 保留原始回溯。

**边界**：捕获范围过宽会把编程错误也吞掉；except 块里的 return 会覆盖异常语义，finally 里的 return 甚至会吞掉未处理异常。

**工程视角**：只在能恢复或能补充上下文的地方捕获异常，边界层统一转换成对外错误，内部保留完整异常链。

### 2. 自定义异常体系 —— 用"业务语言"说错误

想象你叫了一辆网约车，司机告诉你"发动机控制单元第 3 号传感器信号异常"。你完全听不懂。但如果他说"车坏了，需要换一辆"，你就明白了。

自定义异常就是把底层的技术错误"翻译"成调用方能听懂的业务语言。领域模块定义统一根异常，再按失败原因派生子类；异常对象可以携带字段、错误码和原始输入，抛出时用 `from` 关联底层异常，既方便程序判断也方便人阅读。

在 Python 异常、日志与文件 I/O 进阶里可以这样验证：定义 ConfigError，把 FileNotFoundError 与 JSONDecodeError 都转换成该异常，同时在消息中保留路径。

**边界**：不要为每个小分支都建异常类，也不要滥用异常做正常流程控制；异常要能回答"发生了什么、在哪里、如何恢复"三个问题。

**工程视角**：异常层级作为模块公开接口的一部分，版本升级时保持兼容；上层只捕获真正理解的类型，其他异常继续向外传播。

### 3. 文件写入与原子替换 —— 像换菜单一样换文件

想象餐厅要更新菜单。如果你把旧菜单拿走，然后花 10 分钟手写新菜单，这 10 分钟里客人看到的是一张白纸。正确做法是：在后台写好新菜单，然后一瞬间把旧菜单替换掉。

直接覆盖目标文件时，进程在写入中途崩溃会留下半份内容；先写临时文件再原子替换，可以让读者只看到旧版本或新版本。

`tempfile.mkstemp` 在同一目录创建唯一临时文件，写入后 `flush` 并 `fsync` 落盘，再用 `os.replace` 原子替换目标；失败路径负责删除临时文件。

在 Python 异常、日志与文件 I/O 进阶里可以这样验证：实现 write_atomic 函数写入 JSON 配置，并在异常时清理临时文件，验证目标文件始终是合法 JSON。

**边界**：原子替换只能保证单机单文件语义，跨多个文件或分布式系统仍需事务或版本标记；fsync 会带来性能成本，要按数据重要性选择。

**工程视角**：配置、索引和状态文件使用原子写，临时文件与目标放在同一文件系统；为崩溃恢复写测试，而不只测试正常路径。

### 4. 日志上下文与异常记录 —— 像飞机的"黑匣子"

飞机出事后，调查员第一件事就是找黑匣子。黑匣子记录了飞行数据、对话、时间——这些"上下文"比一句"飞机坠毁了"有用得多。

日志记录事件发生时的环境和因果关系；结构化字段、请求标识和异常回溯比一句错误消息更有诊断价值。

`logger.exception` 在异常处理块中同时记录消息和回溯，`extra` 可以附加请求编号与用户标识，handler 决定输出位置，formatter 决定字段布局。

在 Python 异常、日志与文件 I/O 进阶里可以这样验证：在捕获异常后用 logger.exception 记录一次失败，并在结构化字段里带上配置路径，避免只打印一句"失败"的字符串。

**边界**：日志不能记录密码、令牌和完整个人信息；高频路径大量记录调试日志会带来磁盘与性能开销。

**工程视角**：日志级别按环境配置，关键事件带稳定字段名，错误日志附带可检索的请求标识与版本号。

### 5. ExceptionGroup 与 except* —— 像"批量订单的问题汇总"

想象餐厅同时接了 5 个外卖订单，其中 2 个出了问题：一个超时了，一个地址写错了。你可以分别报告这两个问题，也可以把它们打包成一份"问题汇总报告"。

并发任务可能同时产生多个错误，`ExceptionGroup` 把它们打包成一个异常，`except*` 星号语法可以按类型拆分处理。

`ExceptionGroup` 保存子异常列表和统一消息，`except*` 会匹配组内每个分支并重新组合未处理的异常；普通 `except` 只能整体捕获，无法分别处理不同子类型。

在 Python 异常、日志与文件 I/O 进阶里可以这样验证：用 ExceptionGroup 同时承载超时与格式错误，再用 except* 分别记录两类问题，观察剩余异常如何继续抛出。

**边界**：异常组适合天然并行的任务集合，不应为了炫技把互不相关的错误强行打包；异常组不能与普通 except 混用于同一 try 块。

**工程视角**：每个子任务在异常中带上任务标识，处理端按类别汇总并保证未处理异常不会被悄悄丢失。

## 典型应用场景

### 场景 1：捕获后静默跳过 —— "鸵鸟式错误处理"

**比喻**：就像汽车仪表盘亮了故障灯，你直接把灯泡拧下来——问题确实"看不见"了，但发动机随时可能报废。

**典型现象**：在《Python 异常、日志与文件 I/O 进阶》里采用「写 except Exception: pass，把真正的程序错误和外部故障一起吞掉」时，捕获后静默跳过会表现为错误结果、异常中断或状态不一致。

**正确做法**：只捕获预期异常并记录上下文，其他异常继续向外传播。

### 场景 2：重新抛异常时丢失原因 —— "断了线的风筝"

**比喻**：你发现水管漏水，叫了维修工。维修工跟物业报告时只说"有问题"，却不说是哪根管子、在几楼。物业来了完全不知道该带什么工具。

**典型现象**：在《Python 异常、日志与文件 I/O 进阶》里采用「捕获底层异常后直接 raise ConfigError('失败')，原始回溯和原因全部消失」时，重新抛异常时丢失原因会表现为错误结果、异常中断或状态不一致。

**正确做法**：使用 raise ConfigError('...') from exc 建立异常链。

### 场景 3：直接覆盖重要文件 —— "边拆桥边修桥"

**比喻**：你要替换一座桥，如果先把旧桥拆了再建新桥，施工期间所有人都过不去。正确做法是在旁边建好新桥，然后一瞬间切换交通。

**典型现象**：在《Python 异常、日志与文件 I/O 进阶》里采用「打开目标文件反复写入，中途崩溃后留下不完整内容」时，直接覆盖重要文件会表现为错误结果、异常中断或状态不一致。

**正确做法**：写临时文件并 fsync，成功后用 os.replace 原子替换，失败时清理临时文件。

### 场景 4：日志泄露敏感信息 —— "在广场上喊密码"

**比喻**：就像在广场上拿着大喇叭喊"张三的密码是 123456，请确认"——所有人都听到了。日志一旦写出去，运维、监控系统、甚至日志聚合平台都能看到。

**典型现象**：在《Python 异常、日志与文件 I/O 进阶》里采用「把令牌、密码和完整身份证号写进日志，或在调试级别记录请求体全文」时，日志泄露敏感信息会表现为错误结果、异常中断或状态不一致。

**正确做法**：脱敏后再记录，使用稳定字段与摘要，敏感值只保留不可逆标识。

## 代码/协议/SQL 示例

### 最小可验证示例

**教材衔接：原文最小示例**

先看一个最简单的异常链例子——就像在事故报告里写"这次故障的根本原因是XXX"：

```python
try:
    open('missing.json')
except FileNotFoundError as exc:
    try:
        raise RuntimeError('加载失败') from exc
    except RuntimeError as error:
        print(type(error.__cause__).__name__)
```

运行结果会输出 `FileNotFoundError`，因为 `from exc` 把原始的 `FileNotFoundError` 保存为了 `__cause__`。

接下来看一个完整的实战示例，把异常链、自定义异常、原子写入全部串起来：

```python
import json
import os
import tempfile
from pathlib import Path

class ConfigError(Exception):
    """配置读取失败的领域异常。"""

def load_config(path: Path):
    try:
        text = path.read_text(encoding="utf-8")
        return json.loads(text)
    except FileNotFoundError as exc:
        raise ConfigError(f"找不到配置文件: {path}") from exc
    except json.JSONDecodeError as exc:
        raise ConfigError(f"配置不是合法 JSON: {path}") from exc

def write_atomic(path: Path, payload: dict) -> None:
    path.parent.mkdir(parents=True, exist_ok=True)
    fd, temp_name = tempfile.mkstemp(dir=path.parent, prefix=path.name, suffix=".tmp")
    try:
        with os.fdopen(fd, "w", encoding="utf-8") as handle:
            json.dump(payload, handle, ensure_ascii=False)
            handle.flush()
            os.fsync(handle.fileno())
        os.replace(temp_name, path)
    except BaseException:
        Path(temp_name).unlink(missing_ok=True)
        raise

target = Path("demo_config.json")
write_atomic(target, {"name": "学习助手", "version": 2})
print("写入成功:", load_config(target))
try:
    load_config(Path("missing.json"))
except ConfigError as exc:
    print("领域异常:", type(exc).__name__, "原因:", type(exc.__cause__).__name__)
```

**逐行解读**：
- `ConfigError` 是我们的"领域异常"——用业务语言说"配置出问题了"。
- `load_config` 里用 `from exc` 保留原始异常，这样调试时能看到完整的因果链。
- `write_atomic` 先写临时文件，`fsync` 确保数据落盘，最后用 `os.replace` 一步到位替换。如果中途出错，`except BaseException` 负责清理临时文件。

### 考点 10：`领域异常`

- **要点**：用业务语言描述失败原因的异常类型，通常由底层技术异常转换而来。
- **领域异常 的边界**：静态检查只在编译期成立，运行期输入仍需校验。

### 考点 11：`ExceptionGroup`

- **要点**：把多个子异常打包在一起的异常类型，适合表示并发任务的部分失败。
- **ExceptionGroup 的边界**：共享状态与调度顺序会改变结论，单线程或串行测试通过不等于并发下成立。

### 考点 12：排错——捕获后静默跳过

- **现象**：在《Python 异常、日志与文件 I/O 进阶》里采用「写 except Exception: pass，把真正的程序错误和外部故障一起吞掉」时，捕获后静默跳过会表现为错误结果、异常中断或状态不一致。
- **处理**：只捕获预期异常并记录上下文，其他异常继续向外传播。

### 考点 14：综合辨析——`异常链` 与 `ExceptionGroup`

- **辨析点**：`异常链` 的定义是 通过 raise from 或隐式上下文把新异常与原始异常关联起来的因果结构；`ExceptionGroup` 的定义是 把多个子异常打包在一起的异常类型，适合表示并发任务的部分失败。
