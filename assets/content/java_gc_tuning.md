## 本节知识框架

想象你的书桌。每次用完东西随手一放，桌面越来越乱。某天你决定收拾——把没用的扔掉（垃圾回收），把常用的放在手边（年轻代），不常用的塞进抽屉（老年代）。收拾的时候你得停下手里的活（停顿），所以最好快收快停，别一次搞太久。

JVM 的垃圾回收（GC）就是在做这件事：

- **堆**（heap）= 你的书桌，所有对象都放在这里。
- **GC**（垃圾回收器）= 帮你收拾桌面的人，找出没人引用的对象并回收内存。
- **停顿**（pause）= 收拾时你得停下手里的活，时间越短越好。
- **调优** = 通过调整桌子大小、收拾频率和方式，让整体体验更好。

本课会依次聊到四件事：

1. **堆的结构**——年轻代（Eden + Survivor）和老年代，对象按年龄被移动到不同区域。
2. **GC 算法**——Serial、Parallel、CMS、G1、ZGC，不同算法在吞吐量和停顿之间做取舍。
3. **停顿与分配速率**——对象创建越快，GC 越频繁；调优的核心是降低分配速率和控制停顿。
4. **调优实践**——先看指标再改参数，别盲目调大堆内存。

## 核心概念定义

先记住下面四个词，后面所有讨论都围绕它们展开。每个词都用一句话讲清"它是什么"，再补一句"容易踩什么坑"。

| 术语 | 一句话说明 |
| --- | --- |
| `GC` | JVM 的垃圾回收器：按分代回收不可达对象；G1、ZGC 等实现决定吞吐与停顿的取舍。坑：不同收集器行为差异大，换收集器要重新压测。 |
| `堆` | JVM 用于存放对象实例的内存区域，分代收集器会按年龄把对象移动到不同区域。坑：堆不是越大越好，过大反而导致更长停顿。 |
| `停顿` | GC 期间应用线程被挂起的时间；调优目标通常是缩短单次停顿并控制 P99 分布。坑：只看平均停顿不够，P99 才能反映用户真实感受。 |
| `调优` | 基于测量结果调整参数、数据结构或资源分配，在目标指标上获得可复现改善。坑：没有测量就调参等于猜谜。 |

## 原理与运行机制

### 堆的结构：书桌的分区管理

JVM 的堆内存被分成几个区域，就像书桌被分成"桌面""浅抽屉""深抽屉"：

- **年轻代（Young Generation）**：桌面。新创建的对象都在这里。又分为 Eden 区和两个 Survivor 区。
- **老年代（Old Generation）**：深抽屉。在年轻代活了足够多轮（默认 15 次 GC）的对象会被"晋升"到这里。

```text
┌──────────────────────────────────────────┐
│                    堆（Heap）              │
│  ┌─────────────────────────────────────┐ │
│  │           年轻代（Young）             │ │
│  │  ┌─────────┐ ┌─────┐ ┌─────┐       │ │
│  │  │  Eden   │ │ S0  │ │ S1  │       │ │
│  │  └─────────┘ └─────┘ └─────┘       │ │
│  └─────────────────────────────────────┘ │
│  ┌─────────────────────────────────────┐ │
│  │           老年代（Old）              │ │
│  └─────────────────────────────────────┘ │
└──────────────────────────────────────────┘
```

对象在 Eden 区创建，Eden 满了就触发 Minor GC——把存活对象复制到 Survivor，死对象直接回收。经过多轮 GC 仍然存活的对象被晋升到老年代。老年代满了就触发 Major GC / Full GC，通常停顿更长。

### GC 算法：不同"收拾方式"的取舍

| 收集器 | 特点 | 适合场景 |
| --- | --- | --- |
| Serial | 单线程，最简单 | 小堆、嵌入式 |
| Parallel | 多线程并行回收，高吞吐 | 批处理、后台任务 |
| G1（默认） | 分 Region，可控停顿目标 | 大多数 Web 服务 |
| ZGC | 超低停顿（< 1ms），不分代 | 大堆、低延迟要求 |

**G1 是当前默认收集器**（Java 9+）。它把堆切成很多 Region，每次只回收一部分，通过 `-XX:MaxGCPauseMillis` 设置停顿目标（默认 200ms）。

**ZGC** 是 Java 15+ 的生产级收集器，停顿时间几乎恒定在 1ms 以内，不管堆多大。代价是吞吐量略低、内存占用更大。

### 分配速率：决定 GC 频率的关键

分配速率就是"每秒创建多少字节对象"。分配越快，Eden 填满越快，GC 越频繁。

降低分配速率的方法：
- **对象池化**：复用对象而不是每次 new（但要小心线程安全）。
- **基本类型优先**：`int` 比 `Integer` 少一次装箱开销。
- **避免短命大对象**：大字符串拼接用 `StringBuilder`，不要用 `+` 循环。
- **减少不必要的对象创建**：循环内的临时对象提到循环外。

### 内存泄漏：Java 也会"漏"

Java 有 GC 不代表不会内存泄漏。泄漏通常来自：

1. **长生命周期引用**：静态集合不断添加元素，永远不删除。
2. **缓存无上限**：`HashMap` 当缓存用，数据只进不出。
3. **监听器未注销**：注册了事件监听器但忘了移除，对象无法被回收。

```java
// 内存泄漏示例：静态集合只增不减
public class LeakyCache {
    private static final Map<String, byte[]> cache = new HashMap<>();

    public static void put(String key, byte[] data) {
        cache.put(key, data);  // 永远不删除，堆迟早被撑爆
    }
}
```

修复方式：用有上限的缓存（如 Caffeine、Guava Cache），或者定期清理过期条目。

### 查看堆信息的最小示例

```java
public class Main {
    public static void main(String[] args) {
        Runtime runtime = Runtime.getRuntime();
        long max = runtime.maxMemory();
        long total = runtime.totalMemory();
        long free = runtime.freeMemory();
        long used = total - free;

        System.out.println("heap>0: " + (max > 0));
        System.out.println("最大堆: " + max / 1024 / 1024 + " MB");
        System.out.println("已分配: " + total / 1024 / 1024 + " MB");
        System.out.println("已使用: " + used / 1024 / 1024 + " MB");
    }
}
```

```text
heap>0: true
最大堆: 4096 MB
已分配: 256 MB
已使用: 12 MB
```

## 典型应用场景

学完原理，我们来看几个真实场景，帮你把概念落地：

| 场景 | 你会遇到什么 | 怎么做 |
| --- | --- | --- |
| Web 服务延迟高 | 用户请求偶尔超时 | 看 GC 日志，检查停顿分布 |
| 堆内存持续增长 | 服务跑几天后 OOM | 排查内存泄漏（静态集合、缓存） |
| 吞吐量下降 | 同样的请求量变慢 | 检查分配速率和 GC 频率 |
| 大堆启动慢 | -Xmx32g 启动要等很久 | 考虑 ZGC 或减小初始堆 |
| 容器内存限制 | K8s 里 OOMKilled | 对齐 -Xmx 与容器 limit |

**选择与边界**：
- 使用 `GC` 调优时，记住先看分配速率、存活对象、停顿目标和内存使用，而不是先改参数。
- 使用 `堆` 参数时，记住结论随输入规模变化，小规模成立不代表大规模成立，需要重新测量。
- 不同收集器在吞吐、延迟和内存之间取舍，选型要匹配服务目标。

## 代码/协议/SQL 示例

### 完整最小示例

把下面的代码保存为 `GcDemo.java`，用 Java 21+ 编译运行：

```java
public class GcDemo {
    public static void main(String[] args) {
        Runtime runtime = Runtime.getRuntime();

        // 1. 查看初始堆信息
        System.out.println("heap>0: " + (runtime.maxMemory() > 0));
        System.out.println("最大堆: " + runtime.maxMemory() / 1024 / 1024 + " MB");

        // 2. 分配一批对象
        byte[][] data = new byte[100][];
        for (int i = 0; i < data.length; i++) {
            data[i] = new byte[1024 * 1024]; // 每个 1MB
        }

        // 3. 查看分配后的堆信息
        long used = runtime.totalMemory() - runtime.freeMemory();
        System.out.println("分配后已使用: " + used / 1024 / 1024 + " MB");

        // 4. 释放引用
        data = null;

        // 5. 建议 GC（不保证立即执行）
        System.gc();

        // 6. 查看 GC 后的堆信息
        used = runtime.totalMemory() - runtime.freeMemory();
        System.out.println("GC 后已使用: " + used / 1024 / 1024 + " MB");
    }
}
```

```text
heap>0: true
最大堆: 4096 MB
分配后已使用: 112 MB
GC 后已使用: 4 MB
```

运行方式：保存为 `.java` 后用 `javac --release 21` 编译、`java` 运行。可以加 `-verbose:gc` 观察 GC 日志。

## 时间/空间复杂度或性能分析

GC 调优不像算法题用大 O 衡量，更关注"在给定硬件下，停顿和吞吐的拐点在哪里"。

| 指标 | 含义 | 参考值 |
| --- | --- | --- |
| 分配速率 | 每秒创建的对象字节数 | 通常 100MB/s ~ 1GB/s |
| 存活对象大小 | Minor GC 后仍存活的对象总量 | 决定 Survivor 区大小 |
| 停顿时间 | 单次 GC 期间应用暂停的时间 | G1 目标 < 200ms，ZGC < 1ms |
| P99 停顿 | 99% 的 GC 停顿不超过这个值 | 用户体感的真实延迟 |
| GC 频率 | 每秒触发 GC 的次数 | 太频繁说明分配速率过高 |

**测量方法**：
1. 先固定 JVM 参数跑一遍基线，记录吞吐、P99 延迟和堆占用。
2. 把数据量或并发度提高一个数量级复测。
3. 两次结果的差值与波动范围才是结论依据。

## 常见误区与易错点

下面是新手最容易踩的坑，每个都给了"症状→根因→修复"三步对照：

| 容易写错的做法 | 实际现象 | 原因与正确做法 |
| --- | --- | --- |
| 只盯着吞吐量 | 停顿时间被忽略，用户仍感到卡顿 | 同时看吞吐、停顿分布与分配速率 |
| 盲目调大堆内存 | 单次停顿反而更长 | 先定位分配热点与存活对象，再调整堆与回收器 |
| 手动触发回收 | 打乱回收节奏，掩盖真实问题 | 从减少分配和缩短对象生命周期入手 |
| 不看 GC 日志就调参 | 改了参数不知道效果 | 加 `-Xlog:gc*` 记录每次 GC 的详情 |
| 容器里不设 -Xmx | 堆和容器 limit 不对齐，被 OOMKilled | -Xmx 设为容器 memory limit 的 60-75% |

**现场排错示范**：

**症状**：服务运行几天后开始频繁 Full GC，最终 OOM。
**根因**：静态 `HashMap` 当缓存用，数据只增不减，老年代被撑满。
**修复**：改用 Caffeine 缓存库，设置最大条目数和过期时间。观察 GC 日志确认老年代占用稳定。

**容易混淆的相邻概念**：
- `GC` vs `手动释放`：Java 的 GC 自动回收不可达对象，不需要手动 free；C/C++ 才需要。
- `堆` vs `栈`：堆存对象实例（GC 管理），栈存局部变量和方法调用（自动回收）。
- `停顿` vs `吞吐`：停顿是延迟指标（用户感受），吞吐是单位时间处理量（系统能力），通常此消彼长。
