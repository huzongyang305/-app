## 核心概念定义

| 术语 | 操作性定义 | 常见边界与风险 |
| --- | --- | --- |
| 图数据库 | 图数据库把关系作为一等公民，适合多跳关系、路径和推荐场景。 | 易错：拿它当事务型主库，或用多表连接硬套关系；它只擅长多跳与路径，通常要和关系库、分析系统组合使用。 |
| Cypher | 图数据库的声明式查询语言，用 (节点)-[关系]->(节点) 的图形语法描述模式匹配。 | 模式写松了就退化成笛卡尔积，入口属性没建索引时每次全表扫描；判断开销要看执行计划，不能只看结果对不对。 |
| 多跳 | 从起点沿边逐层扩展、经过多步到达目标节点的查询方式。 | 只限跳数不限边类型与方向时路径数会指数膨胀；要固定路径模式、限制深度，并让入口命中索引。 |
| 关系 | 图中的边：连接两个节点，带方向、类型和属性，是图数据库的一等公民。 | 易错：边没有方向与类型，查询语义含糊；正确做法是为边定义类型与方向，并写清允许的路径模式。 |

## 原理与运行机制

### 属性图：点、边、属性

图数据库常见的模型是**带标签的属性图**（labeled property graph）：

- **节点**（node）：表示实体，带一个或多个标签，例如 `:Person`、`:Company`。
- **关系**（relationship）：连接两个节点，有方向、有类型，例如 `-[:WORKS_AT]->`，也可以带属性（入职时间、权重）。
- **属性**（property）：键值对，挂在节点或关系上。

```text
(Alice:Person)-[:KNOWS {since: 2020}]->(Bob:Person)
(Bob:Person)-[:WORKS_AT]->(Acme:Company)
```

和关系库最大的区别在**存储模型**：关系库把关联放在外键列里，查询时靠连接运算拼回去；原生图数据库把每条边存成指向邻居的物理指针（index-free adjacency），遍历一跳就是顺着指针走到相邻节点，代价与"经过多少条边"相关，而不是与整张表的大小相关。

### 从关系到图：多跳为什么不同

关系库里查"朋友的朋友"要两次 JOIN：

```sql
SELECT f2.friend_id
FROM friend f1
JOIN friend f2 ON f1.friend_id = f2.person_id
WHERE f1.person_id = 1;
```

每增加一跳就多一次 JOIN，中间结果随度数放大；优化器还要在连接顺序、索引和临时表之间做选择。图数据库则把查询写成路径模式：

```cypher
MATCH (me:Person {id: 1})-[:FRIEND]->()-[:FRIEND]->(fof)
RETURN fof.id;
```

执行时从入口节点出发，沿 `FRIEND` 边扩展两次，只触碰真正相连的边。两者的差距不在"图一定更快"，而在于**代价增长方式**：图遍历的代价约等于访问的边数，关系查询的代价还包含连接产生的中间行。

但图查询也会爆炸。设平均度数为 d、跳数为 k，路径数约为 d^k：d=100、k=3 就是一百万条路径。多跳查询必须限定边类型、方向和最大深度。

### Cypher 的执行模型

Cypher 是声明式的：你描述"要找什么样的路径"，规划器决定从哪里开始、按什么顺序展开。

- **入口选择**：`MATCH (p:Person {email: $email})` 若能命中 `:Person(email)` 索引，就从单个节点开始；没有索引则退化为全标签扫描。
- **展开方向**：沿关系类型与方向扩展，尽早用 `WHERE` 过滤，避免先产生大量中间结果。
- **断开模式**：一条 `MATCH` 里两个互不连接的模式会产生**笛卡尔积**，行数是两边结果数相乘，必须用共享变量或分步 `WITH` 连起来。
- **可变长度路径**：`[:KNOWS*1..3]` 要显式给上下界，必要时加 `WHERE` 限制节点或关系属性。
- **执行计划**：`EXPLAIN` 只看计划不执行，`PROFILE` 会实际执行并给出每个算子的行数与 db hits。

看到 `AllNodesScan`、`CartesianProduct`、`VarLengthExpand` 的行数异常，就是该补索引或收紧模式的信号。

### 图算法：从遍历到全局计算

多跳查询是"局部遍历"，图算法则常需要"全局计算"：

- **最短路径**：无权图用 BFS，带权图用 Dijkstra 或 A*。
- **PageRank**：按入链质量迭代计算节点重要性，用于权威性排序。
- **社区发现**：Louvain、标签传播，用于分群与反欺诈团伙识别。
- **相似度与推荐**：共同邻居、Jaccard、三角计数。
- **连通分量**：判断两个节点是否属于同一子图，常用于账号合并。

这些算法通常跑在图计算引擎或"投影子图"上，而不是直接压在主库的在线事务上。全局算法的时间复杂度可能是 O(V+E) 到多轮迭代，数据规模大时要离线跑批。

### 超级节点与建模陷阱

**超级节点**是度数极高的节点，例如明星账号、热门商品、默认网关。一次两跳查询经过它，就要展开上百万条边，延迟瞬间失控。常见处理：

- 给边加类型和时间分区，查询时限定 `-[:FOLLOWS {year: 2026}]->`。
- 把超级节点拆成中间节点，或预计算并缓存结果。
- 对确实需要全量邻居的场景改用离线计算。

另一个陷阱是建模：把双向关系存成两条单向边会让路径计数翻倍；把时间只放在节点上，无法回答"某段时间内是否认识"。边和节点都应承载业务语义。

### 写入、事务与索引

- 创建一条边要同时更新两个端点的邻接结构，写放大比单表插入更明显；批量导入时用批处理事务，避免逐条提交。
- 超级节点上的并发写入容易产生锁竞争，需要控制批次大小。
- 为高频入口属性建索引（如 `CREATE INDEX FOR (p:Person) ON (p.email)`），为业务唯一键加约束。
- 图库通常提供 ACID 事务，但跨多个图或与外部系统的一致性仍要自己保证。

## 典型应用场景

### 适合图库的四个场景

| 场景 | 查询特征 | 例子 | 建模要点 |
| --- | --- | --- | --- |
| 反欺诈 | 多跳路径、环路 | 同设备、同银行卡串联出的账号团伙 | 统一实体 ID，边带时间 |
| 推荐 | 共同邻居、多跳 | 好友的好友买过什么 | 限制跳数与边类型 |
| 知识图谱 | 路径与实体消歧 | 企业股权穿透、人物关系 | 边带来源与置信度 |
| 运维拓扑 | 依赖与影响分析 | 服务 → 主机 → 机房 | 区分方向与实时性 |

### 不适合图库的场景

- 单表 CRUD 与简单外键查询：关系库更成熟，运维成本更低。
- 大范围聚合与报表：列式存储和 OLAP 引擎更合适。
- 全文检索与模糊匹配：搜索引擎更合适。
- 超大规模离线图算法：专用图计算框架更合适。

现实系统通常是组合：关系库做主数据与事务，图库放关系子集做多跳，数仓做聚合，三者通过统一 ID 对齐。

### 最小验证场景

- 准备：建 3 个节点、2 条边，记录一次两跳查询的结果与执行计划。
- 观察：先不建索引跑一次，再建入口索引跑一次，比较 db hits 与耗时。
- 判定：两次结果相同但 db hits 大幅下降，说明索引生效；结果不同则先检查边的方向与类型。
- 失败信号：路径数随跳数指数增长，或计划里出现 `CartesianProduct`，说明模式写得过松。

### 选择与边界

- `图数据库` 适合"关系比实体更重要"的问题；实体很多但关系稀疏时，收益有限。
- `Cypher` 要限定方向、类型与深度，否则规划器只能扩大扫描范围。
- `多跳` 的跳数每加一，代价可能乘以平均度数，必须用业务约束封顶。
- `关系` 要带方向、类型和属性，否则同一张图会被不同查询解释成不同语义。

## 代码/协议/SQL 示例

### 关系库里的多跳：递归 CTE

先看关系库怎么走两跳。下面的递归 CTE 从 `a` 出发，沿有向边逐层扩展，并用深度上限防止环导致无限递归：

```sql
WITH RECURSIVE edges(src, dst) AS (
  VALUES ('a', 'b'), ('b', 'c'), ('c', 'd')
), walk(node, depth) AS (
  SELECT 'a', 0
  UNION ALL
  SELECT edges.dst, walk.depth + 1
  FROM edges
  JOIN walk ON edges.src = walk.node
  WHERE walk.depth < 10
)
SELECT node, depth FROM walk ORDER BY depth;
```

```text
node | depth
a    |     0
b    |     1
c    |     2
d    |     3
```

`WHERE walk.depth < 10` 只是兜底；生产环境还要记录已访问节点（PostgreSQL 可用数组路径），否则有环图会重复输出同一条路径。

### 图库里的同一件事：Cypher 路径模式

在 Neo4j 等图库中，先建点边，再用路径模式查同样的两跳：

```cypher
CREATE (alice:Person {name: 'Alice'})
CREATE (bob:Person {name: 'Bob'})
CREATE (carol:Person {name: 'Carol'})
CREATE (alice)-[:KNOWS {since: 2020}]->(bob)
CREATE (bob)-[:KNOWS {since: 2021}]->(carol);

MATCH path = (a:Person {name: 'Alice'})-[:KNOWS*1..3]->(b:Person)
RETURN b.name AS reachable, length(path) AS hops
ORDER BY hops, reachable;
```

```text
reachable | hops
Bob       |    1
Carol     |    2
```

区别在于：Cypher 只声明"从 Alice 出发，沿 KNOWS 走 1 到 3 跳"，怎么走由规划器决定；`*1..3` 的深度上限是必须写的，否则大图上路径数会按度数指数膨胀。

### 读执行计划

对同一条查询执行 `PROFILE`，关注每个算子的实际行数与 db hits：

```text
Operator           Details                  Rows   DB Hits
NodeIndexSeek      a:Person(name='Alice')     1         2
VarLengthExpand    KNOWS*1..3                 2         4
ProduceResults                                2         0
```

如果第一行变成 `AllNodesScan`，说明入口属性没有索引，查询会扫描全部 `Person` 节点；db hits 会从个位数涨到与节点总数同量级。索引建好后再次 `PROFILE`，对比两次的 db hits，就能证明优化是否真正生效。

## 时间/空间复杂度或性能分析

### 路径数量：多跳的第一成本

设平均出度为 d、跳数为 k，不考虑去重时的路径数约为 d^k：

| 平均出度 | 2 跳 | 3 跳 | 4 跳 |
| --- | --- | --- | --- |
| 10 | 100 | 1,000 | 10,000 |
| 100 | 10,000 | 1,000,000 | 100,000,000 |
| 1,000 | 1,000,000 | 1,000,000,000 | 10^12 |

同一句查询，在社交图上多写一跳，代价可能从毫秒级变成分钟级。工程上用"最大深度 + 边类型 + 时间窗"三个约束把路径数压到可接受范围，并让入口命中索引。

### 遍历成本与连接成本

- **图遍历**：从入口出发访问的边数记为 E_visit，时间大致正比于 E_visit 加结果集大小，与全图规模无关。两跳且平均出度 50 时 E_visit 约 2500；若中间经过一个 500 万度的超级节点，E_visit 立刻变成 500 万。
- **关系连接**：每跳一次 JOIN，数据库要扫描或索引查找匹配行，中间结果可能被物化；三跳以上时优化器容易选错连接顺序。
- **索引查找**：入口属性有索引时是 O(log n) 级别的定位；没有索引则是 O(n) 的全标签扫描。

所以"图库更快"只在**从少量入口做局部遍历**时成立；全图聚合并不占优。

### 超级节点与内存

- 一条边在存储上约占几十字节（端点指针、类型、属性、版本信息），1000 万条边大致是几百 MB 到 1 GB 量级，具体取决于属性数量。
- 超级节点会让单次展开的中间结果暴涨，必须靠边类型、时间分区或预计算拆解。
- 并发查询会同时占用遍历缓冲与结果集内存，容量规划要按"峰值并发 × 单查询中间结果"估算。

### 测量方法

1. 用 `PROFILE` 记录每个算子的 rows 与 db hits，先定位是入口扫描还是展开爆炸。
2. 固定图规模、入口节点和跳数，跑 20 次取 P50/P95，而不是只看一次耗时。
3. 把并发从 1 提到 32，观察 P95 与 db hits 是否出现拐点。
4. 对照实验只改一项：加索引、收紧边类型、限制深度，比较改动前后的计划与延迟。

## 常见误区与易错点

| 容易写错的做法 | 实际现象 | 原因与正确做法 |
| --- | --- | --- |
| 把图查询当多表连接 | 多跳查询性能急剧下降。 | 按图模型建模，使用图数据库的多跳与路径语义。 |
| 关系没有方向与类型 | 查询语义含糊，结果不可解释。 | 为边定义类型与方向，并写清允许的路径模式。 |
| 入口属性没有索引 | 每次查询都全表扫描。 | 为高频入口属性建立索引并观察命中情况。 |
| 可变长度路径不设上限 | 路径数随跳数指数增长，查询超时。 | 显式写 `*1..3`，并限定边类型与方向。 |
| 用图库做全表聚合 | 遍历全部节点与边，延迟不可控。 | 聚合交给列式数仓或预计算。 |
| 忽略超级节点 | 单点展开百万条边，P99 飙升。 | 限定边时间窗、拆分节点或离线计算。 |
| 双向关系存成两条边 | 路径与计数翻倍，结果偏大。 | 用单条有向边表达语义，查询时按方向去重。 |

### 现场 1：把图查询当多表连接

**症状**：多跳查询性能急剧下降。

**根因与修复**：按图模型建模，使用图数据库的多跳与路径语义。

**自检**：在本课示例里复现「把图查询当多表连接」，改成按图模型建模，使用图数据库的多跳与路径语义后重跑；如果症状消失且失败路径按预期变化，说明定位正确。

### 现场 2：关系没有方向与类型

**根因与修复**：为边定义类型与方向，并写清允许的路径模式。

**自检**：在本课示例里复现「关系没有方向与类型」，改成为边定义类型与方向，并写清允许的路径模式后重跑；如果症状消失且失败路径按预期变化，说明定位正确。

### 现场 3：入口属性没有索引

**症状**：每次查询都全表扫描。

**根因与修复**：为高频入口属性建立索引并观察命中情况。

**自检**：在本课示例里复现「入口属性没有索引」，改成为高频入口属性建立索引并观察命中情况后重跑；如果症状消失且失败路径按预期变化，说明定位正确。
