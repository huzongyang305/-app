## 核心概念定义

| 术语 | 操作性定义 | 常见边界与风险 |
| --- | --- | --- |
| 应用范式 | 从「纯提示词直答」到「检索增强、工具编排、Agent 自主规划」的能力档位，决定系统的可控性与成本结构。 | 易错：范式越复杂越好，实际上档位越高调试成本和不可预期性越大。 |
| 协议兼容层 | 屏蔽各家 API 在字段命名、流式帧格式、工具消息结构上的差异，对上层只暴露一套接口的适配模块。 | 易错：把兼容层等同于 OpenAI SDK，各家仍有私有字段和限流口径需要单独处理。 |
| 上下文窗口 | 单次请求可容纳的输入与输出 Token 总量上限，由模型与服务端共同决定。 | 易错：窗口大就等于效果好，长上下文会同时推高成本并稀释关键证据。 |
| Token | 模型词表切分后的最小计费与生成单位，不等于汉字或英文单词。 | 易错：用字符数除以二当计费口径，中英混排和代码文本的偏差可达数成。 |
| 成本模型 | 以「输入 Token 单价 × 输入量 + 输出 Token 单价 × 输出量」为骨架，叠加缓存命中折扣与请求次数得到的预算式。 | 易错：只算模型调用费，漏掉嵌入、向量库存储、重试和评测的隐性开销。 |
| 首 Token 时延 | 从请求发出到收到第一个输出 Token 的等待时间，用户体感主要由它决定。 | 易错：用总耗时评价体验，长回答的总时延高但流式体验依然顺畅。 |
| 供应商切换 | 在保持提示词、评测集和接口契约不变的前提下，把推理请求迁移到另一家模型的过程。 | 易错：认为切换只需改模型名，实际要重验格式约束、限流阈值和安全策略。 |
| 评测基线 | 上线前用固定问题集测出的质量与成本快照，作为后续一切优化的对照物。 | 易错：换模型时只看几个人工印象题，没有回归集就无法证明质量没有退化。 |

## 原理与运行机制

### 机制总览：一次 LLM 应用请求的分层结构

一次看似简单的「提问—回答」，在工程上会穿过四层：交互层负责组织语言与呈现，编排层决定走哪条链路、调用哪些工具，模型接入层负责协议转换与重试，推理层决定用哪家托管或自部署的算力。选型的全部工作，本质是判断需求应该落在哪一层、以及每一层的预算是多少。

**教材衔接：四层职责划分**

| 层 | 典型职责 | 常见实现 | 选型的关注点 |
| --- | --- | --- | --- |
| 交互层 | 会话管理、引用展示、多轮状态 | Flutter Web、ChatUI 组件 | 流式渲染与失败重试的用户可见性 |
| 编排层 | 路由分流、工作流、工具调用 | 低代码平台、LangGraph、自研状态机 | 流程是否需要确定性可审计 |
| 模型接入层 | 协议转换、限流重试、密钥管理 | OpenAI 兼容 SDK、LiteLLM 类网关 | 换供应商时代码改动面 |
| 推理层 | 权重加载、批处理、量化 | 云端 API、vLLM、Ollama | 数据边界与单位 Token 成本 |

**教材衔接：协议兼容层的最小骨架**

兼容层的价值不在于封装得多薄，而在于把「差异」留在一个可以单独测试的地方。下面这段代码把供应商做成注册表，业务侧只认 `chat()` 一个入口，模型名和端点从环境变量注入，切换供应商时调用点一行都不用改。

```python
import os
from dataclasses import dataclass
from openai import OpenAI

@dataclass
class Vendor:
    key: str
    base_url: str
    model: str

VENDORS = {
    'deepseek': Vendor('deepseek', 'https://api.deepseek.com/v1', 'deepseek-chat'),
    'qwen': Vendor('qwen', 'https://dashscope.aliyuncs.com/compatible-mode/v1', 'qwen-plus'),
}

def chat(prompt: str, vendor: str = 'deepseek', system: str = '只用中文回答') -> str:
    v = VENDORS[vendor]
    client = OpenAI(api_key=os.environ[v.key.upper() + '_KEY'], base_url=v.base_url)
    resp = client.chat.completions.create(
        model=v.model,
        messages=[{'role': 'system', 'content': system},
                  {'role': 'user', 'content': prompt}],
    )
    return resp.choices[0].message.content

print(len(chat('用一句话说明 RAG 与微调的区别')))
```

**教材衔接：主流生态的差异要点**

| 生态 | 接入形态 | 结构差异 | 选型时要盯的点 |
| --- | --- | --- | --- |
| OpenAI | Chat Completions 与 Responses 双栈 | 流式以 DONE 帧收尾，工具结果用 tool 角色回填 | 长上下文档位的价格跳变与限流分级 |
| Anthropic | Messages 接口 | `max_tokens` 必填，工具调用是 content 里的 tool_use 块 | System 独立成字段而非消息 |
| DeepSeek | OpenAI 兼容端点 | 字段基本对齐，思考模式会额外返回推理内容 | 高峰期限流与缓存命中折扣 |
| 通义 / Kimi | 兼容模式加原生 SDK 双轨 | 长文档解析、联网检索等能力藏在私有参数里 | 上下文长度与多模态计入口径 |

**教材衔接：Token 与成本估算**

成本估算的可信度取决于分词口径。中文常见一个汉字切成一到两个 Token，代码和中英混排的膨胀更严重，所以预算必须以模型自带分词器的实测值为准，而不是靠字符数换算。

```python
def estimate(prompt_chars: int, completion_tokens: int, in_price: float, out_price: float, ratio: float = 1.6) -> float:
    # ratio：中文文本每字符平均消耗多少 Token，需用自己的分词器实测校准
    input_tokens = int(prompt_chars * ratio)
    return (input_tokens / 1_000_000) * in_price + (completion_tokens / 1_000_000) * out_price

# 单价按「元 / 百万 Token」填写
cost = estimate(prompt_chars=3000, completion_tokens=600, in_price=2.0, out_price=3.0)
print(round(cost, 4))
```

**教材衔接：供应商切换的四步执行流程**

切换不是改一个字符串，而是一次带证据的发布。先冻结评测集，再灰度放量，指标守住才逐步扩大比例，任何一步都能用一条命令回退。

```bash
# 1. 冻结基线：同一套问题集分别跑两家模型
promptfoo eval -c evals/chat.yaml --provider openai/deepseek-chat -o baseline.json
promptfoo eval -c evals/chat.yaml --provider openai/qwen-plus -o candidate.json
promptfoo compare baseline.json candidate.json

# 2. 按 5% 流量灰度，观察格式失败率与 P95 时延
export LLM_ROUTER_CANDIDATE_RATIO=0.05
# 3. 指标守住后逐步放大；触发回滚条件立即归零
export LLM_ROUTER_CANDIDATE_RATIO=0
```

## 典型应用场景

| 场景 | 典型输入或前提 | 期望产物 |
| --- | --- | --- |
| 企业内部问答助手 | 已有权限体系与文档库，答案必须可追溯引用 | 检索增强链路 + 引用展示 + 离线评测集 |
| 电商客服自动应答 | 话术固定、必须核查订单状态，错误代价高 | 工作流编排 + 订单查询工具 + 人工接管阈值 |
| 合同条款抽取 | 输入为长 PDF，输出要直接进业务数据库 | 结构化输出 + 字段校验 + 失败重试队列 |
| 营销文案批量生成 | 量大、单价敏感、允许少量人工复核 | 轻量模型 + 提示词模板 + 缓存复用 |

- 典型现象：把「客服核查订单」做成自由问答，模型会编造订单状态。正确做法：把状态查询固定为工具调用，模型不参与事实生成。
- 典型现象：换了更便宜的模型后账单不降反升。正确做法：先量输入 Token，长上下文场景的省钱手段是裁剪召回量而不是换单价。
- 典型现象：全量切换后格式解析报错率飙升。正确做法：灰度按流量比例放量，把结构化输出失败率设为回滚触发条件。

### 最小验证场景

- 准备：一份 50 条真实问题的问题集，两个可访问的模型端点，一个统一的调用入口函数。
- 观察：同一套提示词分别跑两个端点，记录三项数字——格式合规率、平均输入 Token、P95 总时延。
- 判定：候选端点的合规率不低于基线且单条成本下降超过 30%，才允许进入灰度；否则保留在兼容层里但不开流量。

## 代码/协议/SQL 示例

**教材衔接：把用量写进日志便于成本归因**

成本失控通常不是单价问题，而是没人知道钱花在哪个功能上。给每次调用打上业务标签，把 usage 三个字段原样落盘，一周后就能按功能聚合出账单结构。

```python
import json, time
from dataclasses import asdict

def record_call(feature: str, resp, started: float) -> None:
    row = {
        'feature': feature,
        'latency_ms': int((time.time() - started) * 1000),
        'prompt_tokens': resp.usage.prompt_tokens,
        'completion_tokens': resp.usage.completion_tokens,
        'total_tokens': resp.usage.total_tokens,
    }
    with open('usage.jsonl', 'a', encoding='utf-8') as f:
        f.write(json.dumps(row, ensure_ascii=False) + '\n')
```

**教材衔接：按功能聚合的账单查询**

有了逐次记录，用 SQL 就能定位钱花在哪里。下面的聚合口径与各家账单页一致，可以直接对着账单核对。

```sql
SELECT feature,
       COUNT(*)                          AS calls,
       SUM(total_tokens)                 AS tokens,
       SUM(prompt_tokens) * 1.0 / COUNT(*) AS avg_input
FROM usage_log
WHERE ts >= now() - INTERVAL '7 day'
GROUP BY feature
ORDER BY tokens DESC;
```

错误表现：把模型名写死在几十处业务代码里，切换时逐个搜索替换，漏改的那处在线上悄悄退回贵的模型。

```python
resp = client.chat.completions.create(model='gpt-4o', messages=msgs)   # 到处硬编码
```

正确写法：模型名从注册表或配置读取，调用点只关心「用哪一档能力」而不是具体型号。

```python
MODEL = os.environ['LLM_APP_MODEL']            # 单一入口，可按灰度覆盖
resp = client.chat.completions.create(model=MODEL, messages=msgs)
```

## 时间/空间复杂度或性能分析

| 维度 | 度量口径 | 典型量级 | 主要优化手段 |
| --- | --- | --- | --- |
| 首 Token 时延 | 请求发出到首个增量 | 数百毫秒到数秒 | 选低排队档位、缩短输入、开启流式 |
| 总生成时延 | 请求到最后一个 Token | 与输出长度近似线性 | 控制输出长度、提高批处理并发 |
| 单条成本 | 输入与输出 Token 分别计价 | 输入常占七成以上 | 裁剪上下文、缓存高频问答 |
| 吞吐 | 单位时间完成请求数 | 受服务端限流约束 | 并发池加令牌桶、离线批处理 |
| 空间 | 上下文与向量库规模 | 上下文按窗口上限，向量按条数乘维度 | 摘要压缩、分层存储、量化向量 |

选型阶段的性能分析重点是三个「乘积关系」。第一，总成本约等于请求数乘平均输入 Token，而输入量通常远大于输出量，所以裁剪召回片段的收益最大；第二，用户体感时延约等于首 Token 时延加上输出长度除以解码速度，换更小的模型主要改善后者，对流式场景的观感提升有限；第三，并发上限受制于服务端限流而不是客户端线程数，把并发开大只会换来更多 429。

上下文窗口是另一条容易被忽视的隐性成本曲线。多数供应商按输入长度分档计价，窗口越长的档位单价越高；同时长上下文会让模型对中间证据的注意力下降，召回十条和召回三条的效果差异经常大于模型之间的差异。因此「窗口有多大就用多大」在工程上几乎总是错的。

评测基线本身也有成本。一次覆盖 500 条问题、跑三个模型的离线评测，Token 消耗可能超过一周的线上流量。合理做法是把评测集分层：冒烟层几十条用于每次改动，回归层数百条用于发布前，深度层用于季度选型。

## 常见误区与易错点

- **范式越先进越好。** 提示词直答能解决的问题，套上 Agent 只会增加时延、成本和不可解释性；档位选择的依据是「流程是否需要确定性」。
- **换模型只改模型名。** 兼容层统一的是传输结构，格式约束强度、限流阈值、安全策略和内容过滤都不同，必须重跑回归集。
- **用字符数估算 Token。** 中文、代码和中英混排的膨胀系数差别很大，不用对应分词器实测的预算会在真实账单上失配。
- **把上下文塞满。** 长窗口不等于高准确率，稀释关键证据的同时按输入量翻倍付费。
- **只统计成功调用。** 重试和超时同样计费，成本口径要按「发出的请求」而不是「完成的请求」。
- **忽略嵌入与存储费用。** 向量库的条数、维度和副本数都是长期开销，重建索引还要重跑嵌入。
- **用几个人工印象题选型。** 没有固定问题集和指标，结论会随最近一次对话的好坏摆动。
- **把兼容层做成万能抽象。** 抽象越少越稳，只封装真正需要的三五个参数，其余通过透传字典保留逃生口。
- **一次性全量切换。** 没有灰度和回滚阈值的切换等同于线上事故，失败率与成本都要设自动止损线。

## 自测题与参考答案

**教材衔接：题号 1** — 把供应商 A 的模型换成供应商 B 时，让代码改动最小的做法是？

**参考答案**：在兼容 OpenAI 协议的抽象层统一接入。

本题正确项是「在兼容 OpenAI 协议的抽象层统一接入」。主流厂商都提供与 Chat Completions 对齐的端点，把 base_url、api_key、model 三个参数抽成配置后，切换供应商只改环境变量而不改业务代码，测试用例也能原样复用。逐家重写 SDK 会让调用点散落各处，只改提示词并不消除协议差异，让前端拼请求体还会把密钥和重试逻辑暴露在客户端。

**教材衔接：题号 2** — 估算一次调用的输入 Token 费用时，中文长文本应按哪个口径折算？

**参考答案**：按实际分词后的 Token 数统计。

本题正确项是「按实际分词后的 Token 数统计」。计费单位是各家词表切出来的 Token，中文常见一个汉字对应一到两个 Token，但中英混排、标点和代码的切分结果差别很大，只能用对应模型的分词器实测。字符数除以二只适合粗筛量级，乘二和字节数与计费口径无关，用来做预算会在中英混排场景严重偏离真实账单。

**教材衔接：题号 3** — 客服机器人要按固定话术核查订单状态，最贴合的应用范式是？

**参考答案**：工作流编排加工具调用。

本题正确项是「工作流编排加工具调用」。固定话术加确定性核查属于流程受限任务：用节点化工作流约束分支，用工具查订单接口拿事实，模型只负责语言组织，可审计也能回归测试。纯 RAG 只解决知识检索不解决流程控制，自由生成与纯角色扮演会让话术和字段校验失去约束，容易在关键节点漏查或错答。

**教材衔接：题号 4** — 供应商合同要求下季度降本，应用侧最省事的应对手段是？

**参考答案**：把模型名做成可配置项灰度切换。

本题正确项是「把模型名做成可配置项灰度切换」。当调用层已经抽象到统一协议，降本只要按流量比例把更便宜的模型灰度放量，用离线评测守住质量红线，随时可回滚。重写提示词模板推高人力成本且与单价无关，换前端框架不减少推理开销，全量改离线批处理则牺牲实时应答，对客服类场景并不成立。

**教材衔接：题号 5** — 下面代码读取一次非流式响应的用量字段，最后一行打印的是？
from openai import OpenAI
client = OpenAI()
resp = client.chat.completions.create(
  model='deepseek-chat',
  messages=[{'role': 'user', 'content': '一句话解释 KV Cache'}],
)
print(resp.usage.prompt_tokens, resp.usage.total_tokens)

**参考答案**：输入 Token 数与总 Token 数。

本题正确项是「输入 Token 数与总 Token 数」。usage 里的 prompt_tokens 是本次输入的 Token 量，total_tokens 是输入加生成量的合计，两个字段都来自服务端返回的计费口径，SDK 只是映射成属性。输出量对应 completion_tokens 而不是 total_tokens，请求耗时和字节数 SDK 并不提供，只能自己在客户端打点统计。

## 考点精讲

**教材衔接：高频考点**

1. 应用范式分档与选型依据：判断需求属于直答、检索、编排还是自主规划，是全部工程决策的第一步。
2. 协议兼容层的边界：哪些差异必须屏蔽、哪些应该透传，决定切换供应商的实际改动面。
3. Token 计费口径：输入与输出分别计价、按分词器实测估算，是成本类题目的通用出题点。
4. 供应商切换流程：冻结基线、灰度放量、设回滚阈值三段式，是运维类场景的标准答案。

**教材衔接：命题规律**

- 概念题偏爱考「范式与场景的匹配」，正确项通常包含可审计、可回归这类限定词。
- 计算题给字符数、Token 系数和两个单价，要求算出总费用，考察是否区分输入与输出。
- 排错题常描述「账单不降」或「格式报错率上升」，答案指向上下文裁剪与灰度阈值而非换模型。

**教材衔接：常见考点**

问：把供应商 A 的模型换成供应商 B 时，让代码改动最小的做法是？

问：估算一次调用的输入 Token 费用时，中文长文本应按哪个口径折算？

## 术语速查

| 术语 | 一句话说明 |
| --- | --- |
| 应用范式 | 从提示词直答到 Agent 自主规划的能力档位，决定可控性与成本结构。 |
| 协议兼容层 | 把各家 API 的字段与流式差异收敛到一处、对上层只暴露一套接口。 |
| Token | 模型词表切分出的最小计费与生成单位，不等于字符或单词。 |
| 上下文窗口 | 单次请求输入与输出 Token 的总上限，越长越贵且会稀释证据。 |
| 首 Token 时延 | 请求到第一个输出增量的等待时间，是流式体验的主要决定因素。 |
| 成本模型 | 输入输出分别计价再乘请求量的预算式，需叠加重试与存储开销。 |
| 灰度切换 | 按流量比例逐步放量并设自动回滚阈值的模型替换方式。 |
| 评测基线 | 上线前固化的质量与成本快照，用来证明后续改动没有退化。 |
