## 原理与运行机制

### 机制总览

**教材衔接：一句话目标**

让每一次改动都**小、可理解、可回滚**，这样代码评审、排障与协作才不会失控。

**教材衔接：一张图看懂完整工作流**

```text
拉取最新主干
   │
   ▼
建特性分支（命名：feat/order-export）
   │
   ▼
┌─────────────────────────────┐
│ 循环：写代码 → 本地测试 → 提交 │
│  · 每次提交只做一件事         │
│  · 提交信息写清「为什么」     │
└─────────────────────────────┘
   │
   ▼
推送并开 PR（描述：改了什么、为什么、怎么验证）
   │
   ▼
CI 通过 + 至少一人评审
   │
   ▼
合并到主干（squash 或 rebase，保持线性）
   │
   ▼
删除分支，回到主干拉最新
```

**教材衔接：提交粒度：多大的改动最合适**

| 规模 | 评审效果 | 说明 |
| --- | --- | --- |
| < 200 行 | 最佳 | 半小时内能看完 |
| 200~500 行 | 可接受 | 需要写清背景 |
| > 500 行 | 明显变差 | 应拆分 |
| > 1000 行 | 基本无效 | 评审变成走过场 |

**拆分的三种方式**：

1. 按行为拆：先加数据结构，再加接口，最后接界面。
2. 按层次拆：先重构（不改行为），再加功能。
3. 按开关拆：先合并「不生效的代码」，再用开关开启。

**教材衔接：分支策略：三种够用即可**

| 策略 | 适合 | 说明 |
| --- | --- | --- |
| 主干开发 + 短分支 | 大多数团队 | 分支活不过两三天 |
| Git Flow | 有明确发布窗口 | 分支多，成本高 |
| Trunk + 发布标签 | 持续部署 | 主干永远可发布 |

**共同要点**：分支存活时间越短，合并冲突越少。

### 机制拆解：每一步的输入、动作与输出

#### 1. `提交`
- 输入：`Git`；本步把 第 1 次提交：加数据表与迁移脚本（不改变对外行为） 当作判断规则。
- 动作：围绕 `提交` 保留中间状态，并记录它与 `代码评审` 的对应关系。
- 输出：`代码评审`，它可以被下一段代码、测试或记录继续使用。
- `提交` 的失败条件：当混装多件事时，会出现一次提交里既有重构又有新功能。

#### 2. `代码评审`
- 输入：`提交`；本步把 在合并前由他人检查改动的正确性、可维护性、安全性与测试覆盖 当作判断规则。
- 动作：围绕 `代码评审` 保留中间状态，并记录它与 `分支策略` 的对应关系。
- 输出：`分支策略`，它可以被下一段代码、测试或记录继续使用。
- `代码评审` 的失败条件：权限与密钥策略变化会让结论失效，按最小权限并用真实凭据流程复验。

#### 3. `分支策略`
- 输入：`代码评审`；本步把 约定主干、特性分支与发布分支各自的职责，决定合并方式与回滚成本 当作判断规则。
- 动作：围绕 `分支策略` 保留中间状态，并记录它与 `原子提交` 的对应关系。
- 输出：`原子提交`，它可以被下一段代码、测试或记录继续使用。
- `分支策略` 的失败条件：隔离级别与并发事务会影响可见性，换级别或换存储引擎后要重新验证。

#### 4. `原子提交`
- 输入：`分支策略`；本步把 一次提交只做一件事并且能独立通过测试，出问题时可以安全回退 当作判断规则。
- 动作：围绕 `原子提交` 保留中间状态，并记录它与 `PR` 的对应关系。
- 输出：`PR`，它可以被下一段代码、测试或记录继续使用。
- `原子提交` 的失败条件：隔离级别与并发事务会影响可见性，换级别或换存储引擎后要重新验证。

#### 5. `PR`
- 输入：`原子提交`；本步把 Pull Request，把一组分支改动提交评审、自动检查和合并的协作单元 当作判断规则。
- 动作：围绕 `PR` 保留中间状态，并记录它与 `本课示例的最终结果` 的对应关系。
- 输出：`本课示例的最终结果`，它可以被下一段代码、测试或记录继续使用。
- `PR` 的失败条件：当在主干直接改时，会出现随时可能不可发布。

### 复现实验记录

- 环境：`编码工作流：小步提交与可评审的改动` 使用 `text` 示例，固定 `Git`、`提交`、`分支`、`代码评审` 作为第一组条件。

- 基线观察：记录命令、输入、输出和错误原文，不用截图代替可复制的文本。
- 单变量修改：只改变 `Git`，观察 `PR` 是否仍满足定义。
- 失败注入：复现 只写动作，确认现象是 `update code`。

## 典型应用场景

**教材衔接：项目专属规格：编码工作流：小步提交与可评审的改动**

### 核心场景

分支策略、提交粒度、提交信息、评审清单与回滚友好的交付节奏。 项目目标是把「Git、提交、分支、代码评审、小步交付」落实为可运行、可测试、可回滚的交付物。



### 验收场景

1. 正常路径：最小输入得到预期输出，并留下日志与指标。
2. 边界路径：Git 的空值、最大值、重复数据和超长内容都得到明确处理。
3. 失败路径：依赖超时或不可用时能快速失败、重试或降级。
4. 幂等路径：同一请求执行两次不会产生重复副作用。
5. 回滚路径：提交 的失败能按预案恢复，并记录影响范围。

- 使用 `原子提交` 时，先满足它的定义：一次提交只做一件事并且能独立通过测试，出问题时可以安全回退；隔离级别与并发事务会影响可见性，换级别或换存储引擎后要重新验证。

**教材衔接：提交信息的写法**

```text
类型(范围): 一句话说明做了什么

为什么这么改（背景与原因）

怎么验证（命令、结果、截图）

```

```text

```

| 类型 | 用途 |
| --- | --- |
| `feat` | 新功能 |
| `fix` | 修缺陷 |
| `refactor` | 不改行为的重构 |
| `perf` | 性能优化 |
| `docs` | 文档 |
| `test` | 测试 |
| `chore` | 构建与杂项 |

**教材衔接：代码评审：作者与评审者各有清单**

作者自查：

```text
□ 改动是否只做了一件事
□ 是否补了测试，失败路径是否覆盖
□ 是否更新了文档与配置说明
□ 是否自测过（给出命令与结果）
□ 是否清理了调试代码与日志
```

评审者关注：

```text
□ 正确性：边界、异常、并发
□ 可读性：命名、结构、注释是否解释「为什么」
□ 安全性：输入校验、权限、密钥
□ 性能：循环里的 IO、N+1 查询
□ 可测试性：是否依赖全局状态
```

**评审对事不对人**：评论写「这里在并发下会重复扣款，建议加唯一约束」，而不是「你写错了」。

**教材衔接：一次典型的小步交付**

```text
第 1 次提交：加数据表与迁移脚本（不改变对外行为）
第 2 次提交：加仓储方法 + 单元测试
第 3 次提交：加接口 + 参数校验 + 接口测试
第 4 次提交：加界面开关（默认关闭）
第 5 次提交：打开开关并观察监控
每个提交都可单独回滚，出问题只回滚一步
```

**教材衔接：补充：让评审真正发现问题的做法**

### 一次改动怎么拆成多个可评审的提交

```text
目标：给订单接口增加「按时间范围导出」

提交 1  加查询参数与数据层方法（不改对外行为）
        └─ 单测覆盖参数解析与边界
提交 2  接口接入新参数并返回结果
        └─ 接口测试覆盖缺省值（保持原行为）
提交 3  加权限校验与导出上限（防止一次导出全表）
        └─ 测试覆盖越权与超限
提交 4  更新接口文档与变更日志

每个提交都能单独通过 CI、单独回滚
```

**拆分依据有三条**：按行为、按层次、按开关。任选其一，但不要在一个提交里混合「重构 + 新功能 + 格式化」。

### PR 描述模板

```markdown
## 改了什么
订单接口支持按 start/end 导出，缺省时保持原行为。

## 为什么
运营需要按月对账，之前只能导出全部数据。

## 怎么验证
```

### 考点 7：`提交`

- **要点**：第 1 次提交：加数据表与迁移脚本（不改变对外行为）。
- **提交 的边界**：易错：一次提交里既有重构又有新功能；正确做法是拆成多次提交。

### 考点 8：`代码评审`

- **要点**：在合并前由他人检查改动的正确性、可维护性、安全性与测试覆盖。
- **代码评审 的边界**：权限与密钥策略变化会让结论失效，按最小权限并用真实凭据流程复验。

### 考点 9：`分支策略`

- **要点**：约定主干、特性分支与发布分支各自的职责，决定合并方式与回滚成本。
- **分支策略 的边界**：隔离级别与并发事务会影响可见性，换级别或换存储引擎后要重新验证。

### 考点 10：`原子提交`

- **要点**：一次提交只做一件事并且能独立通过测试，出问题时可以安全回退。
- **原子提交 的边界**：隔离级别与并发事务会影响可见性，换级别或换存储引擎后要重新验证。

### 考点 11：`PR`

- **要点**：Pull Request，把一组分支改动提交评审、自动检查和合并的协作单元
- **PR 的边界**：易错：随时可能不可发布；正确做法是走分支加 PR。

### 考点 12：排错——只写动作

- **现象**：`update code`。
- **处理**：`feat(order): 支持按时间范围导出`。

### 考点 13：排错——混装多件事

- **现象**：一次提交里既有重构又有新功能。
- **处理**：拆成多次提交。

### 考点 14：综合辨析——`提交` 与 `PR`

- **辨析点**：`提交` 的定义是 第 1 次提交：加数据表与迁移脚本（不改变对外行为）；`PR` 的定义是 Pull Request，把一组分支改动提交评审、自动检查和合并的协作单元。
- **答题要求**：面对 `编码工作流：小步提交与可评审的改动` 的题目，先判断描述的是 `提交` 还是 `PR`，再归到对应定义，最后写出一个会让该定义失效的边界输入。

### 考点 15：排错评分点

- **现象分**：能写出 `update code`，而不是只写“程序有错”。
- **证据分**：保留触发 只写动作 的输入、版本和错误原文。
- **修复分**：按 `feat(order): 支持按时间范围导出` 只改一处，并同时回归正常路径与边界路径。
