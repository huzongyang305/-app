## 本节知识框架

**课程定位**：所属分类 `llm_apps`（LLM 应用开发），课程主题 `综合项目：企业知识库助手`，学习阶段 应用，建议用时 60 分钟。

本课主线：以一份真实需求为起点走完一遍工程闭环，先做需求拆解与可接受错误率的约定，再做架构选型与组件切分，随后实现检索、路由与工具三类能力，最后补齐上线运维与效果调优两条收尾线。

**学完本课应当能够**

- 把「员工问制度」这类模糊需求拆成可验收的问题分类与指标目标，并识别高风险问题清单。
- 在纯检索问答、GraphRAG、工作流三类方案之间做出选型，说明被放弃方案的代价。
- 独立完成一次上线后的成本与质量联合调优，并给出可复现的验证命令与预期输出。

## 核心概念定义

| 术语 | 操作性定义 | 常见边界与风险 |
| --- | --- | --- |
| 需求基线 | 与需求方共同确认的问题分类、指标与例外清单。 | 易错：只收集样例问题，不约定错误率上限。 |
| 问题分类 | 把提问划为事实查询、流程推理、超范围三类。 | 易错：分类边界含糊，路由准确率无从评估。 |
| 摄取管道 | 文档从来源到可检索状态的同步链路。 | 易错：只做全量重建，增量与删除长期不生效。 |
| 检索层 | 混合召回加重排，输出带来源的片段。 | 易错：只调向量不看元数据过滤条件。 |
| 路由 | 按问题类型分派到不同处理链路。 | 易错：路由用一个大模型自由判断，无稳定输出。 |
| 引用 | 回答里指向原文位置的可点击凭据。 | 易错：引用与内容不匹配，比不引用更伤信任。 |
| 反馈闭环 | 点赞点踩与人工复核回流到评测集。 | 易错：只存不分析，坏例子永远进不了回归。 |
| 运行手册 | 故障定位、降级与回滚的操作说明。 | 易错：写完不演练，真出事时无人能用。 |

## 原理与运行机制

### 机制总览：从需求到验收的推进顺序

正确的推进顺序是：先定「什么叫好」，再定架构，最后写实现。多数失败项目的原因是反过来，先做了检索链路，再去问业务「这样算准吗」，此时改架构的成本已经付不起了。

**教材衔接：需求拆解表**

| 问题类型 | 占比 | 期望时延 | 处理链路 | 不可接受错误 |
| --- | --- | --- | --- | --- |
| 条款原文查询 | 45% | 3 秒 | 混合检索加抽取式回答 | 引用错条款 |
| 跨部门流程推理 | 30% | 8 秒 | 工作流多步推理 | 给出已废止流程 |
| 个人数据相关 | 15% | 2 秒 | 转专用系统与人工 | 泄露他人信息 |
| 超范围与攻击 | 10% | 1 秒 | 直接拒答并说明边界 | 编造答案 |

「可接受错误率」必须与需求方一起写进基线。制度类问答里，编造一条不存在的报销上限，与把报销上限说错一个数字，风险等级完全不同，前者应设为零容忍并触发强制拒答。

**教材衔接：架构选型的三方案对照**

| 方案 | 优势 | 代价 | 本项目判断 |
| --- | --- | --- | --- |
| 全部自由生成问答 | 实现最快 | 流程类问题失控、引用难保证 | 否 |
| 统一走图检索 | 关系推理强 | 索引构建重、条款类问题无收益 | 否 |
| 路由分流到检索问答与工作流 | 各链路各按其类 | 需维护分类器与两条链路 | 采用 |

一半问题需要跨部门流程推理、一半只需查条款原文时，统一走任一极端方案都会牺牲另一半。路由分流的代价是多一个分类节点，收益是两条链路都能各自调到最优。

**教材衔接：路由节点的实现**

```python
def route(label: str) -> str:
    return 'workflow' if label in ('multi_step', 'approval_chain') else 'rag'

print(route('multi_step'), route('clause_lookup'))
```

分类节点必须输出受约束的标签集合，而不是自由文本。否则下游要为每一种可能的表述写兼容逻辑，路由本身反而成了最不稳定的一环。

**教材衔接：摄取管道的增量策略**

文档更新后仍返回旧政策，几乎总是出在这一层。可靠做法是给每份文档记录来源指纹与版本，写入时按指纹判断新增、更新还是删除，并在索引层保留可回溯的文档号。

| 环节 | 触发 | 失败表现 | 保护措施 |
| --- | --- | --- | --- |
| 抓取 | 定时或事件 | 权限变更拉不到 | 拉取失败告警加保留旧版 |
| 切块 | 内容变化 | 表格被切断 | 结构感知切块加长度上限 |
| 嵌入 | 新块产生 | 模型换型后混用 | 全量重建并打版本标签 |
| 入库 | 嵌入完成 | 新旧块同时命中 | 按文档指纹做 upsert 与删除 |
| 生效 | 入库成功 | 缓存仍返回旧片段 | 检索侧带版本号过滤 |

**教材衔接：一次问答的时序**

请求进入后依次经过输入护栏、问题分类、路由、检索、重排、生成、引用校验、输出护栏，最后异步落追踪与反馈存储。任一步失败都要有明确去向：检索为空走「未找到」话术而不是硬编，生成超时切到降级端点，引用校验不通过则撤回回答并记一次缺陷。

| 阶段 | 耗时预算 | 失败去向 |
| --- | --- | --- |
| 输入护栏 | 80 毫秒 | 直接拒答并说明边界 |
| 分类与路由 | 400 毫秒 | 兜底走条款检索链路 |
| 检索与重排 | 700 毫秒 | 返回未找到话术 |
| 生成 | 2100 毫秒 | 切换降级端点重试一次 |
| 引用与输出护栏 | 120 毫秒 | 撤回回答并转人工 |

## 典型应用场景

| 场景 | 关键设计 | 验收方式 |
| --- | --- | --- |
| 制度与流程问答 | 引用必带条款号 | 抽检引用与原文一致性 |
| 入职手续引导 | 工作流收集缺失字段 | 完成率与人工介入率 |
| 系统操作求助 | 截图与步骤库检索 | 一次解决率 |
| 合规红线咨询 | 高风险清单直接转人工 | 零自动回答率检查 |
| 数据类查询 | 走只读接口与工具调用 | 参数校验通过率 |

- 典型现象：上线两周后成本翻倍而质量不变。正确做法：先看平均输入体积是否被更长的上下文撑大，再看是否有渠道刷量。
- 典型现象：问答质量波动大且无法复现。正确做法：检查是否遗漏了提示词版本与检索参数的落库，无版本就无法对比。
- 典型现象：用户抱怨「答得对但没答完」。正确做法：把最大输出长度与分点模板写进规格，并在断言里检查要点覆盖。

### 最小验证场景

- 准备：八十条真实脱敏问题，覆盖四类问题类型，每条标注标准条款号与可接受话术。
- 观察：分类准确率、检索命中率、忠实度、引用正确率、P95 端到端时延、单次成本六项。
- 判定：见下节验证命令表；任一项不达门槛即阻断发布，并回到对应链路而不是全局调参。

## 代码/协议/SQL 示例

**教材衔接：检索结果的最小记录结构**

```python
def pack(doc, score, q):
    return {'qid': q['id'], 'doc_id': doc['doc_id'], 'ver': doc['ver'],
            'score': round(score, 4), 'clause': doc.get('clause')}

hit = pack({'doc_id': 'hr-12', 'ver': 3, 'clause': '4.2'}, 0.812, {'id': 'q-7'})
print(hit['clause'], hit['ver'])
```

**教材衔接：效果与成本的联合看板**

```sql
SELECT week,
       ROUND(100.0 * SUM(hit) / SUM(req), 1)      AS hit_rate,
       ROUND(AVG(faithfulness), 3)                AS faith,
       ROUND(AVG(cost_cents), 2)                  AS cost,
       ROUND(MAX(p95_ms) / 1000.0, 2)             AS p95_s
FROM weekly_stats
WHERE tenant = 'hr-bot'
GROUP BY week
ORDER BY week DESC
LIMIT 12;
```

**教材衔接：容量与延迟的粗略核算**

```python
import time
lat = [0.9, 1.2, 2.5, 3.1, 4.0]
lat.sort()
p95 = lat[int(0.95 * len(lat)) - 1]
print(round(p95, 1))
```

这条脚本给出的是分位延迟而不是平均值，用它做发布门槛才能捕捉尾部体验劣化。生产上应使用完整分位估计，样本量低于两百条时分位数本身不可信。

**教材衔接：高风险问题清单的硬闸口**

```python
import re
BLOCK = re.compile(r'(裁员|薪酬带宽|劳动仲裁)')
```

### 项目专属规格

- 语料规格：来源限定为人力制度、流程手册与 FAQ 三个库；单文档上限 300KB，超过必须拆分。
- 切块规格：目标 800 字符、重叠 100 字符，以条款号为边界优先切断，表格逐行转文本。
- 检索规格：BM25 与向量各召回 12 条，融合后取 20 条送重排，重排输出 4 条，相似度阈值 0.34。
- 生成规格：温度 0.2，最大输出 900 Token，必须逐点回答并附条款号引用。
- 指标门槛：忠实度均值不低于 0.90 且最低不小于 0.86；引用正确率 1.00；高风险问题自动回答率 0。
- 性能规格：条款查询 P95 端到端不高于 3 秒，流程推理不高于 8 秒，可用性 99.5%。
- 成本规格：单次请求平均成本不高于基线 1.15 倍，超限触发上下文压缩与缓存评审。
- 数据规格：出站请求体不得含手机号、邮箱与工号；反馈数据保留 180 天后匿名化归档。

### 项目交付物

- 一套可重复运行的摄取与索引管道，含增量同步、删除回收与文档版本标签。

## 时间/空间复杂度或性能分析

| 指标 | 随什么增长 | 典型区间 | 优化手段 |
| --- | --- | --- | --- |
| 全量重建耗时 | 文档数与嵌入调用 | 线性且受网络限 | 增量同步加分批并发 |
| 检索时延 | 召回条数与是否重排 | 重排占大头 | 先粗召回再小集合精排 |
| 生成时延 | 输入体积与输出长度 | 输入影响预填充 | 压缩上下文、限制输出 |
| 单次成本 | 输入 Token 为主导 | 与块数近似线性 | 减少无效块、缓存高频问答 |
| 索引体积 | 块数乘向量维度 | 与语料同阶 | 量化向量或分层索引 |

成本优化的第一杠杆几乎总是输入体积，而不是换更便宜的模型。把重排输出从 6 条压到 4 条、把每块长度从 1200 降到 800，通常能在质量几乎不变的前提下降两三成成本。第二杠杆是缓存：制度类问题高度重复，命中缓存直接省掉整条链路的开销。

质量与成本之间存在明确的交换曲线。相似度阈值从 0.30 提到 0.34 会减少噪声块、降低成本，但可能让长尾问题召不到内容而触发「未找到」。正确做法是把阈值纳入回归门禁一起测，看整体分布而不是单条样例。

延迟指标要用分位而不是均值。条款查询的平均 1.5 秒若伴随 P95 六秒，用户感知依然是「偶尔很慢」。发布门槛应同时约束均值与分位，并对超出者留下可定位的追踪记录。

## 常见误区与易错点

- **先做技术再问标准。** 没有可接受错误率，任何指标都无所谓好坏。
- **把所有问题塞进一条链路。** 流程推理与条款查询的正确解法不同，混做两边都不达标。
- **摄取管道只做全量。** 增量与删除不生效，用户必然拿到过期政策。
- **换嵌入模型不重建索引。** 新旧向量混用会让相似度失去可比性。
- **路由用自由文本判断。** 输出不可控，下游被迫写大量兼容分支。
- **引用只写文档名不写条款号。** 无法核验，用户也无法跳转。
- **只看平均延迟。** 尾部劣化才是投诉来源，必须记分位。
- **成本看板没有版本维度。** 涨了却不知道是哪次改动导致，无法回滚决策。
- **反馈只存不回流。** 点踩样本不进评测集，同一错误反复出现。
- **运行手册不演练。** 真正故障时无人能在压力下读懂，等于没有手册。
- **把提示词当配置项随手改。** 无版本、无回归，质量漂移无法归因。

## 自测题与参考答案

**教材衔接：题号 1** — 企业知识库助手上线前，最该先和需求方敲定的是？

**参考答案**：可接受错误率与高风险问题清单。

本题正确项是「可接受错误率与高风险问题清单」。知识库助手的价值边界由答错的代价决定，先明确哪些领域宁可不答、可接受的错误比例是多少，才能反推检索深度、引用要求和人工接管阈值。配色、分支规范和采购型号都是执行细节，没有质量底线时讨论它们只会让验收标准变成主观印象。

**教材衔接：题号 2** — 问答里一半问题需要跨部门流程推理，一半只需查条款原文，架构上合理的方案是？

**参考答案**：路由分流到检索问答与工作流。

本题正确项是「路由分流到检索问答与工作流」。条款查询用混合检索加引用即可，跨部门推理需要步骤化编排和工具校验，用一个意图路由把两类请求分发到不同链路，能同时保住成本与质量。全部自由生成会放大幻觉，只用关键词检索会漏掉改写，统一走重型方案让简单问题付出成倍延迟。

**教材衔接：题号 3** — 上线后指标显示答案质量稳定但成本翻倍，优先做的调优是？

**参考答案**：压缩上下文并缓存高频问答结果。

本题正确项是「压缩上下文并缓存高频问答结果」。成本主要来自输入 Token 与重复请求，收紧召回数量、做片段级摘要并按问题哈希缓存高频答案，可以在不损失质量的前提下直接削减调用量。换更大模型会增加单价，取消引用牺牲可验证性，改一次性返回只影响首字延迟而对 Token 消耗没有帮助。

**教材衔接：题号 4** — 知识库文档更新后仍然返回旧政策，最先检查的是？

**参考答案**：摄取管道的增量同步是否生效。

本题正确项是「摄取管道的增量同步是否生效」。文档改了而检索结果没变，说明索引侧的数据没有更新，应检查抓取任务、分块与写入库的增量流程和删除标记是否遗漏。前端缓存与提示词措辞都可能干扰观感，但真正决定内容新旧的是索引数据；温度只影响采样随机性，不能刷新知识来源。

**教材衔接：题号 5** — 下面这段压测汇总脚本打印的数字代表什么？
import time
lat = [0.9, 1.2, 2.5, 3.1, 4.0]
lat.sort()
p95 = lat[int(0.95 * len(lat)) - 1]
print(round(p95, 1))

**参考答案**：约 3.1 秒的 P95 延迟。

本题正确项是「约 3.1 秒的 P95 延迟」。排序后用样本数乘分位系数再减一取下标，五个数得到下标 3，对应升序第四个数 3.1，即这组样本的近似高分位延迟。平均值要除以样本数而不是按下标取，最大值会直接落在末位的 4.0，首 Token 时延需要另外打点，与整体延迟口径不同。

## 考点精讲

**教材衔接：高频考点**

1. 上线前最先与需求方敲定的是可接受错误率与高风险问题清单。
2. 混合型问题占比下，路由分流到检索问答与工作流是合理的架构折中。
3. 质量稳定而成本翻倍时，优先压缩上下文并缓存高频问答。
4. 文档更新后返回旧内容，第一排查项是摄取管道的增量同步是否生效。

**教材衔接：命题规律**

- 项目题偏爱问「最该先」与「最先检查」，正确项指向根因层而非表层修补。
- 架构选型题给出明确占比或约束，排除绝对化表述如「统一走某方案以简化实现」。
- 压测脚本题给一小段延迟数组，问输出对应的统计含义，考察分位与均值的区分。
