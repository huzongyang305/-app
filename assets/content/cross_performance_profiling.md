## 原理与运行机制

### 机制总览

**教材衔接：一句话说清**

性能优化只有一条正确路径：**先测量、再定位、改一处、复测**。
各生态的工具名字不同，但「采样剖析 + 基准测试」这两件事完全一致。

**教材衔接：一张图看懂剖析流程**

```text
① 明确指标：延迟？吞吐？内存？启动时间？
        │
        ▼
② 建立基线：用基准测试记录当前数字
        │
        ▼
③ 采样剖析：找出热点函数（占时间最多的）
        │
        ▼
④ 形成假设：例如「热点在 JSON 解析」
        │
        ▼
⑤ 改一处 → 复测同一基准 → 对比数字
        │
        ├─ 变快 → 保留，更新基线
        └─ 没变 → 回退，回到第 ③ 步
```

**一次只改一个变量**，否则无法判断是哪一个改动带来的效果。

**失败路径（来自本课错误表）**
- 基准不做预热 → 首次运行包含编译与缓存冷启动，数据偏高 → 先预热固定轮次，再统计中位数与波动。
- 只测一个规模 → 复杂度拐点被单点数据掩盖 → 至少测三档规模，观察增长趋势再下结论。
- 只看平均耗时 → 尾延迟问题被平均值掩盖 → 同时记录 P95/P99、分配量与 CPU 占用。

## 典型应用场景

- **基准不做预热**：典型现象是首次运行包含编译与缓存冷启动，数据偏高；正确做法是先预热固定轮次，再统计中位数与波动。
- **只测一个规模**：典型现象是复杂度拐点被单点数据掩盖；正确做法是至少测三档规模，观察增长趋势再下结论。
- **只看平均耗时**：典型现象是尾延迟问题被平均值掩盖；正确做法是同时记录 P95/P99、分配量与 CPU 占用。

| Shell | `time` / `hyperfine` | hyperfine | 无 |

**教材衔接：基准测试的五条纪律**

```text
1. 多次运行取统计值，别只看一次（-count=5 或 --warmup）
2. 先预热：JIT 与缓存会让前几次偏慢
3. 隔离变量：同一台机器、同一负载、同一数据规模
4. 报告分位数：P50 / P95 / P99，而不是只看平均
5. 同时看内存：分配次数比耗时更容易暴露问题
```

| 现象 | 常见根因 | 对策 |
| --- | --- | --- |
| CPU 高但吞吐不涨 | 频繁上下文切换 | 减少线程数或改异步 |
| 延迟毛刺 | GC / 锁竞争 | 调 GC 参数、拆锁 |
| 内存持续增长 | 缓存无上限或泄漏 | 加容量限制、查引用 |
| 启动慢 | 初始化过多 | 延迟初始化、并行加载 |
| 单次调用慢 | 缺少索引或网络往返 | 加索引、批量合并 |
| 大量小对象 | 每次都新建 | 复用或池化 |

**教材衔接：补充：基准测试的统计严谨性与性能门禁**

### 各生态的成熟基准工具

| 语言 | 工具 | 它会自动处理 |
| --- | --- | --- |
| Java | JMH | 预热轮次、JIT、死代码消除 |
| Rust | Criterion | 统计显著性、离群值、回归检测 |
| C++ | Google Benchmark | 迭代次数自适应、最小耗时统计 |
| Go | `testing.B` | `b.N` 自动放大、`-benchmem` 统计分配 |
| Python | pytest-benchmark | 预热、多轮、标准差 |

```text
① 采样剖析（perf、py-spy、async-profiler）
   回答：时间花在哪些函数上

② 差异剖析（pprof -diff_base、JFR 对比）
   回答：这次改动让哪个函数变慢/变快了

③ 指标监控（P95 延迟、GC 次数、分配速率）
   回答：线上是否真的变好了

三者顺序：改动前用 ① 找热点 → 用 ② 验证改动 → 用 ③ 确认线上效果
```

```text
门禁设计要点
  · 只对「关键路径」的基准设阈值，避免噪音导致频繁失败
  · 阈值留出余量（如 +10% 才算回归），而不是要求完全一致
  · 在专用机器或固定配额环境下跑，减少抖动
  · 回归失败要能一键复现命令，否则会被当成噪声忽略
```

| 情况 | 表现 | 如何避免 |
| --- | --- | --- |
| 测了但没测对 | 优化了非热点 | 先剖析再动手 |
| 改了多处 | 无法归因 | 单变量修改 |
| 用开发数据测 | 生产数据分布不同 | 用真实规模与分布 |
| 只看耗时 | 内存或 GC 变差 | 同时看分配与峰值 |

- [ ] 基准至少跑 5 轮并报告分位数
- [ ] 记录了机器、版本与运行参数
- [ ] 用专用工具避免被编译器优化掉
- [ ] 关键路径有 CI 回归门禁（带余量阈值）
- [ ] 改动前后用同一套基准对比

- **分位数 的边界**：只在「报告分位数：P50 / P95 / P99，而不是只看平均」这一前提下成立，换输入或换环境要重新验证。

### 考点 10：排错——基准不做预热

- **现象**：首次运行包含编译与缓存冷启动，数据偏高。
- **处理**：先预热固定轮次，再统计中位数与波动。

### 考点 11：排错——只测一个规模

- **现象**：复杂度拐点被单点数据掩盖。
- **处理**：至少测三档规模，观察增长趋势再下结论。

### 考点 12：综合辨析——`性能` 与 `分位数`

- **辨析点**：`性能` 的定义是 系统在给定负载下表现出的吞吐、延迟、资源占用和稳定性；`分位数` 的定义是 报告分位数：P50 / P95 / P99，而不是只看平均。
- **答题要求**：面对 `性能剖析与基准测试：九种生态横向对照` 的题目，先判断描述的是 `性能` 还是 `分位数`，再归到对应定义，最后写出一个会让该定义失效的边界输入。

### 考点 13：排错评分点

- **现象分**：能写出 首次运行包含编译与缓存冷启动，数据偏高，而不是只写“程序有错”。
- **证据分**：保留触发 基准不做预热 的输入、版本和错误原文。
- **修复分**：按 先预热固定轮次，再统计中位数与波动 只改一处，并同时回归正常路径与边界路径。
