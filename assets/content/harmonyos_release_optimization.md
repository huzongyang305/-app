## 本节知识框架

**课程定位**：所属分类 `harmonyos`（鸿蒙 HarmonyOS NEXT），课程主题 `性能调优与上架 AppGallery`，学习阶段 移动，建议用时 55 分钟。

本课主线：把「能不能上线」拆成三组可度量的问题。第一组是运行时指标——启动耗时、帧率、内存峰值，必须先用工具采到数据再谈优化；第二组是构建产物指标——包体大小、模块拆分、混淆与资源裁剪，直接影响下载转化与合规；第三组是流程指标——签名、隐私声明、权限用途、审核规范与灰度发布，任何一项缺失都会让前面所有工程努力卡在提交环节。

**学完本课应当能够**

- 用启动阶段模型解释一次冷启动的成本分布，并按「首屏必需、可延后、可预热」三类重构初始化清单。
- 用 DevEco Profiler 与卡顿检测能力定位掉帧归因，区分测量、布局、绘制、合成四类瓶颈。
- 制定包体裁剪方案，说明 HAP/HSP 拆分、资源限定目录与依赖裁剪各自能省下什么量级的体积。
- 说清混淆的开关位置、保留规则与验证方式，解释反射与序列化入口为什么必须显式 keep。
- 按上架检查单核对签名、隐私政策、权限用途说明与兼容性声明，判断一次提审会被拒在哪一项。

## 核心概念定义

| 术语 | 操作性定义 | 常见边界与风险 |
| --- | --- | --- |
| 冷启动 | 进程不存在时从拉起应用算起到首帧可见的过程。 | 易错：把「页面可交互」也计入冷启动，导致指标口径不可比。 |
| 首屏必需 | 不执行就无法渲染第一帧的初始化工作集合。 | 易错：把所有启动期任务都归为必需，等于放弃优化空间。 |
| 掉帧 | 单帧主线程工作量超过刷新周期预算，画面出现跳跃。 | 易错：只看平均帧率不看最差帧，偶发卡顿被平均值掩盖。 |
| HiChecker | 运行时性能与规范检查能力，按事件方式回调主线程超时等问题。 | 易错：只在发布版开启，或只订阅不解析，采不到可用数据。 |
| Profiler | 采样式分析工具，提供帧、CPU、内存与 ArkTS 对象多视角时间线。 | 易错：在模拟器上取指标当作真机结论，数据分布完全不同。 |
| 内存水位 | 进程占用的可观测内存量，含 ArkTS 堆与原生资源。 | 易错：只盯 ArkTS 堆，忽略位图与缓冲区这类原生大头。 |
| 包体裁剪 | 通过模块拆分、资源限定与依赖收敛降低制品体积的手段。 | 易错：删掉多语言资源却忘了同步上架地区声明，被视为功能缺失。 |
| 代码混淆 | 构建期重命名标识符以抬高逆向成本的开关，需配套保留规则。 | 易错：反射、序列化与路由表入口未加 keep，运行时才暴露故障。 |

## 原理与运行机制

### 机制总览：把主观的「慢」翻译成可比较的数字

性能工作第一步永远是定义口径。启动要说明从哪一刻算到哪一刻，帧率要说明统计窗口与分位，内存要说明是峰值还是稳态。没有口径，优化就只能靠手感，回归也无从判断。

**教材衔接：冷启动的成本分布**

| 阶段 | 主要工作 | 可控手段 | 常见浪费 |
| --- | --- | --- | --- |
| 进程创建 | 系统 fork、运行时初始化 | 无可控项 | 应用入口做了业务逻辑 |
| 能力初始化 | 配置解析、依赖装配、状态恢复 | 按必需与可延后分组 | 全量预加载资源与数据库 |
| 首帧构建 | 组件树构建、测量布局绘制 | 精简首屏层级、骨架先行 | 首屏嵌重容器与远程图 |
| 数据补齐 | 网络请求、缓存读取 | 缓存兜底加占位视图 | 白屏等待接口返回 |

优化的主线是把后三个阶段的工作往后挪：首屏只画必要的，其余在首帧提交之后再触发。可行做法包括延迟初始化、按需加载模块、把可并行的 IO 与渲染重叠。有一条纪律要遵守：不要用「等待」代替「依赖」，靠轮询或超时兜底的写法只会把不确定性推给线上。

**教材衔接：掉帧的四类归因**

一帧的流水线是构建、测量布局、绘制、合成。构建慢通常是组件树过大或状态更新范围失控，表现为每次微小改动都触发大片重绘；测量布局慢常见于嵌套过深与权重分配反复求解；绘制慢多来自主线程上的自绘开销与复杂图形效果；合成慢往往是层数过多、透明叠加与大图采样不当。Profiler 的帧视角能把这四种瓶颈分开呈现，先确定归因类型再改代码，比盲目删特效有效得多。

**教材衔接：卡顿检测的三种采集方式**

| 方式 | 采集位置 | 能发现的问题 | 局限 |
| --- | --- | --- | --- |
| 帧率回调 | UI 框架逐帧统计 | 掉帧发生的时间点与页面 | 不告诉你是哪一段代码 |
| 主线程超时事件 | 运行时消息循环 | 超过阈值的长任务及其堆栈 | 阈值以上才有记录 |
| 函数级插桩 | 构建期注入 | 具体函数的耗时分布 | 有额外开销只适合灰度 |

工程上推荐组合使用：以帧率回调发现「什么时候卡」，用主线程超时事件回答「卡在哪段代码」，个别顽固问题再上插桩。检测能力应当只在调试与灰度构建开启，并把结果收敛成少量可上报的聚合指标，而不是把完整跟踪数据回传。

**教材衔接：内存的两条泄漏路径**

第一条是 ArkTS 对象引用未断：长生命周期容器持有短生命周期组件回调，页面销毁后整棵组件树仍在。第二条是原生资源未释放：位图、解码器缓冲、文件描述符与订阅句柄，这些不在 ArkTS 堆里，堆内存曲线看起来完全正常。分析方法是重复进出同一页面十几次，对比 Allocation 视角的对象数量趋势与进程内存水位趋势：前者涨说明引用没断，后者涨而前者平稳说明原生资源没释放。

**教材衔接：包体与构建产物的裁剪层次**

包体不是靠删图片解决的，要按层次看：模块层看是否把低频功能拆成按需加载的特性模块；资源层看多语言、多分辨率与深色资源是否用限定目录按需下发；依赖层看是否引入了整包只为用一两个函数；代码层看未使用的页面与旧实验分支是否已摘除。一个可执行的判据是：拆完之后首包体积下降明显，而核心路径功能完整。

**教材衔接：混淆与保留规则**

混淆在构建配置中按产物与构建模式开关，规则文件描述保留策略。必须显式 keep 的入口有四类：反射与动态查找的类名、序列化与反序列化的字段名、路由表里以字符串形式出现的页面路径、以及在资源与配置中被引用的标识。混淆的正确验证方式不是「打开了没报错」，而是打开之后完整跑一遍关键路径，尤其是跨页面跳转、本地数据读写与网络解析。

```json
{
  "buildOption": {
    "arkOptions": {
      "obfuscation": {
        "ruleOptions": {
          "enable": true,
          "files": ["./obfuscation-rules.txt"]
        }
      }
    }
  }
}
```

**教材衔接：上架链路上的合规项**

发布前必须凑齐四组材料：签名与包名（发布证书与 Profile 匹配、包名全局唯一）、隐私与合规（隐私政策链接、个人信息清单、权限用途说明与实际调用一致）、内容声明（分级、适老化与无障碍、地区与语言）、技术声明（设备类型、API 版本、依赖的系统能力）。审核最常见的四类退回原因是权限声明与实际使用不符、隐私政策打不开、后台行为未声明场景、以及首屏在声明的设备类型上不可用。

## 典型应用场景

| 场景 | 典型输入或前提 | 期望产物 |
| --- | --- | --- |
| 冷启动从 1.8 秒压到 1 秒内 | 有启动时间线与初始化清单 | 首屏必需项收敛，其余延后或并发，指标可复现 |
| 长列表滚动出现偶发掉帧 | 真机加帧视角采样数据 | 归因到布局或绘制，改动后最差帧耗时回落 |
| 提审被拒需整改 | 拒审意见与当前配置 | 权限用途、隐私链接、后台声明三项对齐后重提 |

- 典型现象：开发机启动很快，线上低配机型明显更慢。正确做法：把低端机型纳入固定回归设备，并用同一口径统计分位而不是平均值。
- 典型现象：开启混淆后某页面白屏，调试版正常。正确做法：检查该页路由是否在配置里以字符串出现，补 keep 后重新验证全链路。
- 典型现象：包体裁剪后应用市场下载量涨但投诉多。正确做法：核对被删资源是否对应已声明的语言与设备范围，恢复声明一致性。

### 最小验证场景

- 准备：一台低端真机与一台高端真机，同一次构建分别安装调试版与开启混淆的发布版。
- 观察：记录冷启动耗时、首屏帧率、进入并退出目标页十次后的对象数量与内存水位、发布版相对调试版的功能差异。
- 判定：启动达标、无最差帧超预算、对象数量与水位不随次数单调上升、发布版无独有故障，四项同时成立才允许提审。

## 代码/协议/SQL 示例

**教材衔接：把初始化按阶段拆开**

启动优化最有效的改动往往只是把一行调用挪个位置。下面的写法把首屏必需与可延后果分开，并把远程配置改成非阻塞。

```typescript
import { taskpool } from '@kit.ArkTS';

class EntryAbility extends UIAbility {
  onCreate(want: Want): void {
    this.loadTheme();          // 首屏必需：影响第一帧样式
    taskpool.execute(warmCache); // 可延后：不阻塞主线程
  }

  onWindowStageCreate(stage: window.WindowStage): void {
    stage.loadContent('pages/Index', () => {
      this.fetchRemoteConfig();  // 首帧提交后再发，失败有本地兜底
    });
  }
}
```

**教材衔接：卡顿事件的订阅与聚合**

采集到的事件要收敛成可上报的少量指标，避免把完整跟踪数据搬出设备。

```typescript
import { hilog } from '@kit.PerformanceAnalysisKit';

function reportFrameCost(costMs: number, page: string): void {
  if (costMs < 32) {
    return;                 // 两帧预算以内不上报
  }
  const bucket: number = Math.min(Math.floor(costMs / 32), 8);
  hilog.warn(0x0000, 'PerfWatch', `page=${page} bucket=${bucket}`);
}
```

**教材衔接：混淆保留规则示例**

反射与序列化入口必须保留，否则故障只会在发布版出现。

```bash
# obfuscation-rules.txt
-enable-property-obfuscation
-enable-toplevel-obfuscation
-keep-property-name
  bookId
  chapterIndex
  offset
-keep-file-name
  EntryAbility
  DetailPage
```

错误表现：把所有初始化堆在能力创建阶段，无关工作挤占首帧时间。

```typescript
onCreate(want: Want): void {
  this.loadTheme();
  this.preloadAllImages();   // 首屏用不到的图全部解码
  this.warmUpDatabase();     // 建表与迁移同步执行
  this.fetchRemoteConfig();  // 结果此刻还没回来
}
```

正确写法：只保留影响第一帧的部分，其余挪到首帧之后或并发执行。

```typescript
onCreate(want: Want): void {
  this.loadTheme();               // 只留首屏必需
}

onWindowStageCreate(stage: window.WindowStage): void {
  stage.loadContent('pages/Index', () => {
    taskpool.execute(warmCache);  // 并发预热
    this.fetchRemoteConfig();     // 首帧之后再取
  });
}
```

## 时间/空间复杂度或性能分析

| 指标 | 成本来源 | 参考量级 | 优化方向 |
| --- | --- | --- | --- |
| 冷启动 | 进程创建加能力初始化加首帧 | 低端机可达两秒 | 初始化分组、首屏层级精简 |
| 温启动 | 进程存活但页面重建 | 数百毫秒 | 状态缓存、避免重复请求 |
| 稳态帧率 | 每帧构建与绘制工作量 | 60fps 需单帧小于 16 毫秒 | 归因四类瓶颈后定点改 |
| 峰值内存 | 位图、缓冲、列表缓存 | 与图片尺寸平方相关 | 按显示尺寸采样、控制缓存条数 |
| 包体体积 | 代码、资源、依赖 | 首包决定下载转化 | 模块拆分、限定目录、依赖收敛 |

启动时间的分布比平均值更重要。用分位统计（P50 与 P90）而不是均值看回归，因为均值会被少量极端值稀释，而用户投诉几乎都来自 P90 尾部。低端机 CPU 主频与存储速度差距是数倍级别，只在旗舰机上验证等于没验证。一个可靠的经验是：首屏每减少一层嵌套容器、每减少一次同步 IO，收益在低端机上会被放大。

渲染优化的收益要按「帧预算」核算。主线程一帧只有约 16 毫秒，构建、测量布局、绘制加起来必须留有余量给合成。改动的优先顺序是：先减少不必要的状态更新范围，再降低节点数量，最后才是关特效。反过来做通常只能换来两三个百分点的平均帧率，而最差帧依然超预算，用户体感没有变化。

内存与包体是一对空间维度指标，但优化手段完全不同。内存要盯「单调上升」而不是绝对值：重复进出页面后对象数量持续增加，几乎可以断定存在引用未断；位图与缓冲区不进 ArkTS 堆，必须结合进程水位一起看。包体裁剪要区分「下载体积」与「安装体积」，前者影响转化率、后者影响用户存储抱怨，用同一份数据谈两个结论容易失焦。混淆与资源压缩还会改变可调试性——发布版必须能符号化还原堆栈，否则线上问题无从定位，这一步常被当成可选项而遗漏。

## 常见误区与易错点

- **只看平均值。** 均值漂亮但 P90 很差，用户投诉恰恰来自尾部。
- **只在模拟器取指标。** 帧率与内存分布和真机差异明显，结论不可迁移。
- **把启动当黑盒。** 没有阶段划分就无从判断该动哪一段，改完也无法验证。
- **用等待代替依赖。** 轮询或超时兜底把不确定性推给线上，表现为偶发白屏。
- **首屏塞满预加载。** 无关初始化挤占首帧，是最常见也最容易改的浪费。
- **只优化平均帧率。** 掉帧由最差帧决定体感，必须盯超预算帧。
- **只监控 ArkTS 堆。** 位图与缓冲区不体现在堆曲线上，泄漏会看不出来。
- **混淆后不回归。** 反射、序列化与路由字符串入口缺 keep，故障只在发布版出现。
- **声明与实际包内容不符。** 删了资源不改语言与设备范围声明、声明权限却不调用、调用了却没声明，都是高频拒审项。
- **把符号表与合规留到上线前。** 缺符号表时线上崩溃堆栈无法还原只能靠猜，隐私政策与后台场景声明临时补必然返工。

## 与其他知识点的关系

**教材衔接：调优与上架是全部课程的验收关口**

前面每一课的「易错点」在这里都会变成一个可度量指标：状态管理失控变成帧率下降，布局层级过深变成首帧耗时，订阅未注销变成内存水位上升，权限未对齐变成审核退回。因此本课的正确用法不是单独学一套工具，而是拿指标反查前几课的纪律是否被执行。

- 向上承接 `harmonyos_layout_system`：节点数量与嵌套深度直接决定测量布局耗时。
- 与 `harmonyos_state_management` 关联：更新范围失控是构建阶段掉帧的首要原因。
- 与 `harmonyos_network_data` 关联：缓存兜底与预取策略决定启动尾部与弱网体验。
- 与 `harmonyos_multimedia` 关联：位图解码尺寸是内存峰值的主要贡献项。
- 与 `harmonyos_system_capabilities` 呼应：后台场景声明与权限用途说明是审核重点。
- 与 `harmonyos_deveco_setup` 呼应：混淆开关、构建模式与签名配置都在工程配置层。
- 与 `android_development_*` 对照：Android 的启动与包体优化经验可迁移，审核项与混淆语法需重学。
- 与 `kotlin_coroutines_scope` 对照：作用域治理与延迟初始化解决同一类主线程阻塞问题。

| 关联课程 ID | 关联主题 | 关系说明 |
| --- | --- | --- |
| harmonyos_layout_system | 布局系统 | 层级与节点数直接构成首帧与掉帧成本 |
| harmonyos_state_management | 状态管理与数据传递 | 更新范围决定构建阶段是否出现连锁重绘 |
| harmonyos_network_data | 网络、数据与文件 | 缓存与预取策略影响启动尾部与弱网体验 |
| harmonyos_system_capabilities | 系统能力与权限 | 后台场景与权限用途是上架审核的核心项 |
| harmonyos_deveco_setup | DevEco Studio 与工程结构 | 混淆开关与签名配置都在构建配置层落地 |
| cross_platform_flutter | Flutter 跨平台开发 | 包体与帧率指标口径可迁移但工具链不同 |

## 自测题与参考答案

**教材衔接：题号 1** — 关于应用启动优化，下列做法正确的是？

**参考答案**：拆分初始化并按首屏必需、可延后分组。

本题正确项是「拆分初始化并按首屏必需、可延后分组」。启动优化的本质是重新分配工作发生的时间，只有先把清单按是否影响第一帧分类，才谈得上把无关项挪到首帧之后或并发执行。创建阶段同步预加载全部资源会把解码与 IO 压进首屏路径；把首屏必需的初始化推到交互之后会让第一帧缺内容；用轮询或超时兜底的写法只会把不确定性推给线上，三者都不是可行做法。

**教材衔接：题号 2** — 定位页面掉帧原因最合适的做法是？

**参考答案**：用分析工具采集帧率与主线程长任务。

本题正确项是「用分析工具采集帧率与主线程长任务」。掉帧必须区分构建、测量布局、绘制、合成四类归因，只有带时间线的采样数据能给出这种区分。构建日志里的接口耗时与代码无关；用户截图能说明现象却无法定位到帧与函数；在发布说明里承诺不出现卡顿不产生任何可验证信息，对复现与回归毫无帮助。

**教材衔接：题号 3** — 关于代码混淆，下列说法正确的是？

**参考答案**：开启前需为反射与序列化入口保留名单。

本题正确项是「开启前需为反射与序列化入口保留名单」。混淆会重命名标识符，凡是以字符串形式被查找的名字都必须在规则里显式保留，否则故障只在发布版出现。混淆通常让产物略有变小而非显著增大；它的目的恰恰是改变类与成员名称；它抬高的是静态阅读成本，与传输加密和运行时鉴权无关，不能替代安全评估。

**教材衔接：题号 4** — 上架前做包体裁剪，下列做法合理的是？

**参考答案**：按需拆分特性模块让首包只含必需。

本题正确项是「按需拆分特性模块让首包只含必需」。把低频功能从入口包剥离，首包只保留主路径，既降下载体积又不牺牲能力。删除全部语言资源会让已声明的地区与语言范围名不副实；把位图改成常量内嵌既增大代码体积又绕开按显示尺寸解码；签名信息是安装的必要条件，删掉只会导致产物无法安装。

**教材衔接：题号 5** — 这段启动期代码最可能造成的问题是？
class EntryAbility extends UIAbility {
  onCreate(want: Want): void {
    this.loadTheme();
    this.preloadAllImages();
    this.warmUpDatabase();
    this.fetchRemoteConfig();
  }
}

**参考答案**：无关初始化挤占首帧时间拖慢启动。

本题正确项是「无关初始化挤占首帧时间拖慢启动」。全量图片解码与数据库建表迁移都发生在第一帧之前，属于典型的可延后工作，把它们串在创建阶段会直接拉长冷启动。主题加载是首屏必需项，顺序本身没有错；数据库预热不足只会变慢而不会报错；远程配置此时尚未返回是设计使然，只要业务有本地兜底就不构成功能失效。

## 考点精讲

**教材衔接：高频考点**

1. 冷启动的四段成本分布，以及「首屏必需」这一分类标准。
2. 掉帧的四类归因与对应的分析视角，重点是看最差帧而非平均值。
3. 内存的两条泄漏路径：引用未断与原生资源未释放。
4. 混淆必须保留的四类字符串入口与发布版符号化还原。

**教材衔接：命题规律**

- 优化题把「看起来更努力」的错误做法与「按阶段重排」的正确做法并列，正确项一定包含分类依据。

- 上架题常把声明与实际行为的不一致设成正确或错误项，考的是合规意识而非接口记忆。
