## 本节知识框架

想象你开了一家快递公司。以前每位快递员（平台线程）都是全职员工——工资高、占工位，同时最多雇几百人。客户打电话来下单，如果快递员正在送别的件，客户就得等着。现在有了虚拟线程——相当于每位客户都配了一位"影子助手"，助手极轻量，可以同时存在几万个，客户打电话等着的时候助手自动去干别的，完全不需要客户操心。

本课会依次聊到四件事：

1. **虚拟线程是什么**——JVM 管理的轻量线程，大量阻塞任务可由少量平台线程承载。
2. **阻塞 IO 的痛点**——传统模型里，线程在等 IO 时什么都干不了，白白占着资源。
3. **线程池的取舍**——复用固定数量线程处理任务，但虚拟线程时代不再需要为每个请求绑定昂贵平台线程。
4. **结构化并发**——让子任务的生命周期受父作用域约束，便于取消和错误传播。

## 核心概念定义

先记住下面四个词，后面所有讨论都围绕它们展开。每个词都用一句话讲清"它是什么"，再补一句"容易踩什么坑"。

| 术语 | 一句话说明 |
| --- | --- |
| `虚拟线程` | JVM 管理的轻量线程，大量阻塞任务可由少量平台线程承载。坑：长时间持 synchronized 会钉住载体线程。 |
| `结构化并发` | 结构化并发让子任务生命周期受父作用域约束，便于取消和错误传播。坑：版本要固定，API 仍在预览中。 |
| `阻塞IO` | 调用线程在 I/O 完成前一直等待，简单直观但会占用线程资源。坑：虚拟线程里跑 CPU 密集任务不会变快。 |
| `线程池` | 复用固定数量线程处理任务，避免频繁创建销毁，需要定义队列和拒绝策略。坑：虚拟线程不需要传统线程池。 |

## 原理与运行机制

### 平台线程 vs 虚拟线程：全职员工 vs 影子助手

平台线程（platform thread）直接对应操作系统的线程。创建一个平台线程大约需要 1MB 栈空间，几千个就已经很吃力了。

虚拟线程（virtual thread）是 JVM 自己调度的"轻量线程"。一个虚拟线程只占几百字节，你可以同时开几万个。当虚拟线程遇到阻塞操作（比如读数据库、调 HTTP 接口），JVM 会自动把它从载体线程（carrier thread）上"摘下来"，让载体线程去干别的活。等 IO 完成了，虚拟线程再被"挂回去"继续执行。

```java
// 平台线程：最多几千个
for (int i = 0; i < 5000; i++) {
    new Thread(() -> {
        Thread.sleep(60_000);  // 每个线程占 1MB，5000 个 = 5GB
    }).start();
}

// 虚拟线程：轻松几万个
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    for (int i = 0; i < 100_000; i++) {
        executor.submit(() -> {
            Thread.sleep(1);  // 每个虚拟线程只占几百字节
            return "ok";
        });
    }
}
```

### 阻塞 IO：为什么虚拟线程特别合适

传统模型里，一个请求对应一个线程。当线程在等数据库返回时，它就"卡住了"——什么也干不了，但占着 1MB 栈空间。为了服务更多请求，你只能加更多线程，直到系统扛不住。

虚拟线程改变了这个等式：等 IO 的时候，虚拟线程自动让出载体线程。你不需要写回调、不需要学 reactive 编程，只需要像以前一样写同步代码——JVM 帮你在底层做"让出"和"恢复"。

```java
// 虚拟线程 + 阻塞 IO = 简单且高效
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    var future = executor.submit(() -> {
        // 这里调 HTTP 接口时，载体线程不会被占住
        return "virtual-thread-ok";
    });
    System.out.println(future.get());
}
```


### CPU 密集任务：虚拟线程不会自动加速

虚拟线程的强项是处理大量阻塞 IO，不是加速计算。如果你的任务是做数学运算、图像处理这种 CPU 密集工作，虚拟线程不会比平台线程更快——因为 CPU 核心数是硬限制。

```java
// 虚拟线程不会加速 CPU 密集任务
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    executor.submit(() -> {
        long sum = 0;
        for (long i = 0; i < 1_000_000_000L; i++) sum += i;
        return sum;  // 和平台线程一样慢
    });
}
```

### 结构化并发：让子任务"听话"

当你有多个并发子任务时，最头疼的问题是：一个失败了，其他的怎么办？父任务怎么知道所有子任务都结束了？

结构化并发（Structured Concurrency）让子任务的生命周期受父作用域约束——父作用域结束时，所有子任务必须完成（成功、失败或被取消）。就像一位项目经理，下班前必须确认所有组员都交了报告。

```java
// 结构化并发（预览特性，Java 21+）
// 伪代码示意，实际 API 可能随版本变化
try (var scope = new StructuredTaskScope<String>()) {
    Subtask<String> user = scope.fork(() -> fetchUser());
    Subtask<String> order = scope.fork(() -> fetchOrder());
    scope.join();
    // 到这里，user 和 order 都已完成
    return user.get() + order.get();
}
```

注意：结构化并发在 Java 21 仍是预览特性，使用时需要 `--enable-preview`。

## 典型应用场景

学完原理，我们来看几个真实场景，帮你把概念落地：

| 场景 | 你会遇到什么 | 怎么做 |
| --- | --- | --- |
| 高并发 Web 服务 | 每个请求等数据库、调下游 | 用虚拟线程代替平台线程 |
| 批量调外部 API | 同时调 100 个接口 | 虚拟线程 + StructuredTaskScope |
| CPU 密集计算 | 图像处理、加密 | 用平台线程池，不用虚拟线程 |
| 定时任务 | 周期性执行 | `ScheduledExecutorService` |
| 需要取消传播 | 子任务失败要取消其他 | 结构化并发 |

**选择与边界**：
- 使用 `虚拟线程` 时，记住它适合 IO 等待，避免长时间 `synchronized`，否则会钉住载体线程。
- 使用 `结构化并发` 时，记住要固定版本并覆盖边界输入，结论才可复现。
- CPU 密集任务仍然用传统线程池，虚拟线程不会让计算变快。

## 代码/协议/SQL 示例

### 完整最小示例

把下面的代码保存为 `VirtualThreadDemo.java`，用 Java 21+ 编译运行：

```java
import java.util.concurrent.Executors;

public class VirtualThreadDemo {
    public static void main(String[] args) throws Exception {
        // 1. 虚拟线程执行器：每个任务自动分配一个虚拟线程
        try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
            // 2. 提交任务并获取结果
            var future = executor.submit(() -> "virtual-thread-ok");
            System.out.println(future.get());
        }

        // 3. 批量并发：同时发起多个阻塞任务
        try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
            var futures = new java.util.ArrayList<java.util.concurrent.Future<String>>();
            for (int i = 0; i < 100; i++) {
                futures.add(executor.submit(() -> {
                    Thread.sleep(10);  // 模拟 IO 等待
                    return "done";
                }));
            }
            long doneCount = futures.stream()
                .map(f -> { try { return f.get(); } catch (Exception e) { return "err"; } })
                .filter("done"::equals)
                .count();
            System.out.println("完成: " + doneCount);
        }
    }
}
```

```text
virtual-thread-ok
完成: 100
```

运行方式：保存为 `.java` 后用 `javac --release 21` 编译、`java` 运行。

## 时间/空间复杂度或性能分析

虚拟线程的性能优势主要体现在"能同时处理多少阻塞任务"，而不是"每个任务更快"。

| 指标 | 平台线程 | 虚拟线程 |
| --- | --- | --- |
| 创建开销 | ~1MB 栈 + 系统调用 | ~几百字节 + JVM 内部操作 |
| 上下文切换 | 操作系统级，微秒级 | JVM 级，纳秒级 |
| 可同时数量 | 几千 | 几十万到百万 |
| CPU 密集任务 | 适合 | 不会更快 |
| 阻塞 IO | 浪费线程资源 | 自动让出载体线程 |

**测量方法**：固定输入跑一遍记录基线，再把并发度提高一个数量级复测；两次结果的差值才是结论依据。重点观察延迟拐点——当载体线程被占满时，延迟会突然飙升。

## 常见误区与易错点

下面是新手最容易踩的坑，每个都给了"症状→根因→修复"三步对照：

| 容易写错的做法 | 实际现象 | 原因与正确做法 |
| --- | --- | --- |
| 在虚拟线程里长时间持锁 | 载体线程被占用，扩展性消失 | 缩小临界区，必要时改用可重入锁 |
| 把虚拟线程当线程池复用 | 语义不符，收益有限 | 每个任务创建虚拟线程，用结构化并发组织 |
| 忽略阻塞式本地调用 | 载体线程仍被占满 | 识别真正的阻塞点，改用异步 API 或独立线程池 |
| 用虚拟线程跑 CPU 密集任务 | 不会加速，反而增加调度开销 | CPU 密集任务用平台线程池 |
| 在虚拟线程里用 ThreadLocal 存大量数据 | 内存暴涨 | 虚拟线程数量极大，ThreadLocal 开销被放大 |

**现场排错示范**：

**症状**：用了虚拟线程，但并发上去后延迟飙升，吞吐量不涨。
**根因**：虚拟线程里有长时间 `synchronized` 块，钉住了载体线程。
**修复**：缩小临界区，必要时改用 `ReentrantLock`（虚拟线程在 `ReentrantLock` 上阻塞时会自动让出载体线程）。

**容易混淆的相邻概念**：
- `虚拟线程` vs `平台线程`：虚拟线程由 JVM 管理、极轻量；平台线程对应操作系统线程、创建代价大。
- `结构化并发` vs `CompletableFuture`：结构化并发约束子任务生命周期，CompletableFuture 侧重异步结果组合。
- `阻塞IO` vs `非阻塞IO`：阻塞 IO 简单直观但占线程；非阻塞 IO 不占线程但编程复杂。
