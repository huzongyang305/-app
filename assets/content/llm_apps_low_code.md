## 核心概念定义

| 术语 | 操作性定义 | 常见边界与风险 |
| --- | --- | --- |
| 节点 | 工作流里一个原子能力，有输入变量与输出变量。 | 易错：一个节点做太多事，失败时无法定位。 |
| 变量 | 节点之间传递的命名数据，来自上游输出或表单。 | 易错：变量名与提示词占位符不一致，静默传空。 |
| 编排 | 用连线与条件确定节点执行顺序。 | 易错：缺少失败分支，异常时整条流程卡死。 |
| 知识库 | 平台内置的文档摄取、切块、嵌入与检索子系统。 | 易错：默认切块适合所有文档，长表格会被切断。 |
| 插件 | 封装外部接口供节点调用的可安装能力。 | 易错：把写操作插件无确认地挂在自动链路上。 |
| 代码节点 | 在沙箱里运行一小段脚本做数据整形。 | 易错：拿它替代模型做复杂推理，逻辑难维护。 |
| 私有部署 | 把平台与其存储运行在自有环境。 | 易错：只换服务器不换模型出口，数据仍出域。 |
| 发布渠道 | 应用对外的暴露形态，如网页、API、第三方消息端。 | 易错：多渠道共用一套权限与限流。 |

## 原理与运行机制

### 机制总览：三层结构

任何低代码平台都可拆成三层：能力层是模型、检索、工具与代码节点；编排层是条件、并行、循环与人工闸口；交付层是发布渠道与访问控制。评估一个平台是否够用，按这三层逐项对照即可，不必被界面风格干扰。

**教材衔接：节点类型与选择依据**

| 节点 | 输入 | 输出 | 什么时候用 |
| --- | --- | --- | --- |
| 开始 | 用户消息与表单字段 | 结构化变量 | 需要收集固定字段时 |
| 意图分类 | 一段文本 | 类别标签 | 后续要走不同分支 |
| 知识检索 | 查询变量 | 片段列表 | 答案依赖企业文档 |
| 模型推理 | 提示词与上下文 | 文本或对象 | 需要语言理解与生成 |
| 代码执行 | 上游变量 | 整形后的数据 | 确定性逻辑与格式转换 |
| 条件分支 | 布尔表达式 | 走某一条边 | 结果分派与兜底 |
| 迭代 | 数组 | 逐项结果聚合 | 对列表批量做同一件事 |
| 人工确认 | 待执行草案 | 批准或驳回 | 写操作与高风险动作 |

**教材衔接：代码节点的真实定位**

代码节点解决的是「模型不擅长的确定性」：字段改名、单位换算、去重排序、把对象数组拼成表格。它不承担推理，也不该承担长链路业务规则。

```python
def main(rows: list[dict]) -> dict:
    picked = sorted(rows, key=lambda r: r['ts'])[-3:]
    return {'count': len(picked), 'last': picked[-1]['status'] if picked else ''}

print(main([{'ts': 1, 'status': 'ok'}, {'ts': 2, 'status': 'warn'}]))
```

**教材衔接：工作流配置的形状**

平台导出的定义通常是节点表加边表。理解这一形状，就能用脚本做静态校验，例如检查是否存在没有入边的孤立节点。

```python
edges = [{'frm': 'start', 'to': 'llm'}, {'frm': 'llm', 'to': 'reply'}]
dsl = {'nodes': ['start', 'llm', 'reply'], 'edges': edges}
print(dsl['edges'][-1]['to'])
```

**教材衔接：知识库接入的两条路线**

| 维度 | 用平台内置知识库 | 复用已有向量库 |
| --- | --- | --- |
| 上手速度 | 快，上传即可用 | 需要写检索工具 |
| 切块与嵌入可控性 | 受平台参数范围限制 | 完全自主 |
| 数据一致性 | 需双写或定时同步 | 单一数据源 |
| 运维归属 | 平台侧 | 自建检索服务侧 |
| 适合阶段 | 验证与小型场景 | 已有检索资产或合规要求高 |

已有向量库时，把它包装成一个检索工具或外部知识节点接入，比再维护一份重复索引更可取；代价是切块与重排策略要在自己的服务里持续演进。

**教材衔接：私有部署的数据边界**

数据边界要按「传输、计算、存储、日志」四段分别确认。最常见的疏漏是应用与文档都落在内网，但模型推理仍走公网端点；另一类是平台自带的可观测性组件默认上报使用统计。

| 环节 | 需要确认 | 典型风险 |
| --- | --- | --- |
| 文档存储 | 对象存储位置与加密 | 备份被同步到公有云 |
| 向量存储 | 数据库是否在受控网段 | 索引导出即语料泄露 |
| 模型推理 | 请求出口与是否留存 | 敏感字段直接出域 |
| 日志追踪 | 链路里是否记录完整问题 | 个人数据长期留存 |

## 典型应用场景

| 场景 | 适合用平台的理由 | 需要注意 |
| --- | --- | --- |
| 内部问答快速试点 | 上传文档即可验证语料质量 | 默认切块常需调整 |
| 营销文案流水线 | 多节点串成模板化生产 | 品牌话术需人工闸口 |
| 工单自动分派 | 意图分类加条件分支直观 | 需接业务系统写接口 |
| 数据看板问答 | 可挂 SQL 类工具节点 | 必须限制只读与超时 |
| 多渠道客服 | 一次编排多处发布 | 各渠道限流与权限分开 |

- 典型现象：调试时一切正常，发布到渠道后回答变空。正确做法：检查表单变量是否在渠道侧真的传入，缺失字段常被当成空串。
- 典型现象：知识检索召回了段落但答案没引用。正确做法：确认检索输出变量确实绑定到了提示词占位符，而不是只挂在上下文面板上。
- 典型现象：迭代节点处理十条记录耗时线性累加。正确做法：确认是否支持并行迭代，并给单条设置超时。

### 最小验证场景

- 准备：一份十页文档与三个必答题，其中一题在平台默认切块下必然漏答。
- 观察：切换切块长度后该题是否恢复；导出配置确认修改是否落在知识库而非提示词。
- 判定：三题全部命中且给出来源；若靠改写提示词才答对，说明检索层问题被掩盖。

**教材衔接：给工作流做静态体检**

```python
def orphans(nodes, edges):
    linked = {e['frm'] for e in edges} | {e['to'] for e in edges}
    return [n for n in nodes if n not in linked]

print(orphans(['start', 'llm', 'reply', 'stale'],
              [{'frm': 'start', 'to': 'llm'}, {'frm': 'llm', 'to': 'reply'}]))
```

**教材衔接：把调用量与成本按应用聚合**

```sql
SELECT app_id,
       COUNT(*)                             AS req,
       ROUND(AVG(latency_ms))               AS avg_ms,
       SUM(total_tokens)                    AS tokens,
       SUM(CASE WHEN feedback = 'down' THEN 1 ELSE 0 END) AS bad
FROM app_invoke_log
WHERE day >= current_date - 7
GROUP BY app_id
ORDER BY bad DESC, tokens DESC;
```

## 时间/空间复杂度或性能分析

| 指标 | 随什么增长 | 典型区间 | 优化手段 |
| --- | --- | --- | --- |
| 单次编排时延 | 模型节点数量 | 每节点一次往返 | 合并节点、非模型步骤交给代码 |
| 知识库检索时延 | 片段数与是否重排 | 数十到数百毫秒 | 先粗召回再精排 |
| 迭代耗时 | 条目数乘单条时延 | 串行时线性 | 开启并行并设超时 |
| 配置可维护性 | 节点与变量数量 | 超二十节点明显下降 | 抽子流程与命名规范 |
| 存储 | 文档、向量与日志 | 与语料同阶 | 分层存储与日志脱敏 |

低代码平台的性能特征与自研代码没有本质差异，瓶颈同样在模型往返次数。差别在于「可见性」：平台把每次节点调用都摊在画布上，反而更容易看出哪一步是多余的。真正容易被忽略的是重试与超时策略，它们在画布上通常不可见，却会成倍放大尾延迟。

迁移成本要单独评估。平台把三类东西变成了资产也变成了负债：提示词与变量映射、编排结构与切块参数、渠道绑定。前两类可以用导出配置和回归用例承接，第三类往往要在业务侧重写。判断是否该迁出，看的是「平台表达力是否已成上限」，而不是「自研是否更体面」。

## 常见误区与易错点

- **用代码节点做推理。** 它适合整形与确定性判断，不承担语义理解。
- **把业务规则塞进提示词。** 规则变更时无法用单元测试守护，只能重跑全链路。
- **已有向量库还再建一份。** 双索引必然漂移，优先经工具节点复用。
- **私有部署只换应用服务器。** 模型出口、日志上报与备份链路都可能出域。
- **只测主路径不配失败分支。** 任一节点超时就会让整条流程停在中间。
- **画布节点越细越好。** 过细导致变量搬运成本与调试负担同时上升。
- **多渠道共用一套限流。** 一个渠道被刷会拖垮其他入口。
- **写操作插件缺人工确认。** 金额、删除、外发类动作必须有闸口。
- **默认切块一用到底。** 长表格与代码段需要专门策略。
- **忽略导出格式的版本兼容。** 平台升级后旧配置可能无法导入，需先做导出演练。
- **把平台当最终归宿。** 表达力触顶时要早做迁出评估，而不是持续加补丁。

## 自测题与参考答案

**教材衔接：题号 1** — 低代码平台的工作流里，代码执行节点的主要作用是？

**参考答案**：做数据整形与确定性逻辑。

本题正确项是「做数据整形与确定性逻辑」。LLM 节点负责语言生成，代码节点承担字段解析、格式校验和分支聚合这些可测试的确定步骤，让流程中可验证的部分不依赖模型发挥。它不能取代推理，也不负责前端脚本和日志落库，当成万能脚本容器会让工作流退化成难以维护的过程代码。

**教材衔接：题号 2** — 平台自带知识库与已有向量库并存时，通常更合理的选择是？

**参考答案**：复用已有向量库经工具节点接入。

本题正确项是「复用已有向量库经工具节点接入」。已有向量库承载了权限、增量管道和上游治理，用检索工具或外部知识库接口接进来，可以避免双写和数据漂移。整体迁移意味着重建摄取与运维链路，双份索引会让同一问题返回不一致结果并翻倍成本，完全放弃检索则在知识密集场景放大幻觉。

**教材衔接：题号 3** — 低代码应用要求私有部署，首先要确认的是？

**参考答案**：模型推理出口是否落在同一机房。

本题正确项是「模型推理出口是否落在同一机房」。私有部署的意义在于数据不出域，如果平台本地化却把请求转发到公网模型，敏感内容仍然外泄，合规目标落空。发布渠道和节点数量影响功能与复杂度，主题切换属于呈现层偏好，都决定不了数据边界，检查合规时容易把它们误当成关键条件。

**教材衔接：题号 4** — 从低代码平台迁到自研代码时，最大的隐性成本通常是？

**参考答案**：补齐提示词的评测与回归用例。

本题正确项是「补齐提示词的评测与回归用例」。平台里能跑通的提示词依赖隐式的编排、重试和护栏，迁到代码后要自建数据集、断言和回归流水线才能守住同样效果，这部分过去被界面隐藏了。基座模型不需要重训，机房资源与前端样式是一次性工程，唯独评测体系要长期投入，常被低估。

**教材衔接：题号 5** — 下面这段工作流 DSL 数据，print 输出的节点 id 是？
edges = [{'frm': 'start', 'to': 'llm'}, {'frm': 'llm', 'to': 'reply'}]
dsl = {'nodes': ['start', 'llm', 'reply'], 'edges': edges}
print(dsl['edges'][-1]['to'])

**参考答案**：回复节点 reply。

本题正确项是「回复节点 reply」。edges 列表的最后一条把 to 指向 reply，用负数下标取到的是终点字段而不是起点字段，因此输出 reply。把 frm 当成 to 会读到大模型 llm，直接取 nodes 列表末位虽然巧合也是 reply 但走的是另一个数据结构，误读 edges 则把字段名当成了节点标识。

## 术语速查

| 术语 | 一句话说明 |
| --- | --- |
| 节点 | 工作流中一个有输入输出的原子能力。 |
| 变量 | 节点间传递的命名数据，来自上游或表单。 |
| 编排 | 用连线与条件决定节点执行顺序。 |
| 知识库 | 平台内置的摄取、切块、嵌入与检索子系统。 |
