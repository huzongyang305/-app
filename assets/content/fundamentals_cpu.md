## CPU 是什么

CPU（中央处理器）是计算机的运算与控制中心：它不断从内存取出指令、解释执行，再写回结果。核心流程可以概括为 **取指 → 译码 → 执行 → 写回**。

## 指令周期

1. **取指（Fetch）**：程序计数器 PC 指向下一条指令地址，从内存读取指令。
2. **译码（Decode）**：控制器解析操作码和操作数。
3. **执行（Execute）**：ALU 做算术或逻辑运算，或访问内存。
4. **写回（Write Back）**：把结果写回寄存器或内存，PC 递增。

```text
while (true) {
    instruction = memory[PC];   // 取指
    op = decode(instruction);   // 译码
    result = execute(op);       // 执行
    write_back(result);         // 写回
    PC = PC + 1;
}
```

## 时钟频率与 IPC

性能不只是「主频越高越快」，粗略关系是：

```text
程序耗时 ≈ 指令总数 ÷ (主频 × 每周期执行指令数 IPC)
```

现代 CPU 通过流水线、超标量和多核来提升 IPC 与并行度。

## 流水线

把一条指令拆成多个阶段，让不同指令的不同阶段同时进行，就像工厂流水线：

```text
周期:   1    2    3    4    5
指令A: 取指 译码 执行 写回
指令B:      取指 译码 执行 写回
指令C:           取指 译码 执行 写回
```

理想情况下，每个时钟周期完成一条指令，吞吐量提升数倍。

流水线会遇到三类冒险：

- **结构冒险**：硬件资源冲突。
- **数据冒险**：后一条指令依赖前一条的结果。
- **控制冒险**：分支跳转导致取错指令。

解决办法包括转发（forwarding）、停顿（stall）和分支预测。

## 一条真实指令的样子

```asm
mov eax, [num1]   ; 把内存中的 num1 装入寄存器
add eax, [num2]   ; 与 num2 相加
mov [sum], eax    ; 结果写回内存
```

汇编指令会被转换为机器码，最终变成 CPU 能识别的 0/1 序列。

## 本课小结
CPU 的本质是「按地址取指令、按规则执行」。提升性能的两条主线是：**更高主频**和**更高并行度**。


## 指令执行周期速查

| 阶段 | 作用 | 依赖的部件 |
| --- | --- | --- |
| 取指（Fetch） | 按 PC 读取指令 | 指令缓存、PC |
| 译码（Decode） | 解析操作码与操作数 | 译码器、寄存器堆 |
| 执行（Execute） | ALU 运算或地址计算 | ALU、FPU |
| 访存（Memory） | 读或写数据 | 数据缓存 |
| 写回（Write Back） | 结果写回寄存器 | 寄存器堆 |

## 性能概念速查

| 概念 | 含义 |
| --- | --- |
| 主频 | 时钟频率，不一定等价于性能 |
| IPC | 每周期执行指令数，吞吐 = 主频 × IPC |
| 流水线 | 多阶段重叠执行，理想加速比等于级数 |
| 超标量 | 一个周期发射多条指令 |
| 乱序执行 | 由硬件动态重排，掩盖延迟 |
| 分支预测 | 预测跳转方向，猜错要清空流水线 |
| 数据冒险 | 后续指令依赖前面结果 |
| 流水线气泡 | 因冒险或预测失败产生的空转 |
| 超线程 | 一个物理核上跑多个逻辑线程，共享执行单元 |
| 多核 | 真正的并行执行单元 |

指令 2         取   译   执   访   写
指令 3              取   译   执   访   写

## 常见错误对照表

| 容易写错的做法 | 实际现象 | 原因与正确做法 |
| --- | --- | --- |
| 只看主频判断性能 | 结论错误 | 还要看 IPC、核数、缓存与指令集 |
| 认为流水线能线性提速 | 实测提升有限 | 受冒险、预测失败与访存限制 |
| 忽略分支预测失败代价 | 条件分支密集处性能差 | 减少不可预测分支，或用无分支写法 |
| 认为超线程等于双核 | 计算资源高估 | 超线程共享执行单元，提升有限 |
| 忽视缓存局部性 | 大数据遍历极慢 | 顺序访问、分块处理提升命中率 |
| 多线程盲目加速 | 甚至变慢 | 受限于共享资源与同步开销 |
| 用主频比较不同架构 | 不公平 | 不同微架构的 IPC 差异很大 |
| 认为指令数少就一定快 | 可能更慢 | 还要看每条指令的延迟与吞吐 |
| 忽略内存墙 | 计算单元等数据 | 优化数据访问模式往往收益更大 |
| 混用 GHz 与 MHz 换算 | 差 1000 倍 | 统一单位后再比较 |

## 补充：流水线、冒险与性能公式

### 五级流水线：一条指令的一生

```text
理想情况（每拍完成一条）
时钟  1     2     3     4     5     6     7
IF    指令1  指令2  指令3  指令4  指令5  指令6  指令7
ID          指令1  指令2  指令3  指令4  指令5  指令6
EX                指令1  指令2  指令3  指令4  指令5
MEM                     指令1  指令2  指令3  指令4
WB                            指令1  指令2  指令3

五级流水下，理想吞吐是每拍一条；但真实程序会出现「冒险」
```

| 阶段 | 全称 | 做什么 |
| --- | --- | --- |
| IF | Instruction Fetch | 取指令 |
| ID | Instruction Decode | 译码、读寄存器 |
| EX | Execute | 运算 |
| MEM | Memory | 访存 |
| WB | Write Back | 写回寄存器 |

### 三类冒险与解决手段

| 冒险 | 例子 | 解决 |
| --- | --- | --- |
| 结构冒险 | 取指与访存抢同一个内存端口 | 分离指令与数据缓存（I-Cache / D-Cache） |
| 数据冒险 | 后一条指令要用前一条还没写回的结果 | 转发（forwarding）、插入气泡 |
| 控制冒险 | 分支指令结果未知，下一条该取谁 | 分支预测 + 预测失败时冲刷流水线 |

```text
数据冒险示例
  add r1, r2, r3      ; r1 = r2 + r3
  sub r4, r1, r5      ; 需要 r1，但 add 还没写回

  解决：转发——把 EX 阶段算出的结果直接送给下一条指令，不等 WB
  无法转发时（如 load 后立即使用）插入一个气泡，代价是一拍
```

### 分支预测为什么关键

```text
一次预测失败要冲刷流水线，代价约等于流水线深度（10~20 拍）

现代处理器的做法
  · 记录分支历史，用模式识别预测走向（准确率常 >95%）
  · 预测「向后跳转」通常代表循环继续 → 预测跳转
  · 同时预取两个方向并保存结果（预测执行）

对写代码的启示
  · 分支可预测（同一方向反复）时快，随机分支代价高
  · 数据依赖密集、分支不可预测的代码，优化空间有限
```

### 乱序执行与超标量

| 概念 | 含义 | 好处 |
| --- | --- | --- |
| 超标量 | 一个周期发射多条指令 | 提高并行度 |
| 乱序执行 | 不按程序顺序执行，只在结果上保持顺序 | 掩盖访存与运算延迟 |
| 寄存器重命名 | 消除假的数据依赖 | 让指令真正并行 |
| 推测执行 | 提前执行分支后的指令 | 分支命中时零等待 |

**对开发者的意义**：写出「数据依赖少、访存规律、分支可预测」的代码，比纠结单条指令更有效。

### 缓存一致性：多核为什么不打架

```text
MESI 四状态
  M（Modified）  本核改了，与内存不一致，其他核没有副本
  E（Exclusive） 只有本核有副本，且与内存一致
  S（Shared）    多个核都有副本，与内存一致
  I（Invalid）   本核副本已失效

典型动作
  核 1 读同一地址 → 从 I 变 S（共享）
  核 2 想写入     → 先让其他核的副本失效，再进入 M
```

```text
伪共享（false sharing）
  · 两个线程操作同一个缓存行里的不同变量
  · 缓存行通常 64 字节：变量挨在一起会互相使对方失效
  · 表现：单线程很快，多线程反而更慢
  · 对策：填充（padding）让热点变量各占一行
```

### 性能估算公式

```text
程序时间 = 指令数 × CPI × 时钟周期
           └── 算法与编译器决定   └── 微架构决定

CPI（每条指令平均时钟数）= 理想 CPI + 各类停顿

IPC = 1 / CPI（每拍完成多少条指令）

三个优化方向
  ① 减少指令数：更好的算法与编译器优化
  ② 降低 CPI：更好的访存局部性、更少不可预测分支
  ③ 提高频率：受制程与功耗墙限制，现代提升有限
```

```text
一个实用推论
  缓存命中率对性能的影响往往大于指令条数：
  一次主存访问 ≈ 几百个时钟周期，而多数指令只要 1 拍
```

## 面试问答与自测

下面把本课考点换成面试追问。先口述自己的答案，
再对照参考回答检查是否遗漏了前提、边界或失败路径。

### 追问 1：CPU 执行一条指令的正确顺序是？

**参考回答**：正确答案是「取指 → 译码 → 执行 → 写回」，本课在「流水线」中说明：把一条指令拆成多个阶段，让不同指令的不同阶段同时进行，就像工厂流水线。指令周期为取指、译码、执行、写回，程序计数器随后指向下一条指令。本课还在「CPU 是什么」中说明：核心流程可以概括为 取指 → 译码 → 执行 → 写回。本课还在「指令周期」中说明：取指（Fetch）：程序计数器 PC 指向下一条指令地址，从内存读取指令。

### 追问 2：流水线技术主要提升了什么？

**参考回答**：流水线让不同指令的不同阶段并行执行，从而提高单位时间内完成的指令数量。其他选项：流水线让多条指令重叠执行，提高每周期完成的指令数（吞吐量）。针对「流水线技术主要提升了什么，」，本课在「流水线」中说明：理想情况下，每个时钟周期完成一条指令，吞吐量提升数倍。本课还在「流水线」中说明：解决办法包括转发（forwarding）、停顿（stall）和分支预测。本课还在「指令周期」中说明：写回（Write Back）：把结果写回寄存器或内存，PC 递增。

### 追问 3：分支预测主要用于缓解哪类冒险？

**参考回答**：遇到跳转指令时无法立刻确定下一条指令地址，分支预测提前猜测以缓解控制冒险。其他选项：分支预测针对跳转方向未知，属于控制冒险。针对「分支预测主要用于缓解哪类冒险，」，本课在「流水线」中说明：解决办法包括转发（forwarding）、停顿（stall）和分支预测。本课还在「补充·流水线、冒险与性能公式」中说明：对开发者的意义：写出「数据依赖少、访存规律、分支可预测」的代码，比纠结单条指令更有效。本课还在「时钟频率与 IPC」中说明：现代 CPU 通过流水线、超标量和多核来提升 IPC 与并行度。

### 追问 4：多核与超线程（SMT）的区别是？

**参考回答**：超线程利用流水线空闲提高利用率，遇到计算密集任务时提升有限。其他选项：多核是多个物理核心，超线程是在同一核心上跑多个逻辑线程并共享执行单元，因此提升有限。针对「多核与超线程（SMT）的区别是，」，本课在「流水线」中说明：把一条指令拆成多个阶段，让不同指令的不同阶段同时进行，就像工厂流水线。本课还在「时钟频率与 IPC」中说明：现代 CPU 通过流水线、超标量和多核来提升 IPC 与并行度。本课还在「指令周期」中说明：写回（Write Back）：把结果写回寄存器或内存，PC 递增。

### 追问 5：x86 与 ARM 常见的缓存行大小是？

**参考回答**：缓存以行为单位搬运数据，这正是伪共享与数据对齐优化关注的粒度。其他选项：x86 与 ARM 的缓存行常见为 64 字节。针对「x86 与 ARM 常见的缓存行大小是，」，本课在「CPU 是什么」中说明：CPU（中央处理器）是计算机的运算与控制中心：它不断从内存取出指令、解释执行，再写回结果。本课还在「一条真实指令的样子」中说明：汇编指令会被转换为机器码，最终变成 CPU 能识别的 0/1 序列。本课还在「本课小结」中说明：CPU 的本质是「按地址取指令、按规则执行」。
